## §1 도구를 넣고 고칠 때 (T)

- **T-01 실패에서 출발한다.** 새 도구는 "어느 작업에서 무엇이 실패했나"(평가 과제)에서 시작하고, API·명령을 하나씩 감싸지 않는다(R-02, R-05 evaluation first). 적용: 도구 커밋 메시지에 계기가 된 실패(예: `24a973f` ← 30d7e7c27 설치본의 낡은 오브젝트).
- **T-02 겹치는 도구를 만들지 않는다.** 같은 일을 하는 스크립트가 둘이면 고를 때 헷갈린다(R-02, R-03 bloated tool sets). 적용: 새로 만들기 전 `tools/`·`~/bin`·`claude-workspace/tools` 를 찾아 있으면 확장한다.
- **T-03 이름공간.** 관련 도구는 같은 접두·디렉터리에(R-02): `tools/harness/*`(리뷰·구현), `tools/perf/*`, `tools/ab/*`, `claude-workspace/tools/goto/*`.
- **T-04 출력은 고신호·토큰 효율.** 기본은 요약 몇 줄(PASS/FAIL 표·경로), 상세는 파일로·`--detail` 로(R-02 concise/detailed, 기본 상한). 잘라냈으면 다음에 무엇을 하라고 출력한다.
- **T-05 오류 메시지가 고치는 법을 말한다**(R-02, R-06 verbose errors, R-13 F9). 적용: guard 훅의 deny 문구처럼 "왜 + 대신 무엇".
- **T-06 실수하기 어렵게(poka-yoke).** 절대 경로, 명시 인자, 파괴 작업은 거부·확인(R-01). 적용: `goto rm` 이 활성 설치본을 거부하는 식.
- **T-07 사용법은 새 입사자에게 설명하듯, 실행인지 참조인지 밝힌다**(R-02, R-06). 적용: 도구 첫머리 docstring(목적·사용 예·산출물·한계), 스킬에는 "X 를 실행" / "X 를 참조" 를 구분.
- **T-08 고치면 다시 잰다.** 도구를 고친 뒤 대표 입력으로 다시 돌려 결과를 커밋 메시지에 적고, 구현과 설명을 같이 고친다(R-02 self-consistent, held-out). 적용: `compile_check` 수정 뒤 `--commits` 실행 결과(11.5s, 오브젝트 삭제)를 메시지에.
- **T-09 도구 집합은 작업 경계에서 바꾼다.** 도구 정의·MCP 서버·도구 단위 deny 를 세션 중에 바꾸면 프롬프트 캐시가 깨진다. 스킬 호출·파일 편집은 캐시를 지킨다(R-10).
- **T-10 결정론적인 일은 스크립트·훅으로, 판단만 LLM 으로**(R-05, R-06, R-11, R-07 "convert it to a hook"). 적용: 함정은 대기열에서 패치로 은퇴시킨다.
- **T-11 매직 상수 금지.** 기본값마다 이유 주석(R-06 voodoo constants).
- **T-12 사이드이펙트를 밝힌다.** 파괴·외부 게시 여부를 도구 머리말에 적고, 위험한 것은 guard 가 막는다(R-02 annotations).

## §2 서브에이전트를 열 때 (S)

- **S-01 목적은 문맥 격리(조사·검증)이지 역할극이 아니다**(R-14, R-08). 많이 읽고 짧게 돌려줄 일에 쓴다.
- **S-02 병렬 서브에이전트는 읽기·조사·검증만.** 코드를 쓰는 일은 한 흐름이 한다 — 병렬 작업자는 서로의 숨은 결정을 보지 못해 충돌한다(R-15, R-04 코딩은 병렬화가 적다).
- **S-03 위임문 4요소 + 결론 금지:** 목표, 출력 형식(파일 경로), 쓸 도구·자료, 경계(하지 말 것)(R-04). 독립 판정이 목적이면 내 결론·가설을 넘기지 않는다(등록부 #010).
- **S-04 결과는 파일로, 메인에는 짧은 참조만**(R-04 artifacts, R-03 1~2k 요약, R-08 "detailed results … consume significant context"). 적용: 하네스 에이전트는 `OUT/*.json` 으로 쓴다.
- **S-05 규모는 복잡도에 맞춘다.** 기본값: **메인 세션 모델이 Opus 면 서브에이전트 사슬이 기본, 그 밖의 모델이면 단일 세션이 기본(필요할 때만 띄운다)** — 사용자 결정 2026-10-27(리뷰 하네스의 정본 문장은 `skills/harness-review/SKILL.md` 「서브에이전트 구성」). 사슬이어도 단순한 일은 직접, 넓은 조사만 여럿 — 다중 에이전트는 토큰을 약 15배 쓴다(R-04, R-08 같은 사용량 한도). 적용: 배치 1개짜리 PR 은 reviewer·refuter 만(2026-10-23 #8253).
- **S-06 새 문맥에서 시작한다는 전제로 쓴다.** 대화·읽은 파일을 모르므로 필요한 경로·전제를 위임문에 넣는다(R-08).
- **S-07 같은 지시로 자주 띄우면 정의 파일로**(`agents/*.md`), 설명은 짧게·도구는 최소로(R-08).
- **S-08 서브에이전트 결과도 검증 대상.** 인용·경로·수치는 1차 자료로 대조한다 — 자기 확신에 찬 오류가 섞인다(R-04 LLM-as-judge + 사람 확인, 이 하네스의 refuter·gatekeeper).
- **S-09 큰 팬아웃 전에 사용자에게 규모를 한 줄로 알린다**(S-05 근거와 같음).

## §3 토큰·사용량 한도 대비 — 사용자 관점 (B)

사용자가 바쁘고 세션이 언제든 끊길 수 있다는 전제로, **끊겨도 사용자가 잃는 것이 없게** 한다.
- **B-01 상태는 문맥 밖 파일에.** 계획·진행·결정·다음 한 걸음을 작업 파일(세션기록·plan.json·harness-out)에 둔다 — 한도·압축·`/clear` 뒤에도 그 파일만 읽으면 이어진다(R-03 note-taking, R-04 save plan, R-14 progress file: 목표·접근·한 일).
- **B-02 단계마다 커밋·push·보드 한 줄.** 끝에 몰아서 하지 않는다(R-04 checkpoints·resume). 적용: Stop 훅이 worklog 없는 종료를 막는다.
- **B-03 무거운 작업은 미리 말한다.** 큰 팬아웃·전체 CTP·대용량 읽기·긴 루프는 규모와 이유를 한 줄로(R-09 서브에이전트·팀은 같은 한도).
- **B-04 큰 출력은 파일로, 문맥에는 요약만**(R-02 기본 상한, R-09 hook 으로 로그 전처리). 적용: 빌드·CTP·벤치 로그는 `> 파일` 후 `tail`·`grep`.
- **B-05 문맥 사용률 40~60% 를 넘기 전에 의도적으로 압축한다** — 모델은 진행 파일을 갱신한 뒤 사용자에게 `/compact <보존할 것>` 또는 새 세션을 권한다(R-14, R-07; 명령은 사용자가 친다). `/compact` 자체가 큰 요청이라 작업 사이에(R-10).
- **B-06 사용량 한도로 멈출 수 있는 작업은 자동 이어가기에 맞춘다.** 리셋 뒤 Claude Code 는 마지막 메시지를 다시 보내지 않고 "멈춘 곳" 부터 잇고, 권한 프롬프트에서 멈출 수 있으며, 연속 2회까지만 재시도한다(R-12) — 그래서 다음 단계가 파일에 적혀 있어야 하고, 무인 구간은 권한 허용 범위 안의 작업만.
- **B-07 `/clear`·세션 종료 전 인수인계.** `pre-clear` 스킬로 남은 일(결정 필요 / 그냥 할 일)·산출물 경로·도는 작업을 남긴다(R-07 새 세션 + spec, R-14).
- **B-08 같은 지점에서 두 번 바로잡아도 틀리면 문맥 오염이다** — 모델은 배운 것을 진행 파일에 적고 사용자에게 새 세션을 권한다(R-07).
- **B-09 상시 로드되는 것은 짧게.** CLAUDE.md ≤200줄 권고, 업무별 지시는 스킬로(R-09, R-07). 적용: §7.
- **B-10 캐시를 깨는 행동을 작업 중간에 피한다** — 모델 전환·도구 집합 변경(R-10).
- **B-11 유휴 중에도 문맥 전체를 보내는 것(루프·감시·세션 간 메시지)은 필요할 때만**(R-09 why usage climbs).
- **B-12 압축은 중요도로 자동 판별한다.** 실행 문구는 `공통-CLAUDE.md` 「Compact instructions」(P0 그대로·P1 한 줄+경로·P2 버림과 판별 신호) — 압축 요약이 그 절을 따른다(R-07·R-09 CLAUDE.md 로 압축 지시). 근거: 처음엔 재현율 우선 뒤 정밀도(R-03), 되찾을 수 있는 원문은 경로·URL 만 남기는 되돌릴 수 있는 압축(R-16), 진행 파일에 목표·접근·한 일(R-14), 짧게 만들려고 도메인 세부를 버리지 않기(R-19 brevity bias). 압축 뒤에는 CLAUDE.md·auto memory 가 디스크에서 다시 들어오고 호출한 스킬 본문은 **앞부분 5,000토큰만** 남으므로(R-22), 스킬의 중요한 지시는 위쪽에 둔다. 기계화: 대기열 H-20(PreCompact 가 상태 파일을 쓰고 `compact` SessionStart 가 다시 넣는다 — `session_start.sh` 는 matcher 없이 걸려 이미 압축 뒤에도 돈다).
- **B-13 PR 작업이 끝나면 불필요한 것만 지운다.** 판별: **다시 만들 수 있고, 어떤 문서(세션기록·보고서·PR 본문·JIRA·규칙)도 가리키지 않으면** 지우고, 가리키면 남긴다(지우기 전에 문서 리포를 경로로 grep). 사용자 지시·결정·증거·규칙은 남긴다. 실행 절차는 기존 정본: `post-merge`(브랜치·goto 캐시·`tc/pr-n`·보드·현황·staging, §2-1 하네스 산출물), `record` §5(세션 전용 메모리·`/clear`), 사본은 만들지 않는다(메모리 `백업-만들지-않기`). 기계화: 대기열 H-21(`post_merge.sh` 가 하네스 산출물 후보와 참조 여부를 계획에 함께 보인다).

## §4 문맥 구성 (C)

- **C-01 문맥은 유한 자원 — 가장 적은 고신호 토큰으로**(R-03, R-17 길이에 따른 저하).
- **C-02 한 세션에 무관한 일을 섞지 않는다**(R-07 kitchen sink). 다른 일이 오면 이어갈 것을 파일로 남기고 사용자에게 `/clear` 또는 새 세션을 권한다.
- **C-03 경로·식별자를 들고 필요할 때 읽는다(just-in-time)**, 자주 쓰는 것만 미리 고른다(hybrid)(R-03). 적용: 하네스 팩(implement_request·review_request)이 "미리 고른 문맥".
- **C-04 비슷하지만 답이 아닌 문서를 같이 넣지 않는다** — 방해 문서 하나도 성능을 떨어뜨린다(R-17).
- **C-05 실패는 남겨 배우고, 해소되면 정리한다**(R-16 keep the wrong stuff in, R-13 F3 해소된 오류 숨기기).
- **C-06 긴 작업은 목표·남은 일을 끝부분에 다시 적는다**(R-16 recitation — todo 갱신).
- **C-07 같은 틀의 예시로 쏠리지 않게 변화를 준다**(R-16 few-shot rut).

## §5 소스 지식 분리 (K)

소스 지식(엔진 코드가 어떻게 동작하나)은 하네스의 일부지만, **절차(스킬·규칙)와 섞지 않고 확인 가능한 참조 문서로 분리**한다.
- **K-01 절차와 사실을 나눈다.** 스킬·CLAUDE.md·규칙에는 "어디서 보나" 만, 사실 본문은 참조 문서에: 모듈 지식 `dev4-ai-source/modules/*`(§1~§4), 대기소 `staging/*`, 구조 정본 엔진 `AGENTS.md`(R-05, R-06 점진적 공개, R-07 "file-by-file descriptions" 는 CLAUDE.md 에서 빼고 링크).
- **K-02 사실 항목은 확인할 수 있게 쓴다:** 근거(file:line·함수), 기준 리비전, 확인 날짜, 확인 방법(정적/동적·실측), 상태(미수정/머지됨/정정). 시간에 민감한 내용은 이력 절로(R-06 avoid time-sensitive).
- **K-03 참조는 스킬에서 한 단계로**, 100줄 넘는 참조 문서는 목차를 둔다(R-06).
- **K-04 영역별로 나눠 필요한 것만 읽게**(R-06 domain-specific organization, R-05 서로 배타적인 경로는 분리).
- **K-05 낡음은 기계가 잡는다.** 인용한 file:line·심볼이 현재 develop 에서 그대로인지 스크립트로 확인한다 — LLM 이 믿고 쓰지 않는다(대기열 H-18).
- **K-06 한 사실은 한 곳(정본)에**, 다른 곳은 가리킨다(record 판단표).
- **K-07 틀린 사실은 지우지 않고 정정 표시로 남긴다** — 반박·재발 방지의 재료(예: 2026-10-23 loaddb NaN 주장 정정).

## §6 자가진화 방식 (E)

- **E-01 규칙집은 항목 단위로 더하고 다듬는다** — 통째로 다시 쓰면 세부가 깎인다(R-19 context collapse). 적용: 등록부·대기열은 append, 은퇴는 상태 표시.
- **E-02 짧게 만들려고 근거·사례를 버리지 않는다**(R-19 brevity bias). 규칙마다 근거 한 줄을 붙인다.
- **E-03 실패 → 말로 된 교훈 → 다음 작업 시작 때 해당 축만 읽는다**(R-20). 적용: `harness-implement` S2·`harness-review` 시작에서 등록부 해당 축.
- **E-04 생성·반성·정리를 나눈다**(R-19): 작업(생성) → 독립 리뷰·반증 서브에이전트(반성) → 등록부·대기열 정리(정리).
- **E-05 외부 근거를 주기적으로 다시 읽는다.** §0 의 확인일이 90일을 넘으면 다시 읽고 바뀐 권고를 규칙에 반영한다(사용자 지시: 최신 자료 기반). 1차 자료(공식 문서·저자 저장소·논문)만 근거로, 2차 요약은 출처로 쓰지 않는다(대기열 H-19 가 기한을 알린다).
- **E-06 규칙마다 기계화 판정을 하고, 기계로 막을 것은 하네스 패치로 은퇴시킨다**(R-11, R-07). LLM 이 기억해서 지키는 상태를 최종 해법으로 두지 않는다.

## §7 이 하네스의 현재 위반·개선 대기

현재 위반과 그 패치는 `claude-workspace/하네스-패치-대기열.md` 가 정본이다 — 상시 로드 CLAUDE.md 길이(B-09) H-17, LLM 기억에 맡긴 함정(E-06·T-10) H-01~H-16 외, 소스 지식 인용의 낡음(K-05) H-18, 외부 레퍼런스 갱신(E-05) H-19. 서브에이전트 위임문(S-03·S-06)은 하네스 에이전트 프롬프트가 경로만 넘겨 부합한다(2026-10-23 검토).
