# 리뷰 하네스 평가 — 고친 하네스가 실제로 나아졌나

근거·규칙: [`하네스-작성-규칙.md`](하네스-작성-규칙.md) §8 V-01~V-08 (R-26 "Demystifying evals for AI agents", R-27, R-28). 사용자 지시 2026-11-17.
과제 `harness/evals/tasks.jsonl` · 채점 `tools/harness/eval_score.py`(시험 `tools/harness/tests/test_eval_score.py`).

## 1. 언제 재나
- 하네스(스킬·에이전트 정의·판정기·팩 구성)를 바꾸기 **전과 후** — 같은 과제·같은 k 로. 차이가 과제 수에 비해 작으면 "나아졌다" 고 쓰지 않는다.
- 메인 모델이 바뀌었을 때 — §8 등록표의 구성 요소를 **하나씩** 빼서 잰다(V-06). 빼도 점수가 그대로면 은퇴 후보로 사용자에게 올린다.
- 무거우니(과제 하나 = 리뷰 한 번) 미리 규모를 알린다(S-09·B-03): 과제 수 × k × 리뷰 1회.

## 2. 과제 — 실제 실패에서, 정/부를 함께
한 줄 = 과제 하나(JSON). 필드는 `eval_score.py` 머리말이 정본이다.

| 출처 | kind | expect | 언제 더하나 |
|---|---|---|---|
| `references/놓친지적-반성.md` 의 타당한 놓침 | capability | finding | 그 항목을 append 할 때 같이 |
| 우리가 동적 확인한 🔴 (게시본·작성자 수정) | regression | finding | PR 이 머지돼 post-merge 할 때 |
| 반증 단계가 drop 한 지적의 자리(거짓 지적) | capability | no_finding | refute 결과에 drop 이 있을 때 |
| 우리 PR 에 달린 타당한 지적(자기 리뷰가 놓침, `리뷰에서-배운것.md` ⑤) | capability | finding | 그 항목을 쓸 때 |

- 두 사람이 같은 판정을 내릴 수 있게 쓴다(R-26) — `keywords` 는 지적의 핵심 낱말 묶음(AND of OR), 너무 좁으면 같은 지적을 다른 말로 쓴 시도가 unknown 이 된다.
- 과제는 그 PR 의 **우리가 리뷰한 head** 로 고정한다(뒤에 고쳐진 코드면 과제가 깨진다).
- 지금 4개(놓침 2·동적 확인 🔴 2). 처음 목표 20~50개 — 위 표대로 생길 때마다 더한다.
- capability 과제가 늘 통과하게 되면 regression 으로 옮긴다(R-26 graduate).

## 3. 돌리기
시도마다 깨끗한 산출 디렉터리에서 리뷰를 처음부터 돌린다 — 앞 시도의 산출물·git 이력이 답을 흘리지 않게(R-26: 이전 시도의 git 이력을 읽은 사례).
**평가 모드 `HARNESS_EVAL_PR=<pr>`** — 그 PR 의 정답이 팩에 실리지 않게 하고 기록을 덮어쓰지 않는다(2026-11-17 첫 기준점에서 실제로 찾은 유출 두 길):
- episodic: `examples/episodic/PR-<pr>.json`(그 PR 의 과거 리뷰·다른 리뷰어 스레드)을 팩에서 빼고, 리뷰 끝의 episodic 적재(그 파일을 덮어씀)를 건너뛴다.
- known pitfalls: 그 리뷰가 찾은 결함이 dev4-ai-source §3 에 올라가 같은 PR 의 팩에 다시 실린다 — `PR#<pr>`·`#<pr>` 가 적힌 항목을 뺀다(PR#8375 팩에 두 regression 과제의 답이 들어 있었다).
- unit suite: 그 PR 의 리뷰가 만든 suite(`origin.pr`·이름의 `PR#<pr>`)는 `unit_regress` 가 고르지 않는다 — suite 이름과 [defect] 결과가 곧 그때의 지적이다(PR#8375 판정이 그 결과로 '이전 리뷰의 지적' 을 그대로 다시 냈다).
- **에이전트 지시문에 '평가' 를 쓰지 않는다**(평소 리뷰와 똑같이) — "평가 실행(평가.md)" 이라고 쓴 첫 판에서 에이전트가 평가 정의를 찾다가 과제 파일과 예전 게시 코멘트를 열었다. 대신 하네스 규칙("팩에 없는 문서는 열지 않는다 — 소스 노트는 known pitfalls 절로만, claude-workspace·examples·references·harness·unit 아래는 열지 않는다")을 지시문에 분명히 쓴다.
- 시도가 끝나면 `python3 -m tools.harness.eval_leak_check --pr <pr> --jira <키> <에이전트 기록…>` — LEAK 이 나온 그룹이 정답 자리를 맡았으면 그 과제는 이번 시도에서 `contaminated` 로 적고 점수에서 뺀다.
- base 는 `git merge-base <head> upstream/develop` — 기본값(지금 develop)이면 그 뒤 develop 변경이 diff 에 섞인다.
```bash
# 과제 하나, 시도 i (i = 1..k, 기본 k=3) — 엔진 소스·빌드를 쓰므로 CTP·goto·벤치와 겹치지 않을 때(H-05)
b=$(git -C ~/dev/sources/cubrid merge-base <head> upstream/develop)
HARNESS_EVAL_PR=<pr> python3 -m tools.harness.run full --pr <pr> --sha <head> --base $b --out ~/dev/utils/harness-eval/<날짜>/<과제 id>/<i>
#   이어서 harness-review SKILL 의 판정·반증·종합 단계까지 — findings.adjudicated.json 이 그 디렉터리에 남아야 채점된다
python3 -m tools.harness.eval_score --tasks harness/evals/tasks.jsonl --runs ~/dev/utils/harness-eval/<날짜> --json ~/dev/utils/harness-eval/<날짜>/score.json
```
- `--sha` 리뷰는 보드에 "리뷰중" 을 띄우지 않는다(run.py). 평가 리뷰는 **게시하지 않는다** — post_review 를 부르지 않는다.
- 같은 PR·head 의 과제가 여럿이면 리뷰 하나를 돌리고 과제 디렉터리를 링크로 묶는다(`ln -s <과제A> <과제B>`).
- head 가 force push 로 사라졌으면 `gh api repos/CUBRID/cubrid/commits/<짧은 sha> -q .sha` 로 전체 sha 를 얻어 `git fetch upstream <전체 sha>`(작업 트리는 바꾸지 않는다).
- 하네스를 바꾼 판과 바꾸기 전 판을 같은 날 같은 과제로 돌린다(모델 갱신·서버 부하가 섞이지 않게).

## 4. 읽기
- 과제별 `pass@k`(한 번이라도 찾나)와 `pass^k`(늘 찾나). 리뷰는 실제로 한 번 돌리므로 **pass^k 를 품질로** 본다.
- `unknown` 은 앵커는 맞고 낱말이 안 맞은 시도다 — 그 시도의 findings·transcript 를 읽고, 같은 지적이면 과제 `keywords` 를 넓히고, 다른 지적이면 fail 로 본다(V-05). 판정은 사람이 정한다.
- 한 과제가 모든 시도에서 0 이면 과제부터 의심한다(head·앵커 줄이 맞나, keywords 가 너무 좁나).
- 결과는 바꾼 커밋 메시지(T-08)와 `§8 등록표` 의 "마지막 확인" 칸에 날짜·점수로 남긴다.

## 5. 하지 않는 것
- 과제를 점수에 맞춰 고치지 않는다 — keywords 수정은 unknown 을 사람이 읽고 "같은 지적" 으로 판정했을 때만, 그 사유를 과제 `note` 에.
- 평가 리뷰 결과를 PR 에 게시하거나 보드·worklog 에 리뷰로 올리지 않는다.
