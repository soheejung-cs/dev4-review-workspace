# 설계문서 공동 작성 (design-doc) — `/design-doc <CBRD-n | 증상>`

혼자 쓰지 않는다. **인터뷰 → 초안 → 사용자 수정 → 확정** 의 왕복이고, 각 질문은 사용자가 예/아니오·선택으로 답할 수 있게 닫는다(design-review §4). 코드는 인터뷰 도중에 **근거로만** 연다(팩) — 설계가 코드에 끌려가지 않게.

## 0. 시작
- 인자가 CBRD 키면 JIRA 조회(`howto/JIRA-API-사용법.md`), 증상 문장이면 **발번은 마지막에**(작업트래커 발번 규칙 — "미발번" 금지, 문서는 발번 후 `projects/CBRD-n/` 으로).
- 기존 문서 확인: `projects/CBRD-n/`, `projects/현황.md`, 보드 카드, `dev4-ai-source/modules/<모듈>.md` §3(이미 알려진 예비 이슈인가).
- 첫 메시지에 **인터뷰가 5라운드 안에 끝난다는 것**과 각 라운드의 주제를 알린다.

## 1. 인터뷰 라운드 (라운드마다 2~3 질문, `AskUserQuestion` 권장)
| R | 주제 | 반드시 얻는 것 |
|---|---|---|
| 1 | **증상** | 누가(사용자/QA/CI) · 무엇이(에러·느림·오답·정지) · 수치(회/초, ms, 행 수) · 언제부터(회귀 리비전·PR) · 재현물 유무 |
| 2 | **기대 동작과 경계** | 고쳐진 뒤 무엇이 참이어야 하나(관찰 가능한 문장) · 바뀌면 안 되는 것(호환·답안·성능) · 범위 밖으로 둘 것 |
| 3 | **영역 판정 4단계** (문서규약 앞머리) | ① 컴포넌트 [A]~[I] ② 불변조건 INV-1~5 ③ Tier ④ 공유·격리(S/A/B/C, 계약 3요소). 여기서 **팩을 한 번 만든다**: `python3 -m tools.harness.implement_pack --key CBRD-n --symbols … --grep "에러코드,메시지"` → 후보 함수·관문 경로·계층 간선(arch.json)을 근거로 판정을 사용자에게 **확인받는다**. 불변조건을 흔들면 "고칠 문제가 아니라 설계 재검토" 라고 말하고 R4 를 그 축으로 |
| 4 | **대안** | 최소 2개(사용자가 던진 것 포함) · 각각 장점/왜 안 택하나/남는 약점 · PG/InnoDB/Oracle 은 어떻게 하나(`oracle-reference` 는 요청 시만) · 채택안의 비유 한 줄 |
| 5 | **검증·결정** | TC 시나리오(재현→기대, 종류 sql/shell/동시성/벤치) · 측정이 근거면 계약(측정-규칙) · 남는 위험(수용/결정) · **결정 요청 Q1~Qn**(닫힌 질문, 선택지별 비용) |

라운드 사이에 **초안을 갱신해 보인다** — 문서가 자라는 것을 사용자가 보면서 고친다. 사용자가 "그건 아니고" 하면 그 자리에서 문서를 고치고 다음 질문.

## 2. 문서 — `claude-workspace/projects/CBRD-n/설계문서.md` (문서규약 형식)
```
# CBRD-n — <한 줄 제목>
- 유형: 구현 | 분석   - 상태: 설계중   - 브랜치 / 기준 리비전:   - 관련: 보드 #, PR#, source-notes 모듈
## 영역 판정          (4단계 표 + "이건 [X] 영역 작업이므로 ~를 고려해야 한다" 한 문단)
## 증상과 재현        (R1: 수치·회귀 지점·재현물 경로)
## 기대 동작 / 범위 밖 (R2)
## 아이디어           (채택안: 비유 · 계약 3요소 · 메커니즘 그림(mermaid 가능) · 바꿀 함수 목록 = 팩의 candidate 중)
## 대안표             | 대안 | 장점 | 왜 택하지 않았나 / 채택 | 남는 약점 |
## 외부 근거          (PG/InnoDB/Oracle)
## 검증 계획          (TC 시나리오 표, 측정 계약)
## 남은 위험 · 결정 요청  Q1… (상태: 미결/추천/결정)
## 부록: 팩 manifest  (implement_pack 산출 경로, candidate fids, codegraph_complete)
```
- 용어는 원문 그대로(`SCH_S`, `prev_version_lsa`), 필요하면 괄호 설명. 그림은 박스 이름이 아니라 **화살표에 의미**.
- 설계 리뷰를 받을 문서면 `design-review` §3 덱 구조로 `설계리뷰-덱.html` 을 같은 디렉터리에(아티팩트 게시는 사용자 허용 시만).

## 3. 등록 (문서가 확정되면)
1. `projects/현황.md` 행 추가(상태 "설계중"), 2. 보드 카드 — `agent-board new -l engine "[CBRD-n] 제목" <본문>`(카드 본문 = 문서 §증상 요약 + 문서 경로), 3. worklog 1줄, 4. `claude-workspace` 커밋·push.
5. 다음 단계 안내: 구현은 **`harness-implement CBRD-n`**(문서의 「아이디어」와 팩 manifest 를 plan 의 입력으로 쓴다).

## 하지 않는 것
- 사용자 답 없이 라운드를 건너뛰어 혼자 채우지 않는다(추정은 "추정" 표시 후 확인).
- 인터뷰 중 코드를 고치지 않는다. 벤치 DB 에 재현을 걸지 않는다(작업-생애주기 (B)).
- 한 라운드에 질문 4개 이상 던지지 않는다. 열린 질문("어떻게 생각하세요?")으로 결정을 미루지 않는다.
