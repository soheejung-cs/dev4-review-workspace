# 설계 리뷰 (design-review)

코드 리뷰가 아니다 — **잘 짜인 코드가 틀린 자리에 놓인 것**을 잡는 층이다.
근거 문서: `references/cubrid-사전설계문서.md` (1장 불변조건 5개 · 3장 컴포넌트 [A]~[I] · 4장 의존 관계·사이클 ·
7장 성능 임계도 · 13장 동시성 도메인, 특히 13.2 공유 자원 등급 S/A/B/C 와 원칙 P2).
래치·락·B트리 구조 판정은 `rules/설계-리뷰-규칙.md` **§9 BTL 표**로 한다 — lock/latch 판별은 BTL-01·02,
커플링 방향은 BTL-03. `references/` 원문 지도는 표가 diff 에 안 맞을 때 §0 진입표를 통해서만 연다.

## 0. 설계 리뷰가 필요한 신호 (하나라도 해당하면 연다)
**먼저 `rules/설계-리뷰-규칙.md`** — 불변조건·컴포넌트·의존·동시성 등급·산출물 형식을 한 문서로 요약한 것. 원문(1·3·4·7·8·13장)은 표의 '원문' 열이 가리킬 때만.
- 모듈 경계를 넘는 변경(다른 계층 헤더 새로 include, 반대 방향 호출)
- 클라이언트/서버 경계(`SERVER_MODE`·`CS_MODE` 가드)를 건드림
- 공유 자료구조에 필드·락·원자 연산 추가, 격리 도메인을 공유로 바꿈
- 새 컴포넌트·데몬·스레드풀 · WAL·MVCC·Vacuum·래치 프로토콜 근처
- 리뷰 중 "여기가 맞는 자리인가"가 한 번이라도 떠오름

## 1. 영역 판정 — 코드를 보기 전에 말로 정리한다
| 확인 | 어디 | 무엇을 얻나 |
|---|---|---|
| ① 어느 컴포넌트인가 | 3장 [A]~[I] | 책임·핵심 자료구조·확정 사항. 한 기능이 여러 계층에 걸치면 계층마다 따로 검토 |
| ② 불변조건에 걸리나 | 1장 5개 — 3-tier / **클라이언트 컴파일** / 3-way 빌드 / MVCC+Vacuum / ARIES WAL | 걸리면 "고칠 문제"가 아니라 설계 재검토 |
| ③ 성능 임계도 | 7장 Tier-0/1/2 | Tier-2 작업의 부작용이 Tier-0/1 을 오염하는지 |
| ④ 공유·격리 | 13.1 / 13.2 S·A·B·C | 공유면 **불변식 + 허용 동시성 + 완화 기법** 3요소 계약을 적는다(P2) |
첫 보고와 덱 앞머리에 **"이건 [X] 영역 작업이므로 ~를 고려해야 한다"** 로 적는다.

## 2. 아이디어마다 적을 것
- 한 줄 요약 + **비유**(예: 클래스 게이트 = "테이블마다 하나뿐인 통계 수집 예약석") — 리뷰어가 첫 장에서 이해 못 하면 실패.
- 계약 3요소(불변식/허용 동시성/완화 기법).
- **대안표**: 대안 / 장점 / 왜 택하지 않았나 — 채택안도 한 행으로 넣고 남은 열린 질문을 표시. 사용자가 던진 대안
  ("묵시적 커밋이면 안 되나")도 행으로 넣어 근거를 남긴다.
- 용어 설명을 아끼지 않는다 — chn(행 버전 번호), 락 수준 전/후 표(누가/어느 자원/전/후), 데드락 vs 라이브락 같이
  결정에 필요한 개념은 그림과 함께.
- 외부 근거: 같은 문제를 PG/InnoDB/Oracle 은 어떻게 하나 — 발명이 아니라 표준 동작의 이식임을 보인다.

## 3. 덱 구조 (예시: `examples/설계리뷰-덱-CBRD-27369.html`, 13장)
표지(수치) → 무엇이 무너졌나(메커니즘 그림) → 영역 판정 표 → 아이디어 한눈에 → 아이디어별 장(비유·그림·계약·대안표)
→ 락/자원 수준 전·후 → 외부 근거 → 남은 위험(수용/결정, 라이브락 등 그림) → **결정 요청 Q1~Qn**(결정된 것은 표시).
- HTML 덱은 **사용자가 아티팩트를 명시 허용한 경우에만** 아티팩트로 게시한다(기본 금지). 원본 HTML 은
  `claude-workspace/projects/CBRD-XXXXX/설계리뷰-덱.html` 에 남긴다.
- 그림은 메커니즘을 그린다(박스 이름이 아니라 화살표에 의미: "S: 존재 확인", "X: 커밋까지 보유").
- 리뷰어 질문이 오면 덱을 **고쳐서 재게시**한다(같은 링크) — 답변을 채팅에만 남기지 않는다.

## 4. 결정 요청은 닫힌 질문으로

어휘: "책임이 맞는 자리에 있나"를 말할 때 `imports/xmilex-git/skills/codebase-design/SKILL.md` 의 깊은 모듈·seam·adapter 용어를 쓴다(원 작성자 xmilex-git).
"A/B/C 중 어느 것", "수용하고 릴리스 노트에 적을까요" — 각 선택지의 비용과 남는 약점을 함께. 결정되면 덱과
`projects/CBRD-XXXXX/세션기록-*.md` 의 결정 상태 표를 갱신한다(`record` 스킬).

## 하네스로 시작하기 (2026-09-16)
리뷰 전에 `python3 -m tools.harness.run full --pr <n>` 을 돌려 `out/<pr>/<sha>/review_request[.batchN].md` 를 읽는다(코드+설계+성능 입력이 한 파일: 지시·의무 항목·자동 MEAS·arch 요약·팩). 지적은 `findings.json`(스키마 `harness/schemas/finding.json`, `layer` 로 코드/설계 구분) 으로 쓰고 `run full --pr <n> --findings <파일>` 로 판정·report.md·episodic 까지 이어간 뒤 보고서를 다듬는다. 설계: `arch.json`/`arch.mmd` 의 계층 간선과 리스크를 인용한다. 상세 `harness/ARCHITECTURE.md`.
