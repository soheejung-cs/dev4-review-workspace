# 설계 리뷰 (design-review)

코드 리뷰가 아니다 — **잘 짜인 코드가 틀린 자리에 놓인 것**을 잡는 층이다.
**하네스로 할 때는 `/harness-review <PR>`** — 실행 절차의 정본은 그 스킬이다(하네스는 설계 규칙 §0~§2 를 매번 주입한다).

## 0. 먼저 `rules/설계-리뷰-규칙.md` — 판단 기준의 정본
설계 리뷰가 필요한 신호(§0), 영역 판정 4단계와 컴포넌트 [A]~[I](§1), 불변조건 INV-1~5(§2), 책임 경계·의존 방향(§3), 동시성 등급 S/A/B/C 와 3요소 계약(§4), 성능 임계도(§5), 근거(§6), 산출물 형식(§7), 레퍼런스 펼칠 때(§8), 래치·락·B트리 판정표 BTL(§9, `BTL-03 위반` 형태로 인용)이 모두 거기 있다. 원문(`references/cubrid-사전설계문서.md`, `references/B트리락킹-Graefe서베이.md`)은 표가 diff 에 안 맞을 때 그 문서가 가리키는 절만 연다.
- 신호가 하나라도 걸리면 코드 리뷰와 별개로 이 스킬을 연다. 리뷰 중 "여기가 맞는 자리인가"가 한 번이라도 떠오르면 걸린 것이다.
- **코드를 보기 전에** 영역 판정을 말로 정리하고, 첫 보고와 덱 앞머리에 **"이건 [X] 영역 작업이므로 ~를 고려해야 한다"** 로 적는다. 불변조건에 걸리면 "고칠 문제"가 아니라 설계 재검토다.

## 1. 아이디어마다 적을 것 — 규칙 §7 산출물 형식에 덧붙여
- **비유**는 리뷰어가 첫 장에서 이해하게(예: 클래스 게이트 = "테이블마다 하나뿐인 통계 수집 예약석") — 첫 장에서 이해 못 하면 실패.
- **대안표**에는 사용자가 던진 대안("묵시적 커밋이면 안 되나")도 행으로 넣어 근거를 남긴다. 채택안도 한 행, 남은 열린 질문 표시.
- 용어 설명을 아끼지 않는다 — chn(행 버전 번호), 락 수준 전/후 표(누가/어느 자원/전/후), 데드락 vs 라이브락 같이
  결정에 필요한 개념은 그림과 함께.
- 근거는 규칙 §6 — 연구 논문·전공 교과로(절차 [`references/근거기반-설명-작성법.md`](../../references/근거기반-설명-작성법.md), 2026-10-23). **다른 DB 제품의 이름·구현은 근거로 쓰지 않고 덱·코멘트·문서에도 적지 않는다**(참조 구현 언급 금지, 2026-10-22 강화 — 저작권).

## 2. 덱 구조
**덱 작성·갱신 절차는 퍼스널 스킬 `design-deck`**(`claude-workspace/skills/design-deck`, 2026-09-30)을 따른다 — 한 장에 적게·쉬운 말, 표준 장 순서, 빌더·린트, 결정 반영 규약. 그 스킬이 없는 팀원은 아래 장 구성 요약만으로 만든다.
표지(수치) → 무엇이 무너졌나(메커니즘 그림) → 영역 판정 표 → 아이디어 한눈에 → 아이디어별 장(비유·그림·계약·대안표)
→ 락/자원 수준 전·후 → 근거(논문·교과서) → 남은 위험(수용/결정, 라이브락 등 그림) → **결정 요청 Q1~Qn**(결정된 것은 표시).
- HTML 덱의 아티팩트 게시는 `record` §4(사용자 명시 허용 시만). 원본 HTML 은
  `claude-workspace/projects/CBRD-XXXXX/설계리뷰-덱.html` 에 남긴다.
- 그림은 메커니즘을 그린다(박스 이름이 아니라 화살표에 의미: "S: 존재 확인", "X: 커밋까지 보유").
- 리뷰어 질문이 오면 덱을 **고쳐서 재게시**한다(같은 링크) — 답변을 채팅에만 남기지 않는다.

## 3. 결정 요청은 닫힌 질문으로
"A/B/C 중 어느 것", "수용하고 릴리스 노트에 적을까요" — 각 선택지의 비용과 남는 약점을 함께. 결정되면 덱과
`projects/CBRD-XXXXX/세션기록-*.md` 의 결정 상태 표를 갱신한다(`record` 스킬).
