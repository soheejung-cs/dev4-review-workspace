# 리뷰 대응 (review-response)

> 도구(dev4-review-workspace 루트에서): 수집 `python3 -m tools.harness.review_threads --pr <PR>`(미해결을 **대응 필요**(리뷰어가 마지막)와 **resolve 대기**(작성자가 마지막)로 갈라 `threads.md/json`, 2026-09-30) · 답글 `python3 -m tools.harness.review_reply --pr <PR> --draft <replies.md>`(기본 dry-run: 초안 `## T<idx>` 절 ↔ 스레드 매핑표, 승인 뒤 `--post`) · 새 지적의 인라인 게시 `python3 -m tools.harness.post_review`(머리말이 초안 형식의 정본). 도구가 고장 났을 때만 원시 명령: 수집 `gh api repos/CUBRID/cubrid/pulls/<n>/comments --paginate`(스레드마다 `original_commit_id` 가 있다), 답글 `gh api repos/CUBRID/cubrid/pulls/<n>/comments/<root_id>/replies -X POST -F body=@reply.md`.

> **서브에이전트 (2026-10-08)**: 수집 `harness-threads`, 결함 주장의 재현 `harness-repro`, 게시 전 **`harness-gatekeeper`**(재현 절차 완전성·층 태그·울타리·길이·제품명·한국어), 게시 후 `harness-auditor`(§6·§7). 띄울지의 기본값은 `harness-review` 「서브에이전트 구성」(메인 세션이 Opus 면 사슬, 그 밖은 단일 세션 — 사용자 결정 2026-10-27). 정의·흐름은 `agents/README.md`.

## 0. 누구 PR 인가
- **내 PR**(PR author 가 현재 `gh` 로그인 사용자): 수정 가능. 답글 → 작성자가 **봇이면 resolve**, **사람이면 resolve 안 함**(리뷰어가 닫는다).
  리뷰어가 "종결하겠습니다" 한 스레드는 그대로 둔다.
- **타인 PR**: 코드 수정 금지. 코멘트는 게시하지 않고 사용자에게 보고 → 승인 후에만.
- 컨테이너 예외: `.51` 에서는 내 PR 도 타인 PR 로 취급한다(사용자 지시 2026-09-16) — 정본 `claude-workspace/hosts/51.md` 「용도」.

## 1. 수집
`review_threads`(위 도구)로 모은다. 스레드 단위로 묶고(루트 id 기준), 분류: **결함 주장 / 확인 요청 / 제안 / 설계 이견**. 같은 결함을 두 스레드가
지적하면 하나에 상세, 다른 하나에 "~스레드에 적었습니다"로 연결.
**답하기 전에 지적 시점 커밋을 본다** — `review_threads` 가 지적 시점(`original_commit`)이 현재 헤드와 다른 스레드에 `⚠ 지적 시점 … ≠ head`(그 뒤 그 파일이 바뀌었는지까지)를 단다. 그런 스레드는 항목마다 "아직 있나 / 어느 커밋이 바꿨나" 대조표를 만든 뒤 답한다. 이미 닫힌 것은 커밋·줄 번호로 답하고 같은 자리를 두 번 고치지 않는다(같은 실수가 두 번 기록됐다: `references/리뷰에서-배운것.md` 2026-09-30 PR#7957, 2026-10-22 PR#8196 17번).

## 2. 결함 주장은 재현이 먼저
1. **수정 전 빌드(PR 헤드)로 재현** — 리뷰어가 준 시나리오를 그대로 스크립트로 만든다. 재현되지 않으면 그 사실을 답한다.
2. 원인 확정 → 수정 → **같은 스크립트로 release·debug 재검증**. 기능을 죽이지 않았는지 양성 대조도(예: piggyback 유지).
3. 리뷰어가 짚지 않은 **반대 방향**도 본다(같은 원인이 다른 증상을 내고 있었나) — 답글에 함께 적으면 신뢰가 붙는다.
3-1. **코멘트의 재현 절차는 그 결과를 낸 스크립트의 셋업까지 전부 적는다** — DDL, 앞선 PREPARE/EXECUTE, **그 사이의 ALTER/DROP/CREATE**, 세션 파라미터. **게시 전에 코멘트에 적힌 줄만 새 프로세스에 그대로 넣어 한 번 더 돌린다** — 재현되지 않으면 조건이 빠진 것이다(사용자 지시 2026-10-07 .50 "앞으로도 까먹지 않도록" — PR#8022 에서 같은 날 두 번 재발). 도구: `python3 -m tools.harness.repro_check --draft <초안> --dev <develop 설치본> --pr <PR 설치본>` — 초안의 `sql` 울타리 블록만 절마다 버릴 DB·새 SA 프로세스로 두 빌드에 돌려 `repro_check.md` 를 남긴다(H-27, 게이트키퍼는 `--verify` 로 그 산출물만 본다).
4. 스크립트는 `claude-workspace/projects/CBRD-XXXXX/repro/` 에 남기고, 재현용이면 JIRA 에도 첨부.

## 3. 답글 초안 → **사용자 검토 → 게시** (이 순서를 어기지 않는다)
사용자에게 이렇게 보여준다:
```
## N번 코멘트 — <작성자> (<파일:줄>, <주제>) · <봇이면 "답글 후 resolve">
> 답글 본문 …
```
**문체 규약** (사용자 지시 2026-09-16) — 밖으로 나가는 리뷰 글(코멘트·답글)의 문체 정본:
- **사람이 동료에게 말하듯** 쓴다. 표·헤더로 짜인 보고서 말투가 아니라 문단으로.
- **빌드 번호·시각으로 설명하지 않는다.** 재현 시나리오는 "세션 A 가 …하면, B 는 …" 식으로 **서술**한다.
- 구조: ① 인정/재현 사실 ② 원인(왜 그 코드가 그렇게 동작했나) ③ **반대 방향 손실**이 있었으면 그것도
  ④ **수정을 구체적으로**(어느 함수, 어떤 규칙, 왜 그게 맞나) ⑤ **수정 후 결과**(수정 전/후 대비, release·debug).
- **CTP 수치는 붙이지 않는다**(사용자 지시). 시나리오 실측(ms, 행 수, null_frequency 등)은 괜찮다.
- 제안을 받지 않을 때는 이유를 락 그래프·계약 수준에서 설명하고 대안(예: 릴리스 노트 기재)을 제시한다.
  "다르게 보시면 그대로 반영하겠습니다"로 닫는다.
- 재현·수정에 리뷰어의 확인이 도움됐으면 그 사실을 적는다.
- **번역하기 어려운 용어는 원문 그대로**(`SCH_S`, `prev_version_lsa`…) — 억지 한국어 번역 금지, 필요하면 괄호 설명. (2026-09-16)

## 게시 형식 — 첫 줄 · 본문 · 자리 (리뷰 코멘트·답글 공통)
**첫 줄 `[층] [카테고리] 이모지`**, 그 다음 줄부터 본문(층 표기 사용자 지시 2026-09-16, 카테고리·중요도 2026-09-17). 한 코멘트에 두 층을 섞지 않는다 — 섞이면 둘로 나눈다.
- `[설계 리뷰]` — 경계·불변조건·의존 방향·공유 자원 계약·대안 비교·락 수준. 근거는 `rules/설계-리뷰-규칙.md` 절 번호.
- `[코드 리뷰]` — 정확성·메모리/래치 짝·로깅·에러 경로·핫패스 비용. 근거는 `파일:라인` + 규칙 ID.
- 예: `[코드 리뷰] [주석 제안] 🟢`(suggestion 블록 동반) · `[코드 리뷰] [성능 검토] 🟡`(규칙 ID, 측정 요청이면 `[측정 요청]`) · `[코드 리뷰] [버그 가능성] 🔴` · `[설계 리뷰] [설계 판정] 🟡` · `[설계 리뷰] [문서 제안] 🟢` · `[코드 리뷰] [테스트 제안] 🟡`.
- **중요도** — 🔴 높음: 오답·정지·회복 불가·데이터 손상·머지 차단, **확인(static/dynamic)이 끝난 버그만**(우려 단계면 `[확인 질문] 🟡`) · 🟡 중간: 수정 권고, 회귀·비결정성·성능 회귀 가능, 확인 질문 · 🟢 낮음: 주석·문서·표기·이름(작성자가 미루어도 되는 것). 정의 정본은 `harness/schemas/finding.json` 의 `importance`·`category`(판정기 `adjudicate.fill_importance` 가 빈 importance 를 채우고, 보고서는 중요도 순으로 정렬한다).
- 카테고리: 버그 가능성 / 성능 검토 / 설계 판정 / 주석 제안 / 문서 제안 / 테스트 제안 / 측정 요청 / 확인 질문.
- **`[주석 제안]` 은 두 경우에만 단다**(사용자 지시 2026-10-27, PR#8213): ① **지금 있는 주석이 코드·동작과 다르다**(낡은 설명·틀린 계약 — 그 주석 줄과 다른 사실을 함께 보인다) ② 이 PR 이 **새 API**(함수·매크로·구조체 필드)를 만들어 그 **쓰임을 제한**해야 한다(호출 조건·소유권·스레드 등 계약). 설명 보강·의도 기록·용어 다듬기 같은 그 밖의 주석 제안은 **달지 않는다** — 보고서의 변경 지도(`function_notes`)에만 남긴다. 하네스: finding 의 `comment_basis`(`mismatch`·`new_api_contract`)가 없으면 판정기가 `withheld` 로 빼고 게시 도구도 건너뛴다.

**본문** — 모든 코멘트에 결과·영향·근거 문단(`왜 문제가 되는지:`)과 **제안+예시**(`제안:` — 주석은 ```suggestion 확정 문구(한 줄 앵커: 주석 + 원래 줄), 코드 스케치, 매뉴얼 문구, TC 시나리오, 확인 방법)가 있어야 한다. 에러 우려는 `확인 결과(정적/동적):` 를 먼저 적고 그 결과에 따라 지적/철회/질문을 정한다(오답/정지/회복 불가/비결정성/발견 가능성 중 무엇이며 누가 겪나, 근거는 수치·규칙 ID·스펙 절). 초안 형식(`## N번 코멘트` · `앵커:` 줄 · `[층]` 본문 · `---`)은 `tools/harness/post_review.py` 머리말이 정본이다 — 그 형식이어야 `--draft` 가 승인한 본문을 그대로 게시한다.
**읽히게** — 울타리는 줄 맨 앞에서 열고 닫는다(`제안:` 뒤 빈 줄), 절(`왜 문제가 되는지:`·`확인 결과:`·`제안:`)은 빈 줄로 가르고 ` / ` 로 잇지 않는다, 열거는 한 줄에 하나, 한 문단 600자·한 코멘트 🟢 1,200 · 🟡 2,500 · 🔴 4,000자, 반증·완결성 비평 결과는 본문에 붙이지 않는다(결론만 반영, 2026-10-06 PR#8034). `review_reply`·`post_review` 가 게시 직전 같은 검사(`tools/harness/md_lint.py`, H-32)로 `↻`(자동 교정)·`⚠`(경고)·`✗`(거부)를 알려 주니 **그 출력을 읽고 고친다**.

**자리** (사용자 지시 2026-09-16):
- **보고서는 게시하지 않는다.** 보고서(`리뷰보고서-PR<n>.md`)는 로컬·보드용이다.
- 코멘트는 **코드 줄에 각각 인라인**으로 단다 — `post_review`(reviews API, 앵커가 헌크 안인지 검사하고 ±3줄 안이면 맞춘다). 설계 층 코멘트도 관련 코드 줄(구조체 필드·상수 정의·호출 지점)에 앵커한다.
- **리뷰 대응 중 새로 찾은 지적·후속 검증 결과도 일반(issue) 코멘트가 아니라 원인 함수 줄에 인라인으로** 단다 — resolve 가능한 스레드가 되게(사용자 지시 2026-10-07 .50: "resolve 가능하게 함수 하위에 달아줘"). 원인 줄을 아직 모르면 오류를 내는 함수 호출 줄에 단다. 기존 일반 코멘트에 대한 회신만 일반 코멘트로.
- 예: `examples/리뷰보고서-예시-PR7899.md`(Findings 를 두 층으로 나눈 보고서).

## 4. 게시
답글은 `review_reply --post`(사용자 승인 뒤). `review_reply` 는 resolve 하지 않으므로 **봇 스레드 resolve** 만 직접:
```
TID=$(gh api graphql -f query='{repository(owner:"CUBRID",name:"cubrid"){pullRequest(number:<pr>){reviewThreads(first:50){nodes{id comments(first:1){nodes{databaseId}}}}}}}' -q '.data.repository.pullRequest.reviewThreads.nodes[] | select(.comments.nodes[0].databaseId==<id>) | .id')
gh api graphql -f query="mutation{resolveReviewThread(input:{threadId:\"$TID\"}){thread{isResolved}}}"
```
PR 본문 갱신은 `gh api -X PATCH repos/CUBRID/cubrid/pulls/<n> -F body=@file` (`gh pr edit` 는 이 서버에서 조용히 실패 — H-25).
**CI 트리거(`/run all`)는 사용자·리뷰어가 친다.** TC 답안을 고쳤으면 `/run all` 전에 `tc/pr-<n>` push 가 끝나 있어야 한다.
엔진 헤드가 그대로이고 TC 만 고친 재실행은 `/run all` 이 아니라 CI 본문(런 Summary)의 `/run rerun <run_id>` 다 — gha-ci 스킬 §1-6, `gha_rerun_cmd.sh`(2026-10-30).
게시로 끝나지 않는다 — §6(보드·세션기록)과 §7(배운것 append + `/self-evolution`)까지가 대응이다.

## 5. TC PR(cubrid-testcases-private-ex `tc/pr-<n>`) 의 답글
- **답안 변경 사유 코멘트**: 답안마다 ① 케이스 의도 ② 무엇이 바뀌었나(줄 단위) ③ 왜(엔진 커밋과 원인) ④ 의도 훼손 여부
  ⑤ 검증(재생성 빌드·실행 횟수). 예: `examples/리뷰답글-예시-PR7900.md` 뒤쪽.
- **리뷰어가 TC 추가를 제안하면** 만든다: 진입 순서를 **동기화**(예: `cubrid lockdb` 에 대기가 보일 때까지 기다린 뒤 진행),
  판정은 문장의 메시지가 아니라 **카탈로그/상태**로, 그리고 **수정 전 빌드에서 NOK 가 나는지** 확인해 TC 가 버그를 실제로
  잡는다는 것을 답글에 적는다. shell TC 는 `write_ok "<케이스> : <무엇>"` 로 서브체크마다 이름을 남긴다.

## 6. 게시 후
보드 카드에 요약 코멘트, `projects/CBRD-XXXXX/세션기록-*.md` 갱신 (`record` 스킬).

## 7. 배운 것을 남긴다 — 답글과 한 세트다 (사용자 지시 2026-09-18)

**답글을 게시했으면 `references/리뷰에서-배운것.md` 에 사례 항목을 append 한다.** 선택이 아니라 대응의 일부다 —
리뷰가 잡아준 것을 기록하지 않으면 같은 지적이 다음 PR 에 다시 온다. 그리고 **`/self-evolution` 을 돌려** 규칙으로 올릴 것을 정한다(규칙 문장의 정본은 `references/자가진화-규칙.md`, 사용자 결정 2026-10-27).

한 항목에 네 가지를 적는다:

| | 무엇 |
|---|---|
| ① 지적 | 누가·어느 파일에서 무엇을 지적했나 (한두 문장) |
| ② **검증** | 어느 함수·파일 정의를 열어 확인했나, 무엇을 돌렸나, 결과가 무엇이었나. **지적이 맞았는지 틀렸는지** |
| ③ 고친 것 | 커밋과 무엇을 바꿨나. 받지 않았으면 그 근거 |
| ④ **승격** | 다음에 어디서 같은 실수를 하나 — 규칙으로 올렸으면 `→ 승격: <파일 §> / 규칙 #NNN` 한 줄, 아직이면 일반화 문장 |

**어디에 무엇을 보내나** (중복이 아니라 역할 분담):

| 성격 | 목적지 |
|---|---|
| 리뷰가 나를 어떻게 고쳤나 (사례) | **`references/리뷰에서-배운것.md`** ← 이 단계 |
| 다음 작업에 바로 쓸 규칙 | `references/자가진화-규칙.md` (`/self-evolution`) 또는 해당 스킬 절 |
| 그 코드가 어떻게 동작하나 (검증된 코드 사실) | `dev4-ai-source` 해당 모듈 §2·§3 (`source-learning` 규약) |
| 일하는 방식이 바뀌었으면 | 해당 규칙 파일 / `claude-workspace/공통-CLAUDE.md`·`hosts/<끝자리>.md`(고친 뒤 `hosts/build.sh` — `~/.claude/CLAUDE.md` 는 생성물이라 직접 고치지 않는다) |
| 하네스·도구의 결함 | `claude-workspace/하네스-패치-대기열.md` (H-NN) |

**리뷰어가 틀렸던 경우도 적는다.** 무엇을 근거로 반박했는지가 다음 반박의 재료다.

답글 초안을 사용자에게 보일 때 **"배운 것에 무엇을 남길지"도 한 줄로 함께 보인다** — 게시 후 따로 묻지 않고
바로 append 할 수 있게.
