# 구현 리뷰 (code-review)

설계 리뷰(`design-review`)와 층이 다르다 — 여기서는 **이 코드가 맞게·빠르게 쓰였나**만 본다.
"여기가 맞는 자리인가"가 한 번이라도 떠오르면 `design-review` 를 연다.

## 0. 먼저 구분
- **내(soheejung-cs) PR**: 고칠 수 있다. 답글·resolve 규칙은 `review-response`.
- **타인 PR**: 코드 수정 금지. 코멘트는 게시하지 않고 사용자에게 보고 → 승인 후에만.
- **`.51` 컨테이너(리뷰 전용, 팀 공유 계정 예정)에서는 내 PR 도 타인 PR 로 취급한다**(사용자 지시 2026-09-16): 코드 수정 없이 코멘트만, 앞선 리뷰가 이미 지적·수정한 것은 HEAD 반영만 확인하고 재지적하지 않는다. 미응답 스레드에는 구체안으로 답글.

## 2. 규칙집 사용 규약 (규칙집 L10~23, 어기면 리뷰가 아니다)
- **측정 근거 없는 최적화 제안 금지.** 데이터가 없으면 "측정 먼저".
- **핫패스/콜드패스를 먼저 구분.** 에러 처리·초기화·종료에는 성능 규칙을 적용하지 않는다(가독성 우선).
- 우선순위 **정확성 > 메모리 안전성 > 가독성 > 성능.** 성능을 위해 UB 를 도입하지 않는다.
- **C 코드에 모던 C++ 관용구를 제안하지 않는다** (`.c` 가 C++17 로 컴파일돼도 C 스타일).
- 정량으로 — "빠르다"가 아니라 "캐시 미스 N회 감소". 임계값은 기준선이며 실측으로 조정.
- **규칙은 ID 로 인용한다** (`MEM-03 위반`). ID 가 있어야 리뷰가 검증 가능하다.

## 3. 정확성 리뷰의 순서 — 재현이 먼저
1. 지적(내 것이든 리뷰어 것이든)이 결함 주장이면 **수정 전 빌드에서 재현**한다. 증거 없이 고치지 않는다.
   재현 스크립트는 `claude-workspace/projects/CBRD-XXXXX/repro/` 에 남긴다 (`record` 스킬).
2. 원인을 코드로 확정한다 — "어느 프로세스에서 도는 코드인가"가 첫 질문(클라이언트 컴파일 결과는 서버로 XASL 만 건너간다).
3. 수정 → **같은 스크립트로 release·debug 양쪽 재검증** (debug 는 assert 를 위해). piggyback 류의 "생략" 로직은
   생략이 **여전히 일어나는 케이스**(양성 대조)도 함께 확인한다 — 안전하게만 고치면 기능이 조용히 죽는다.
4. 결과는 표로: 시나리오 / 수정 전 / 수정 후.
5. 반대 방향도 묻는다 — 한 방향(예: 롤백 시 오판)을 고치는 규칙이 다른 방향(커밋 시 놓침)도 틀리게 하고 있지 않았나.

## 4. 리뷰에서 자주 걸리는 것 (이 저장소)
- NULL snapshot 힙 읽기 = 가시성 검사 생략(최신 물리 버전). "최신 커밋"이 필요하면 snapshot fn 을 명시.
- 객체 계층 유니크 조회는 S 락 두 겹(`S_SELECT_WITH_LOCK` + dirty fetch). 컴파일 경로에서 카탈로그 행 락을 잡고 있지 않나.
- `ws_decache` 는 dirty 객체에 금지. 카탈로그 객체를 읽고 버릴 때 `ws_is_dirty()`.
- 서버 왕복 사이에 `SM_ATTRIBUTE*`/클래스 포인터를 들고 있지 않나(decache 로 dangling).
- 비용·선택도의 부동소수점 `==`(FP-01/02), 1회 측정 판정(MEAS-04), 행 루프의 컴파일타임 분기(BR-04).

## 5. 산출물

### 보고서는 "지적 목록"이 아니라 **요청자가 판단하는 데 필요한 것**으로 시작한다 (사용자 지시 2026-10-02)
"리뷰해줘" 는 "결함을 찾아줘" 가 아니라 **"내가 이 PR 을 두고 판단할 수 있게 해줘"** 다.
보고서 맨 앞 `## 0. 먼저 알아야 할 것` 에 아래를 **빠짐없이** 둔다 — 지적보다 먼저, 퀴즈보다 먼저.

| 넣을 것 | 왜 |
|---|---|
| **이 PR 이 무엇을 바꾸나** — 한 문단 + 단계 표 | 제목·본문만으로는 규모가 안 보인다 |
| **사용자가 보게 되는 변화**(스펙 변경·새 오류코드·매뉴얼 대상) | 머지 = 스펙 수용이다. 표로 develop ↔ PR 대비 |
| **TC·CI 상태** — 답이 바뀐 TC 수, 게이트가 막혔나, `/run all` 결과 | 승인 전에 확인할 외부 조건 |
| **⚠ 내(요청자) 작업에 미치는 영향** — 열린 내 PR 과 겹치는 파일·설계 충돌, 먼저 머지되는 쪽이 누구에게 재작업을 지우나 | **가장 자주 빠뜨리는 축.** `gh pr view <내 PR> --json files` 로 교집합을 세서 수치로 적는다. 이해충돌이 있으면 "내가 정하지 않는다"고 명시 |
| **이 리뷰를 얼마나 믿을 수 있나** — 정적/동적 여부, 커버리지 공백, 팩 품질, 반증 탈락률, 안 읽은 자료 | 신뢰도를 숨기면 요청자가 과신한다. "첫 판 지적의 N% 가 반증으로 죽었다"까지 적는다 |
| **머지 후 되돌릴 수 있나** | revert 비용(파일 수·오류코드 번호 이동·TC 동반·후속 PR 의존)이 "지금 막을까" 판단을 바꾼다 |
| **리뷰 분담** — 난이도·필요 인원·추천(`review-recommend` 계산) | 대규모를 혼자 승인하지 않게 |
| **내가 코멘트를 게시하면 생기는 일** — 작성자 작업량 추정, 코멘트로 풀 문제 vs 회의/JIRA 로 올릴 문제 | 게시 승인의 실제 비용 |
| **결정이 필요한 것 Q1~Qn** — 닫힌 질문, 선택지별 비용 | 요청자가 할 일이 명확해진다 |

그다음에 판정 → 영역 판정 → 확인했고 문제 없던 것 → 지적 → 보류 → 돌릴 것 순서다.

### 한국어 주석 리뷰 PR (`annotate`)
`function_notes` 를 PR head 소스에 `/* [리뷰] … */` 로 심어 **fork 안에** draft PR 을 연다 —
Files changed 한 화면에서 원 변경 + 한국어 설명 + 지적 번호를 같이 읽는다. 보고서와 diff 를 왕복하지 않아도 된다.
```bash
python3 -m tools.harness.annotate --pr <N> --head <sha> --notes notes.json --push --pr-create
```
base `review/pr<N>-base`(merge-base) ← head `review/pr<N>-ko`(PR head + 주석 커밋).
**upstream 에 열지 않는다** — 팀 PR 목록·알림에 끼지 않게 fork(`soheejung-cs/cubrid`) 안에서 연다.
**확인 퀴즈는 이 절이 다 채워진 뒤에 낸다** — 요청자가 읽을 것을 안 주고 묻지 않는다.

**보고서**: `imports/xmilex-git/skills/cubrid-pr-review/SKILL.md` 형식(TL;DR 판정 / Summary / Findings / JIRA / Existing Comments, 80줄 상한, 이모지·화살표 기호 금지, 한 지적 = 파일:라인 + 한 문장 + 근거)을 따르되 **Findings 를 `### [설계 리뷰]` 와 `### [코드 리뷰]` 로 나눈다**(설계 층은 영역 판정 문장으로 시작, 코드 층은 Blocking / Non-blocking / Questions). 끝에 `## 돌릴 것 (제안 -- 확인 후 실행)` 을 붙여 `review-testing` 매트릭스 제안을 적고 요청자 확인을 받는다. 예: `examples/리뷰보고서-예시-PR7899.md`. 보고서는 `claude-workspace/projects/<JIRA>/리뷰보고서-PR<n>.md` 에도 둔다(보드가 찾는다).

**보고서 형식·영문 체크리스트(들여온 것)**: `imports/xmilex-git/skills/cubrid-pr-review/SKILL.md`(한국어 리뷰 보고서 TL;DR/Findings 형식, 예 `imports/xmilex-git/review-reports/`), `imports/xmilex-git/skills/cpp-perf-rules/CHECKLIST.md`(§18 영문 체크리스트, ID 동일). 원 작성자 xmilex-git.

## 하네스로 시작하기 (2026-09-16)
리뷰 전에 `python3 -m tools.harness.run full --pr <n>` 을 돌려 `out/<pr>/<sha>/` 의 **`preamble.md`**(지시·의무 항목·자동 MEAS·arch 요약·스키마)를 한 번 읽고 **`review_request.batch<N>.md`**(팩)를 번호 순으로 읽는다(배치가 하나면 `review_request.md` 하나로 자립). 배치가 많으면 `batch_index.md` 의 배치별 파일·그룹 제안을 먼저 본다. 지적은 `findings.json`(스키마 `harness/schemas/finding.json`, `layer` 로 코드/설계 구분) 으로 쓰고 `run full --pr <n> --findings <파일>` 로 판정·report.md·episodic 까지 이어간 뒤 보고서를 다듬는다. 설계: `arch.json`/`arch.mmd` 의 계층 간선과 리스크를 인용한다. 상세 `harness/ARCHITECTURE.md`.
