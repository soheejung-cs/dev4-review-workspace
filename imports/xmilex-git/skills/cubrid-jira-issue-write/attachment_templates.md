# design.md / test.md 고정 템플릿

두 파일 모두 Markdown, 한국어. 섹션 이름·순서를 바꾸지 말 것.
해당 없는 섹션은 삭제하지 말고 `N/A` 한 줄로 남긴다(템플릿 일관성 = 토큰 최적화).
읽는 쪽도 LLM이다: 완성된 산출물이 아니라 판단에 필요한 포인트만 적는다. JIRA 본문과 중복 금지.

## design.md — 개발자 대상 설계 상세

JIRA 본문에서 금지된 코드 수준 상세(호출 경로, 자료구조, 함수/파일 단위 변경)를 여기에 담는다.

```markdown
# <TICKET_KEY> Design

## 배경
<본문 Description을 반복하지 말고, 설계 판단에 필요한 기술적 배경만 1~2문단>

## 설계 요약
<핵심 설계 결정과 그 이유를 3줄 이내로>

## 상세 설계
<모듈/함수/자료구조 수준의 변경 내용. 필요 시 하위 소제목, 코드 블록, 호출 경로 사용>

## 대안 검토
<검토했으나 채택하지 않은 대안과 기각 사유. 없으면 N/A>

## 영향 범위
<영향받는 컴포넌트, 호환성, 성능, 알려진 한계. 없으면 N/A>
```

- `상세 설계`가 유일하게 길이 제한이 없는 섹션이다. 나머지는 짧게 유지한다.
- 확정되지 않은 내용을 확정된 것처럼 쓰지 않는다. 미확정 항목은 `미정:` 접두어로 명시한다.

## test.md — QA TC 작성 가이드

QA가 `cubrid-testcases`(sql) / `cubrid-testcases-private-ex`(shell)에 넣을 TC를 어떻게 작성하면
되는지 안내하는 문서다. 개발 과정의 내부 검증 기록(측정 캠페인, 진단 빌드, sanitizer 등 QA 리포
밖의 수단)은 언급하지 않는다. TC를 실제로 쓰는 것은 저쪽 LLM이므로 시나리오·판정 포인트 중심으로
쓰되, **실행 레시피(DB 파라미터, 셋업 SQL, 실행 SQL)는 아는 경우 반드시 실제 값·실제 문장으로
적는다.** "적당히 큰 데이터", "관련 파라미터 조정" 같은 서술로 대체하지 않는다. 개발 검증에서
실제로 쓴 재현 레시피가 있으면 그것을 그대로 옮긴다.

```markdown
# <TICKET_KEY> Test

## 검증 포인트
<이 변경이 지켜야 할 관찰 가능한 행동을 항목별로. 재발 시 TC가 잡아야 할 결함 포함>

## TC 배치
<권장 리포와 경로. csql 스크립트+answer로 판정 가능하면 cubrid-testcases(sql),
파라미터 변경·서버 제어·트레이스 판독·외부 프로그램이 필요하면 cubrid-testcases-private-ex(shell)>

## 실행 레시피

### DB 파라미터
<cubrid.conf 값 블록. 각 파라미터가 왜 필요한지 한 줄 주석. 서버 재기동 필요 여부와
SET SYSTEM PARAMETERS 대체 가능 여부 명시. 기본값으로 충분하면 N/A>

### 셋업 SQL
<테이블 생성과 데이터 적재를 복사-실행 가능한 실제 SQL로. 데이터 규모가 판정 조건이면
그 규모가 왜 필요한지(문턱 등) 한 줄>

### 실행 SQL
<판정 대상 SQL과, 비교 기준이 필요하면 기준(직렬 등) SQL을 실제 문장으로>

## 시나리오

| ID | 시나리오 | 파라미터/데이터 조건 | 판정 기준 |
| --- | --- | --- | --- |
| T1 | <무엇을 유도> | <실행 레시피의 어느 조합인지> | <관찰 가능한 판정> |

## 주의사항
<결정성 함정, 선재하는 비결정성, 버전 의존 등. 없으면 N/A>
```

- `판정 기준`은 스크립트가 기계적으로 OK/NG를 가릴 수 있는 형태(결과 비교, 트레이스 라인 존재 여부, 정상 종료)로 적는다.
- 판정에 쓰면 안 되는 것(비결정적 출력 등)을 아는 경우 `주의사항`에 명시한다.
- 실행 레시피를 확정할 수 없는 항목만 `미정:` 접두어로 남긴다. 셋업→실행 SQL 없이 시나리오 표만 있는 test.md는 불합격이다.
