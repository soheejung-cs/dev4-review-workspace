## 변경의 요지

문자열 히스토그램에서 후행 공백을 떼는 기준이 저장측(컬럼 타입)과 프로브측(상수 타입)으로
갈라져 있던 것을, `hist::string_key_size_for_column ()` 하나로 모아 **컬럼 타입**으로 못박는다.
같은 뿌리에서 나온 두 번째 결함 — CHAR 컬럼의 LIKE/REGEXP 가 스트립된 값에 패턴을 맞추던 것 —
은 `histogram_repad_char_value ()` 로 컬럼 정밀도까지 되채워 실행기가 보는 모양으로 되돌린다.
정밀도는 HST2 헤더의 예약 4바이트(오프셋 28)를 `HV2_PRECISION` 으로 삼아 실어 나른다.

## 확인한 것

- **오프셋 28 재사용이 안전하다.** develop 전체에서 `HV2_RESERVED` 를 읽는 코드가 없다 —
  빌더가 0 을 쓰는 곳과 enum 정의뿐이다. 구 바이너리는 이 자리를 보지 않고, 신 바이너리가
  구 blob 을 읽으면 0 이 된다.
- **폭의 출처가 실제로 컬럼 정밀도다.** `mr_readval_char_internal ()` 이
  `precision = (domain != NULL) ? domain->precision : DB_MAX_CHAR_PRECISION` 으로 DB_VALUE 를
  만들므로 힙 CHAR 값은 컬럼 폭을 들고 온다. 최악값도 `DB_MAX_CHAR_PRECISION` = 2048 이라
  되채우기가 폭주할 여지는 없다.
- **blob 을 만드는 경로가 하나다.** PR head 의 `histogram_sampler_sr.cpp` 에 `build_blob<>` 호출부는
  한 곳(`col_collector_t::build`)뿐이고 collector 구현도 하나라, 폭을 못 싣는 샛길이 없다.
- **고쳐진 값이 실측과 맞는다.** PR head 빌드로 재현 fixture 를 올려 확인했다 —
  `t_vc.c='abcd '` sel 0.0625(100행), `='abcd    '` 0.025(40행),
  `t_ch.c LIKE 'abcd %'` 0.212556(340행), `REGEXP '^abcd +$'` 0.212556.

컨텍스트 팩은 4배치로 나뉘었고 **10개 항목이 예산에서 밀려났다**(`dropped 10`). 팩에 들어온
범위 안에서의 판정이다.

## 지적

### 1. 🟡 [코드] `histogram_repad_char_value` 주석이 되채우기가 꺼지는 조건을 틀리게 적는다

`src/optimizer/histogram/histogram_cl.cpp:1757`

주석은 "컬럼 노드에 `data_type` 이 없으면 정밀도가 없어 되채우기가 꺼진다"고 하는데, 2차 자기
리뷰에서 정밀도 출처를 blob 헤더로 옮긴 뒤로 그 조건은 존재하지 않는다. 실제 조건은
"CBRD-27251 이전에 수집된 blob 이라 폭이 0" 이고 해법은 `update statistics` 재수집이다.

두 조건은 성격이 완전히 다르다 — 하나는 질의 모양, 하나는 통계 나이다. 나중에 "LIKE 추정이 왜
안 고쳐졌나"를 쫓는 사람이 컬럼 노드를 들여다보며 엉뚱한 곳을 파게 되고, PR 본문에는 적혀 있는
마이그레이션 조건이 코드에서는 사라진다.

검증(static): PR head 파일에서 두 호출부(1989·2186)가 `histogram_reader.value_precision ()` 을
넘기고 `HistogramReader::reset` 이 `HV2_PRECISION` 에서 읽는 것을 확인했다. 정밀도 경로에
컬럼 노드는 더 이상 등장하지 않는다(코드셋만 콜레이션에서 읽는다).

제안 — 문장을 실제 조건으로 교체(코멘트에 `suggestion` 블록으로 첨부).

### 3. 🟡 [설계] 재수집 전에는 아무 일도 하지 않는데 그걸 볼 방법이 없다

`src/optimizer/histogram/histogram_builder.cpp:276`

업그레이드 직후의 운영 DB 는 전부 폭 0 인 blob 을 들고 있으므로 CHAR 컬럼의 LIKE/REGEXP 추정은
고치기 전과 똑같이 두 자릿수 과소추정을 계속한다. 그런데 관측할 신호가 없다 — 플랜 덤프의
`sel` 은 숫자만 보여 주고 `;info histogram` 도 폭을 찍지 않는다. "패치를 넣었는데 왜 그대로냐"가
그대로 문의가 되고, 답이 "재수집하세요"라는 걸 아는 사람은 PR 본문을 읽은 사람뿐이다.

같은 형태의 조용한 무동작을 오늘 CBRD-27138 에서도 봤다.

제안 — `;info histogram` 출력에 헤더의 precision 한 줄(0 이면 "재수집 전"). 범위를 넘으면
최소한 릴리스 노트와 JIRA 본문에 재수집 조건을 명시한다(JIRA 본문에는 이번에 넣었다).

### 4. 🟢 [코드] 되채우기는 컬럼 코드셋으로 세고, 바로 뒤에서 패턴 코드셋으로 라벨링한다 (질문)

`src/optimizer/histogram/histogram_cl.cpp:1805`

`histogram_get_like_selectivity` 는 `column_codeset` 을 컬럼 콜레이션에서 얻어 문자를 세는데,
`like_match_value` 의 `db_make_varchar (&src, ...)` 는 `db_get_string_codeset (pattern_db_value)` 를
쓴다. 저장 바이트는 컬럼의 것이므로 세는 쪽은 맞다. 다만 그 바이트를 패턴 코드셋으로 해석해
`db_string_like` 에 넣으므로, LIKE 의 `_` 가 문자 단위로 매칭하는 멀티바이트 값에서 결과가
달라질 수 있다.

라벨링 자체는 이 PR 이 만든 것이 아니지만, 이번에 바로 옆에 컬럼 코드셋을 쓰는 새 경로가 생겨
한 함수 안에 두 기준이 공존하게 됐다. 순 ASCII 에서는 차이가 없어 발견이 늦다.
`LANG_RT_COMMON_COLL` 이 호환 불가 조합은 거르지만 호환되면서 다른 코드셋 조합은 거르지 않는다.
실제로 그런 조합이 만들어지는지는 확인하지 못해 질문으로 남긴다.
