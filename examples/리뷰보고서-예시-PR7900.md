**이 변경은 [E] query(클라이언트 실행 `do_update_stats`) · [G] 스토리지(`statistics_sr`·`catalog_class`·`btree`) · [F] 트랜잭션(`mvcc_satisfies_committed`·`xlocator_fetch`) · [D] 통신(새 요청 1개, 4파일 계약 충족) 영역이고, 불변조건 5개를 흔들지 않는다.**

### 1번 — `src/query/execute_statement.c:4979`

[코드 리뷰] [버그 가능성] 🟡

편승(piggyback) 경로는 sm_update_statistics ()·히스토그램 빌드를 건너뛰면서 그 둘이 하던 이 세션의 클라이언트 캐시(class_->stats / class_->histogram) 무효화도 건너뛴다 → 같은 초 안의 수집이면 이 세션의 다음 컴파일이 구 통계·구 히스토그램을 쓴다.

**왜 문제가 되는지:** UPDATE STATISTICS 의 동기 계약(PR 본문: 반환 시 최신 통계)이 '이 세션' 안에서 깨진다. 정상 경로 sm_update_statistics () 는 schema_manager.c 4311~4320 에서 class_->stats·class_->histogram 을 free 하고 4332 에서 다시 받는다. 편승은 stats_updated=true 로 그 호출을 건너뛰므로(5057) 캐시가 그대로다. 다음 컴파일의 sm_get_class_with_statistics () 는 캐시된 time_stamp 로 서버에 묻는데(4155) 서버는 time_stamp >= ci_time_stamp 면 NULL 을 돌려주고(statistics_sr.c xstats_get_statistics_from_server, ci_time_stamp 는 초 단위 stats_get_time_stamp ()), 히스토그램 캐시는 그 갱신(updated) 이 있을 때만 다시 읽는다(4194~4198). 즉 이 세션이 캐시한 통계의 초와 편승한 수집의 초가 같으면 통계·히스토그램 모두 구 버전으로 컴파일된다. 사용자는 'Statistics updated successfully' 를 보므로 발견할 수 없다. 이 PR 이 겨냥한 '수 초 안에 다수 세션이 같은 테이블을 갱신' 시나리오에서 같은 초 충돌은 드물지 않다.

**제안:** 편승으로 stats_updated 가 true 가 된 자리(4979 뒤)에서 sm_update_statistics () 와 같은 무효화를 한다. 서버 왕복 뒤라 sm_class 포인터는 다시 받아야 한다(4896~4904 의 DECACHE 주의 그대로):
```c
if (stats_updated)
  {
    /* piggyback: the collection is on the server; drop this session's cached copies so the next
     * compile refetches them regardless of ci_time_stamp's second granularity (sm_update_statistics ()
     * does the same) */
    SM_CLASS *cached = NULL;
    if (au_fetch_class_force (class_mop, &cached, AU_FETCH_READ) == NO_ERROR)
      {
        stats_free_statistics (cached->stats); cached->stats = NULL;
        stats_free_histogram_and_init (cached->histogram); cached->histogram = NULL;
      }
  }
```
또는 sm_update_statistics () 의 4308~4320 을 sm_decache_statistics (classop) 같은 헬퍼로 뽑아 두 곳에서 부른다. TC: 세션 A 가 t 를 SELECT(캐시 적재) → B 가 UPDATE STATISTICS ON t 커밋 → 같은 초 안에 A 가 UPDATE STATISTICS ON t(편승) → A 에서 `SELECT /*+ RECOMPILE */` 의 플랜 카디널리티가 B 커밋 후 새 세션과 같아야 한다.

**검증(static):** schema_manager.c sm_get_class_with_statistics (4102~4210): stats 는 time_stamp 비교로, histogram 은 stats 가 갱신됐을 때만 재적재. sm_update_statistics (4308~4332): 두 캐시 free 후 재적재. statistics_sr.c xstats_get_statistics_from_server 677: `time_stamp >= ci_time_stamp` 면 NULL. ci_time_stamp 는 stats_get_time_stamp () (초). do_update_stats 5057: stats_updated 면 sm_update_statistics 호출 안 함. 재현(dynamic)은 하지 않음 — 같은 초 타이밍 재현이 필요해 TC 로 제안.

### 2번 — `src/storage/statistics_sr.c:168`

[설계 리뷰] [설계 판정] 🟡

게이트 대기는 트랜잭션 lock_timeout 을 그대로 따르고(LK_UNCOND_LOCK → logtb_find_wait_msecs), 타임아웃/데드락 메시지·lockdb 는 게이트 OID 의 클래스명 조회에 실패해 '객체 v|p|slot(bit14)' 만 찍는다 → 사용자가 어느 테이블의 통계 게이트인지 알 수 없다.

**왜 문제가 되는지:** 이 변경은 [G] 스토리지/[F] 트랜잭션 영역에 새 공유 락 자원(가짜 OID)을 추가하는 것이고 불변조건은 흔들지 않는다. 다만 §4 공유 자원 계약의 '발견 가능성' 이 비어 있다: lock_timeout 이 유한한 환경(예: 15s)에서 뒤에 선 UPDATE STATISTICS 는 편승 대신 ER_LK_OBJECT_TIMEOUT 로 실패하는데, lock_manager.c lock_describe_resource () 는 heap_get_class_name (gate_oid) 실패 시 er_clear 후 OID 구문(MSGCAT_LK_RES_DESC_OBJECT)으로 떨어지므로 메시지가 'object 0|123|16385 … waiting for …' 가 된다. 운영자는 bit14 를 알아야만 이것이 어느 클래스의 통계 게이트인지 역산할 수 있다. lockdb 출력(5657)도 같은 경로로 클래스명 없이 나온다. 무음 타임아웃은 아니다(er_set 은 된다) — 해석 불가가 문제다.

**제안:** lock_describe_resource () 의 주석이 말하는 확장점을 그대로 쓴다 — 게이트 OID 를 한 종류로 인식해 실 클래스명으로 풀어 준다:
```c
/* lock_describe_resource (), LOCK_RESOURCE_CLASS 분기 안 */
else if (OID_IS_UPDATE_STATS_GATE_OID (oid))
  {
    OID real; OID_GET_CLASS_OID_FROM_UPDATE_STATS_GATE (oid, &real);   /* slotid & ~MASK */
    if (heap_get_class_name (thread_p, &real, &classname) == NO_ERROR && classname)
      { snprintf (desc, desc_size, lock_res_desc_format (MSGCAT_LK_RES_DESC_STATS_GATE), classname); ... return true; }
  }
```
(oid.h 에 판별 매크로 1개, msgcat 문구 1개 — 'statistics-update gate of class %s'). lockdb 의 5657 경로에도 같은 매크로를 쓴다. 최소안: xstats_enter_update_gate () 에서 lock_object 실패가 ER_LK_OBJECT_TIMEOUT 계열이면 er_set 으로 클래스명을 덧붙인 전용 메시지를 낸다. 어느 쪽이든 PR 본문 Remarks 에 'lock_timeout 유한 시 대기자는 타임아웃 에러' 를 한 줄 적어 두면 좋다.

**검증(static):** lock_manager.c lock_object (6253~): LK_UNCOND_LOCK 이면 wait_msecs = logtb_find_wait_msecs (tran_index) → 트랜잭션 lock_timeout 적용. lock_set_error_for_timeout → lock_describe_resource: LOCK_RESOURCE_CLASS 에서 heap_get_class_name (gate_oid) 실패 → er_clear → OID 구문. 에러 자체는 설정됨(무음 아님). 게이트 락 카운트 +1(arch risk gate-imbalance) 은 커밋까지 보유하는 의도된 것으로 오탐.

### 3번 — `src/query/execute_statement.c:4963`

[코드 리뷰] [설계 판정] 🟡

편승 조건은 '내' 명시적 BUCKETS / RANDOM SEED 만 배제하고 '상대' 세션이 명시적 n BUCKETS 로 수집한 경우는 배제하지 않는다 → 기본 버킷 수를 기대한 요청이 더 거친(예: 10 버킷) 히스토그램에 편승한다.

**왜 문제가 되는지:** 4959~4962 주석의 계약은 'equivalent to (or stronger than) this request' 인데, 서버가 기록하는 것은 chn 과 statistics_strategy(fullscan 여부)뿐이라(catcls_get_class_stats 4536~4543) 상대의 bucket_count 는 알 수 없다. 세션 B 가 `UPDATE STATISTICS ON t WITH 10 BUCKETS` 를 커밋하는 동안 기다린 세션 A 의 `UPDATE STATISTICS ON t`(기본 default_histogram_bucket_count, 보통 300)는 stats_fresh·rebuilt 가 모두 참이라 10 버킷 히스토그램으로 끝나고 'Statistics updated successfully' 를 받는다. 오답은 아니지만 선택도 정밀도가 요청과 다르게 남고, 재현·발견이 어렵다(;info histogram 으로 버킷 수를 세어야 안다).

**제안:** 두 가지 중 하나를 고른다. (a) 계약을 코드로: _db_class 부기에 bucket_count 도 기록해(catcls_update_class_stats 인자 +1) 게이트 응답에 stored_bucket_count 를 실어 `stored_bucket_count >= 요청(또는 기본값)` 을 편승 조건에 추가한다. (b) 제한을 명시: 4959 주석과 PR 본문 piggyback 절에 '상대가 명시적 BUCKETS 로 수집한 경우도 편승한다(버킷 수는 상대 요청을 따른다)' 를 적고, 필요하면 `WITH n BUCKETS` 를 명시하도록 안내한다. 히스토그램 정밀도가 옵티마이저 품질에 미치는 영향이 크지 않다고 보면 (b) 로 충분하다 — 판단은 작성자에게.

**검증(static):** do_update_stats 4963~4966 조건식과 catcls_get_class_stats 4536~4543 의 저장 필드(chn, statistics_strategy) 대조: 상대의 bucket_count 를 알 수 있는 경로 없음.

### 5번 — `src/query/execute_statement.c:4953`

[코드 리뷰] [확인 질문] 🟢

클래스 목록(`UPDATE STATISTICS ON t1, t2`)은 클래스마다 게이트를 순서대로 잡고 커밋까지 쥐므로, 두 세션이 목록 순서를 뒤집어 실행하면 게이트끼리 데드락이 나고 한쪽 문장 전체가 abort 된다 — 의도한 동작인지 확인.

**왜 문제가 되는지:** 게이트는 X 자기충돌 락이고 커밋까지 보유(4934~4936 주석)한다. A: gate(t1) 획득 → gate(t2) 대기, B: gate(t2) 획득 → gate(t1) 대기 → 데드락 감지기가 한쪽을 ER_LK_UNILATERALLY_ABORTED 로 abort. PR 이전에도 같은 두 세션은 _db_histogram 행 락에서 데드락했으므로 악화는 아니지만, PR 제목이 '직렬화' 라 사용자는 '대기 후 성공' 을 기대할 수 있다. 확인 질문으로 남긴다 — 재현은 하지 않았다.

**제안:** 허용한다면 PR 본문 Remarks 에 한 줄로 명시하고 TC 로 고정한다: 세션 1 `UPDATE STATISTICS ON t1, t2 WITH FULLSCAN;` 세션 2 `UPDATE STATISTICS ON t2, t1 WITH FULLSCAN;` 을 오토커밋 OFF 로 동시에 → 한쪽만 ER_LK_UNILATERALLY_ABORTED, 재시도하면 편승 또는 수집으로 성공, 서버 무한 대기 없음. 피하고 싶다면 4843 루프에서 이미 db_object 로 풀린 class_list 를 클래스 OID 순으로 정렬해 게이트를 잡는다(출력은 TRACE 줄 순서만 바뀐다).

**검증(static):** xstats_enter_update_gate 168: lock_object (…, X_LOCK, LK_UNCOND_LOCK) 커밋까지 보유(해제 코드 없음, 의도). 클래스 루프 4888 안에서 클래스마다 호출(4953). 데드락 감지는 transaction/AGENTS.md 불변조건(wait-for graph 주기 검사) — 게이트 락은 일반 락 엔트리라 감지 대상.

**제안:** PR 본문 piggyback 절(pr-body 16)을 다음으로 바꾼다: "게이트 획득 전/후로 _db_class 행의 chn(통계 기록마다 catcls_update_class_stats 가 +1)과 부기 컬럼(checked_time/statistics_strategy) 존재 여부를 읽어, 대기 중 다른 세션의 수집이 커밋됐으면 재스캔·히스토그램 빌드·store 를 건너뜁니다(초 단위 timestamp 대신 chn 을 쓰므로 같은 초의 두 수집도 구분). 히스토그램이 실제 재작성됐는지는 클라이언트가 _db_histogram 행 chn 으로 따로 확인합니다."

### 7번 — `src/transaction/mvcc.c:652`

[코드 리뷰] [주석 제안] 🟢

mvcc_satisfies_committed 는 이름과 달리 '자기 트랜잭션의 미커밋 변경은 보인다'(own insert SATISFIED, own delete TOO_OLD) — 그 계약이 함수 안 한 줄 주석에만 있어 호출자가 '새 트랜잭션이 볼 커밋 상태' 로 오해할 수 있다.

**왜 문제가 되는지:** INV-4 는 '가시성 규칙을 명시하라' 다. 이 함수는 스냅샷 없이 힙을 읽는 새 경로의 규칙이고, xlocator_fetch·xbtree_find_unique·catcls_get_class_stats 세 곳이 쓴다. stats_get_histogram_generation () 은 자기 dirty 객체를 ws_is_dirty 로 따로 피하는데(2358~2365), 그 이유가 '이 함수는 자기 변경을 보여 준다' 와 맞물려 있음이 코드만으로는 드러나지 않는다. 643~659 의 분기 순서를 읽어 확인했다.

**제안:** ```suggestion
      /* committed (or own) insert, not deleted. 'committed' is relative to OTHER transactions: like
       * mvcc_satisfies_dirty, this transaction's own uncommitted insert is visible and its own
       * uncommitted delete hides the row -- callers wanting 'what a new transaction would see'
       * must exclude their own dirty objects (see stats_get_histogram_generation ()). */
```
(652 의 한 줄 주석을 위 문단으로 교체.)

**검증(static):** mvcc.c 643~668 분기 순서 확인: INSID 유효·!내것·활성 → TOO_NEW; DELID 무효 → SATISFIED(내 미커밋 insert 포함); 내가 삭제 → TOO_OLD; 타인 활성 삭제 → SATISFIED; 커밋된 삭제 → TOO_OLD.

### 8번 — `src/object/object_accessor.c:3797`

[코드 리뷰] [주석 제안] 🟢

obj_find_multi_attr_committed () 는 임의 클래스를 받는 공개 API 인데 committed 분기는 DB_NOT_PARTITIONED_CLASS 로 고정 조회한다 — 파티션 클래스에 쓰면 조용히 KEY_NOTFOUND 가 된다.

**왜 문제가 되는지:** 지금 호출자는 db_get_histogram_committed (_db_histogram) 하나라 실해는 없다. 하지만 헤더(object_accessor.h)에 노출된 함수라 다음 사용자가 일반 테이블에 쓰면 파티션 프루닝 없이 루트 인덱스만 보게 되고, 결과는 에러 없이 '없음' 이다(3830~3833 경고만). 3811 의 기존 경로 btree_find_unique 와 동작이 다른 점이 주석에 없다.

**제안:** ```suggestion
      /* S_SELECT lookup: the server answers without a lock for the classes that allow it (see
       * xbtree_find_unique ()); the found object is then fetched as its latest committed version, unlocked.
       * NOTE: no partition pruning (DB_NOT_PARTITIONED_CLASS) -- meant for catalog-like, non-partitioned

```
(3791~3792 주석을 교체.) 원하면 `assert (!sm_is_partitioned_class (op));` 를 3796 앞에 둔다.
