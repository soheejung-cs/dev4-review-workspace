## 설계 비교 (database-reference 참고)

- 이 PR 은 **다중 플랜 + 추정 선택도 기반 매칭 + 같은 플랜 병합** 구조로, database-reference 참고의 adaptive cursor sharing 과 같은 모양이다: 커서(여기서는 base 엔트리)당 자식 플랜 여러 개, 선택도 범위(여기서는 지문 band 1.5)로 자식을 고르고, 같은 플랜이면 자식을 늘리지 않고 범위를 합친다.
- 차이 1 — **피드백의 출처.** reference 는 실행 뒤 실제 행수로 bind-aware 를 승격하고 선택도 범위를 넓힌다. 이 PR 은 **컴파일 시 히스토그램 추정치만** 쓴다 — 추정이 틀린 값 영역(MCV 밖, 상관 컬럼)에서는 두 값이 같은 지문을 내고 같은 변형을 받는다. "플랜이 실제로 느렸다" 는 신호로 변형을 추가하는 경로가 없다(결정 Q ⑦).
- 차이 2 — **공유 범위.** reference 의 커서 캐시는 인스턴스 공유라 변형이 세션을 넘어 쌓이고, 이 PR 도 서버 XASL 캐시의 디렉터리를 모든 클라이언트가 공유한다(이전 판 "핸들당 초반 N회" 는 세션 단위 캐시 전제라 CUBRID 에서 성립하지 않아 작성자가 버림, 본문 Purpose). 다만 reference 는 서버가 플랜을 만들고 이 PR 은 클라이언트가 만든다 — 그래서 예약(COMPILE)·등록(REGISTER) 두 왕복과 고아 예약 문제(F1)가 생긴다. reference 에는 이 문제가 구조적으로 없다.
- 차이 3 — **학습 종료.** reference 는 자식 수 상한에 닿으면 오래된 자식을 버리고 계속 배우지만, 이 PR 은 limit 또는 32회 컴파일에서 디렉터리를 **고정**하고 변형을 교체하지 않는다(bind_variant.h 'No variant is ever replaced'; 단 변형 엔트리 단독 축출은 가능 — F12). 통계 갱신이 세대를 바꾸지 않는 것(F11)도 reference 의 '통계 갱신 → 커서 무효화' 와 다르다.
- 차이 4 — **관측성.** reference 는 자식별 실행 통계·선택도 범위를 뷰로 보여 준다. 이 PR 은 plandump 한 줄(plans/compiles/fingerprints/checks)과 디버그 로그뿐이고 pending 은 보이지 않는다(F1 C).
