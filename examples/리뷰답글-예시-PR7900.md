## 답안 변경 사유 (엔진 PR CUBRID/cubrid#7900, 헤드 `f79eda483`)

두 답안의 변경은 모두 #7900 의 커밋 `348e93909` **"Read histograms for the optimizer without locking _db_histogram rows"** 에서 옵니다. 이 커밋 전에는 질의 컴파일 때 옵티마이저가 히스토그램을 읽는 경로(`stats_get_histogram` → `db_get_histogram` → `db_find_multi_unique`)가 객체 계층의 **잠금 조회**였습니다 — 서버 `sbtree_find_unique` 가 `S_SELECT_WITH_LOCK` 으로 `_db_histogram` 행에 S 락을 잡고, 이어지는 `LC_FETCH_DIRTY_VERSION` fetch 가 다시 S 락을 잡아 **트랜잭션 끝까지** 보유했습니다(#7476 에서 히스토그램이 기본 수집되면서 생긴 부수효과). 그래서 오토커밋 OFF 세션이 `UPDATE STATISTICS` 를 커밋하지 않으면 같은 테이블의 모든 SELECT 컴파일이 그 행의 X 락 뒤에서 블록됐고, 반대로 컴파일만 한 세션의 S 락이 `UPDATE STATISTICS` 를 막았습니다. `348e93909` 는 옵티마이저 읽기를 **잠금도 트랜잭션 스냅샷도 만들지 않는 "최신 커밋 버전" 조회**(`btree_find_multi_uniques(S_SELECT)` + `LC_FETCH_COMMITTED_VERSION`)로 바꿨습니다. 쓰기 경로(`UPDATE STATISTICS` 자체, DDL)는 그대로입니다.

### 1. `shell/_06_issues/_14_1h/bug_bts_13242/cases/issue_13242.answer`

케이스 의도: SERIALIZABLE 격리에서 `SELECT ... FOR UPDATE` 가 잡는 락을 `cubrid lockdb` 로 확인(6개 테스트 포인트).

- **지운 것**: 각 테스트 포인트의 `Object type: Instance of class () = _db_histogram.` / `Granted_mode = S_LOCK, Count = 2` 블록 전부(합계 20개), 그리고 그에 딸린 파생값 — `Current number of objects which are locked` 9→6, 16→11, 14→8, 15→9 와 `Class = _db_histogram` IS 락의 `Nsubgranules` 3/5/6→0.
- **이유**: 이 S 락들은 FOR UPDATE 가 잡은 락이 아니라 **컴파일 시 히스토그램 읽기가 남긴 락**이었습니다(위 설명). `348e93909` 이후 컴파일이 `_db_histogram` 행을 잠그지 않으므로 덤프에서 사라지고, 히스토그램 클래스 IS 락은 남되 하위 그래뉼(인스턴스 락)이 0 이 됩니다. 케이스가 검증하는 대상(대상 테이블 t1~t4 의 IX/X, 루트 클래스 IX 등)은 한 줄도 바뀌지 않았습니다.
- **부수 확인**: 케이스 스크립트 `run_test_point` 가 기다리는 기대 락 수(6/4/11/6/8/9)가 새 답안의 값과 정확히 일치합니다. 이 숫자는 #7476 이전 것이라, 그동안은 각 테스트 포인트마다 60초 폴링을 다 소진한 뒤 히스토그램 락이 섞인 표를 덤프하고 있었습니다. 이제 첫 폴링에서 맞아 케이스 의도대로 돕니다.

### 2. `shell/_06_issues/_17_1h/cbrd_20145_1/cases/histogram.answer`

케이스 의도: `;.hist` 클라이언트 요청 히스토그램의 항목 구성을 확인(값은 스크립트가 전부 0 으로 마스킹).

- **추가된 것**: `update` / `select` / `delete` 세 문장의 표에 `BTREE_FIND_MULTI_UNIQUES` 행 1줄씩.
- **이유**: 새 읽기 경로가 `btree_find_unique`(요청 `BTREE_FIND_UNIQUE`, 락 고정) 대신 op_type 을 실어 보낼 수 있는 `btree_find_multi_uniques(S_SELECT)`(요청 `BTREE_FIND_MULTI_UNIQUES`)로 `_db_histogram` 을 조회하기 때문입니다. 통계·히스토그램을 가져오는 세 문장에만 나타나고, `create table` 과 첫 `insert` 에는 통계 fetch 가 없어 나타나지 않습니다. 기존 `BTREE_FIND_UNIQUE` 행은 다른 유니크 조회가 남아 그대로 있습니다. 값은 마스킹되므로 행의 존재만 달라집니다.

### 검증
답안은 PR 헤드 `f79eda483`(debug, 11.5.0.2565)로 재생성하고 케이스마다 2회 실행해 통과를 확인했습니다(커밋 `38bac27fb`). 같은 엔진 커밋에 대한 CTP sql(debug, `tc/pr-7900`)은 17459/17459 통과, 코어 0 이었습니다.
