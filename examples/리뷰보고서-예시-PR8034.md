## 판정

**머지 차단 없음.** valid 9 / blocking 0 (자동 2건 오탐 제외 시 7). 변경 자체는 정확하고, 팩과 소스를 대조해 확인한 범위에서 새 결함은 없다.
지적 7건은 전부 non-blocking 또는 확인 질문이며, 성격이 "이 PR 이 깨뜨렸다" 가 아니라 **"이 PR 이 만든 새 계약의 가장자리"** 다.

### 이 변경이 무엇인가

트랜잭션 전역 `LOG_TDES.wait_msecs` 를 몇 호출 동안 저장·복원하던 엔진 코드 7곳을,
스레드 소유 `THREAD_ENTRY.wait_msecs_override`(센티널 `LK_WAIT_NOT_OVERRIDDEN = -3`)로 옮긴다.
읽는 쪽은 `logtb_find_current_wait_msecs ()` / `pgbuf_find_current_wait_msecs ()` 가 **override 를 먼저** 보고,
없으면 TDES 로 내려간다. CBRD-27198 이 넣었던 `force_latch_wait` bool 을 이 int override 로 일반화한다.

영역 판정: **[F] 트랜잭션 · [G] 스토리지 · [I] 횡단**에 걸치고, 13.2 기준 **공유 자원(TDES)을 스레드 격리로 내리는** 변경이다.
불변조건 5개는 흔들지 않는다 — INV-3(3-way 빌드)만 확인이 필요했고, `wait_msecs_override` 필드와 두 접근자 모두 모드 가드 없이
세 바이너리에서 같은 의미를 갖는 것을 확인했다(`pgbuf_force_latch_wait ()` 가 잃은 SA 분기는 SA 에 경합이 없어 무해).

### 확인했고 문제 없던 것 (지적하지 않음)

| 확인 항목 | 결과 |
|---|---|
| override 저장/복원 짝 7곳 전부 | 누수 경로 없음. `log_rollback ()` 의 `log_zip_alloc` 실패 조기 return 은 직전 `logpb_fatal_error (…, true, …)` 가 `exit`/`abort` 로 끝나 도달하지 않는다 |
| 중첩 (`disk_is_page_sector_reserved` → `disk_get_volheader_internal`) | LIFO 로 올바르게 복원된다 |
| 복원 함수 짝 | 7곳 모두 `logtb_set_thread_wait_msecs ()` 로 되돌린다 — TDES setter 와 섞어 `-3` 을 TDES 에 쓰는 자리는 없다 |
| `pgbuf_timed_sleep ()` 진입 assert | override 가 `-3` 으로 도달할 수 없다(조회 함수가 `-3` 을 반환하지 않음) |
| 스레드 재사용 | `entry::entry ()` 초기화 + `retire_context ()` 복귀로 태스크 간 누수 없음 |

## 지적 7건

### 1. 🟡 [설계] 27183 "해결" 주장이 실제 범위보다 넓다 — 계약 층은 남는다
`src/storage/page_buffer.c:7368`

`pgbuf_timed_sleep ()` 의 `er_set_return` 마지막 else 는 `old_wait_msecs` 가 `LK_ZERO_WAIT` 여도 `er_set` 없이 `ER_FAILED` 를 돌려준다.
오염 원인이 막혀도 **사용자가 `lock_timeout=0` 을 건 세션**은 정상적인 래치 타임아웃에서 `er_errid () == NO_ERROR` 인 NULL fix 를 받는다.
CBRD-27355 가 코어로 확정한 바로 그 분기이고, 그 6줄 계약 수정(닫힌 PR#7843 `3c58abb63`)은 이 PR 에 없다.

제안: (a) 계약 커밋을 가져오거나, (b) 본문 Remarks 를 "오염 원인은 막히지만 `lock_timeout=0` 세션의 무오류 실패는 남습니다" 로 좁히고
27355 를 Relates 로 연결한다. **권고는 (b) + 27355 별건** — 계약 변경은 `ASSERT_ERROR_AND_SET` 호출자 전수가 회귀 범위다.

### 2. 🟡 [코드] TDES 에 남기기로 한 값이 override 에 가려진다
`src/transaction/lock_manager.c:6340`

`lock_object ()` 가 override 를 먼저 읽게 되면서, 여전히 TDES 에만 쓰는 `lock_object_wait_msecs ()`(6795~6807)의 **인자가 사문**이 된다.
`lock_initialize_composite_lock ()`(9132)은 override 를 스냅샷으로 떠서 창이 닫힌 뒤 쓴다.
현재 도달 경로는 찾지 못했다(호출자 셋 다 override 창 밖). 즉 **잠재 결함**이고, 안전이 코드가 아니라 관찰에 얹혀 있다.

제안: `lock_object_wait_msecs ()` 를 `logtb_set_thread_wait_msecs ()` 로 옮긴다(그 자체가 PR 이 없애려는 패턴이다).
TDES 에 남기기로 한 자리(`btree_load.c` 락 승격, lock dump)에는 `assert (… == LK_WAIT_NOT_OVERRIDDEN)` 한 줄.

### 3. 🟡 [설계] "워커에 상속하지 않는다" 불변식이 강제되지 않는다
`src/transaction/log_tran_table.c:2621`

설계가 "override 를 세운 채 워커를 띄우는 코드가 없다" 는 전역 관찰 위에 서 있다. 깨뜨리는 변경은 한 줄이면 되고,
깨지면 증상은 이 PR 이 고친 버그와 같다. 같은 부류가 두 달 동안 넷(26571·27308·27198·27183/27486) 따로 발견된 것이 근거다.

제안: `entry_manager` 의 claim 경로에 `assert (context.wait_msecs_override == LK_WAIT_NOT_OVERRIDDEN);`.
`retire_context ()` 의 복귀와 짝이 맞고 release 비용 0 이다.

### 4. 🟢 [설계·확인 질문] 교착 탐지기·lockdb 는 override 를 못 본다
`src/transaction/lock_manager.c:5249`

탐지기 3곳이 `LK_CAN_TIMEOUT (logtb_find_wait_msecs (…))` 로 TDES 만 읽는다. 본문의 "탐지기가 읽어야 하므로 TDES 에 남긴다" 는
전제가 lock_manager 7곳 전환으로 부분적으로 깨졌다. **현재는 무해함을 확인했다** — override 를 가장 오래 드는 `log_rollback ()` 은
두 호출자가 직전에 `TRAN_UNACTIVE_ABORTED` 로 바꾸고 victim 선정이 비활성 트랜잭션을 건너뛴다.

질문: `log_rollback ()` 의 undo 구간에서 트랜잭션 락을 새로 요청하는 복구 함수가 있습니까? 없으면 그 사실을 Remarks 에 한 줄로.

### 5. 🟢 [설계] `pgbuf_force_latch_wait ()` 가 올릴 것이 없을 때도 override 를 설치한다
`src/storage/page_buffer.c:5325`

유효값이 유한이거나 이미 무한이면 그 값을 그대로 스레드에 복사한다. 기능은 같지만 2번의 마스킹 창을 공짜로 넓히고,
이름과 실제 동작("지금 값을 스레드에 고정")이 어긋난다. 제안은 no-wait 가 아니면 설치하지 않고 현재 override 를 그대로 반환하는 것.

### 6. 🟢 [코드] 우선순위 규칙이 두 함수에 복제됐고 TODO 가 스테일하다
`src/storage/page_buffer.c:16885`

`pgbuf_find_current_wait_msecs ()` 와 새 `logtb_find_current_wait_msecs ()` 가 같은 규칙(override 먼저, 없으면 TDES)을 따로 구현한다.
release 반환값은 모든 입력에서 같지만 `tdes == NULL` 의 debug 동작이 다르고(조용히 0 vs `assert`), 바로 위 `TODO: … but not log_impl.h` 는
이 PR 이 log_impl.h 에 같은 함수를 넣은 뒤라 사실과 어긋난다. 제안: pgbuf 쪽을 위임 한 줄로 줄이고 TODO 삭제.

### 7. 🟢 [주석] 필드 주석 "set only through logtb_set_thread_wait_msecs ()" 가 같은 PR 안에서 두 번 어긋난다
