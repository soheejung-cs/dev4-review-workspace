**리뷰 일시:** 2026-09-16 (정소희 세션, Claude) -- 정적 리뷰. 빌드·실행 검증은 아래 "돌릴 것" 확인 후.

> **TL;DR** (Non-blocking): 병합·재분배는 sysop 1개 + 리프 WRITE 래치라는 기존 규약 안에 있고 로깅도 기존 핸들러만 써서 복구 경로에 새 위험이 없다. 남는 것은 (1) 한 키의 체인을 끝까지 컴팩션하는 동안 그 리프의 DML 이 멈추는 시간이 체인 길이에 비례한다는 점, (2) 스캔 재개를 OID 앵커로 바꾼 것이 관리 명령을 위해 일반 읽기 경로의 불변조건을 하나 더 도입했다는 점 -- 둘 다 머지를 막을 사안은 아니고 문서화·후속 판단 사항이다.

## Summary

- **변경 요약**: 비유니크 인덱스의 OID 정렬 오버플로 체인을 리프 래치 아래 sysop 단위로 병합·재분배하는 `ALTER INDEX ... COMPACT` 추가 + 키 중간 스캔 재개를 페이지 기준에서 OID 앵커 기준으로 변경.
- **주요 이슈**: 리프 WRITE 래치 점유가 키 단위(체인 전체)라 긴 체인에서 DML 정지 시간이 선형 증가 (`btree_ovf_compact_chain` 루프에 리프 양보 지점 없음).
- **확인 필요 사항**: TC PR 두 개가 비어 있는 draft -- 스캔 중단 vs 컴팩션 레이스 재현이 TC 로 들어오는지. HA standby 에서 이 문이 재생될 때의 동작.

## Findings

### [설계 리뷰]

영역 판정: **[G] 스토리지(btree 오버플로 체인) + [E] 실행(범위 스캔 재개)**, 조율은 클라이언트 `do_alter_index_compact()`, 자원 연산은 서버 `xbtree_compact_overflow()` -- 클라이언트 컴파일/서버 자원 분리(사전설계 1.2)에 맞다. 흔드는 불변조건 없음(WAL·MVCC 규칙 그대로, 새 복구 핸들러 없음).

1. **불변조건 완화가 두 곳에 같은 문장으로 적혀 있다** (`btree.c:12356` 주석, `btree_load.h:289`) -- "separator 는 생성 시 고정"이 "COMPACT 만 (왼쪽 최대 OID, 이 페이지 최소 OID] 안에서 올릴 수 있다"로 바뀌었다. 라우팅 불변조건(정렬 유지·모든 객체 라우팅 가능)은 `btree_ovf_dir_set_separator()` 의 assert 3개(`:727-729`)가 지킨다. 채택할 만한 완화다.
2. **스캔 재개 재설계가 진짜 설계 변경이다.** 컴팩션은 "가시 객체가 있는 페이지는 반납되지 않는다"는 스캔의 전제를 깨므로 재개를 OID 앵커로 바꾼 것은 불가피하고, 24094 의 전역 OID 정렬 위에서 정확하다. 대신 일반 읽기 경로가 두 가지 사실에 **새로 의존**한다: (a) 체인이 전역 OID 정렬이다, (b) 한 OID 는 스냅샷당 가시 버전이 최대 1개다(`btree.c:29674-29680` 주석). (b) 는 MVCC 의 성질이라 안전하고, (a) 는 유니크 인덱스 legacy 체인을 `BTREE_IS_UNIQUE` 로 갈라 놓았다. 대안 "컴팩션이 리프 래치 대신 스캔과 같은 자원을 잡아 스캔 중에는 병합하지 않기"는 스캔이 반복 사이에 래치를 다 놓기 때문에 잡을 자원이 없다 -- 앵커 방식이 맞다.
3. **락·래치 수준**: 클래스 SCH_S(트랜잭션 끝까지) + 키별 리프 WRITE + 데이터 페이지 2개 WRITE + 디렉터리 페이지 WRITE. DML(IX) 은 클래스 수준에서 안 막히고, 같은 리프의 DML 만 래치로 막힌다. 오토커밋 OFF 면 SCH_S 가 커밋까지 남아 그 사이 `DROP/ALTER INDEX` 가 대기한다 -- 다른 읽기 DDL 과 같은 성질이므로 문제는 아니지만 매뉴얼에 한 줄 필요.
4. **vacuum 시 자동 병합 보류**는 동의한다 -- vacuum(C 등급 백그라운드)에 쓰기를 더하면 포그라운드 간섭 시나리오가 새로 생긴다.

### [코드 리뷰]

#### Non-blocking (should consider)

1. `src/storage/btree.c:1051-1074` (`btree_ovf_compact_chain`) -- **리프 WRITE 래치가 한 키의 체인 전체에 걸쳐 유지된다.** 루프는 병합/재분배마다 sysop 을 커밋하지만 리프는 `xbtree_compact_overflow()` 가 체인이 끝난 뒤(`:1557`)에만 놓는다. PR 실측(800 -> 600 페이지, 약 200 병합에 0.07 s)으로 환산하면 병합 1회 약 0.3 ms 이므로 1만 페이지짜리 단일 키 체인이면 그 리프의 INSERT/DELETE 가 약 1.5 s 멈춘다. 재개 위치가 이미 OID 앵커로 정확하므로 N 병합마다 리프를 놓고 `btree_compact_fix_leaf()` 로 돌아오는 것이 어렵지 않다. 지금 수치로는 수용 가능 -- 문서에 "체인 길이에 비례해 해당 키 DML 이 대기"를 적거나 양보 주기를 넣는 것 중 하나.
2. `src/storage/btree.c:956-961` -- 주석 "Legacy chain (nothing we know how to compact)" 은 24094 의 규약과 어긋난다. 비유니크 체인에 legacy 헤더는 **손상**이고(`btree_ovf_dir_check`, `:13520`), 같은 PR 의 스캔 경로도 그렇게 취급한다(`btree_ovf_scan_locate_resume`, `assert_release (false)`). 여기서는 조용히 `NO_ERROR` 를 돌려 checkdb 가 잡을 손상을 컴팩션이 감춘다. `dir_hdr == NULL` 을 assert_release 로, `VPID_ISNULL (dir_vpid)` 만 단일 페이지 체인으로 나누기를 권한다.
3. `src/query/execute_schema.c:4562` -- 결과(`keys_compacted`, `pages_freed`)가 `er_log_debug` 에만 남아 사용자는 효과를 `SHOW INDEX CAPACITY` 를 다시 쳐야 안다. 관리 명령이므로 서버 로그 INFO 급 한 줄이나 csql 메시지가 있으면 운영에서 "돌아갔는지" 확인이 쉬워진다.

#### Questions for the author

1. TC PR 두 개(`cubrid-testcases#3460`, `cubrid-testcases-private-ex#4106`)가 파일 0개 draft 다. PR 본문의 검증 중 **스캔 중단 vs 컴팩션 1,212회 레이스**와 **컴팩션 중 kill -9 복구**는 shell TC 로 들어와야 한다고 본다 -- 계획이 있는지.
2. HA 구성에서 이 문이 standby 에 DDL 로 재생되는지(재생된다면 standby 쪽 인덱스도 독립적으로 컴팩션되므로 오히려 맞는 동작이고, 재생되지 않으면 standby 체인은 그대로 남는다). 어느 쪽인지 확인했는지.
3. `ER_INTERRUPTED` 로 빠져나오면 문은 실패하지만 이미 커밋된 sysop 의 병합은 남는다(설계상 맞다). 사용자 관점에서 "실패했는데 일부 페이지가 줄었다"가 되는데, 매뉴얼에 "중단 시 그때까지의 컴팩션은 유지된다"를 적을 것인지.

확인한 것(지적 없음): sysop 안 fix/unfix 짝·에러 경로 unfix(`btree_ovf_compact_pull` `:886` 은 dealloc 전 unfix, delete 경로와 동일), UPDATE_ALL 로깅의 undo/redo 이미지(`:830`, `:858`), RPC 응답 패턴(`sbtree_class_test_unique` 와 동일), `unsigned_integer` BIGINT 절단 처리(`csql_grammar.y`), 서버측 fill_factor 재검사, 파티션 순회 후 `free_and_init`. 핫패스 추가 비용은 `btree_select_visible_object_for_range_scan()` 의 OID 복사 1회(`:29709`) -- 측정 대상 아님.
