- [코드 리뷰] [성능 검토] 🟡 `src/optimizer/plan_generation.c:1754` — 인덱스가 채택하지 않은 값싼 파생 필터를 데이터 필터로 남기는 판정이 추정 선택도(> 0.5 이면 드랍)에만 의존한다 — 통계가 없는 테이블(TC 규모, UPDATE STATISTICS 미실행)에서는 OR-of-equality 의 선택도가 기본 상수라 파생 필터가 항상 남고, 플랜이 바뀌지 않는 질의에서는 스캔 행마다 순수 추가 평가 비용만 낸다.

- [코드 리뷰] [테스트 제안] 🟡 `src/optimizer/rewriter/query_rewrite_term.c:4855` — WHERE 레벨(location 0) 팩터의 각 분기에 null-padded 쪽 테이블의 `IS NULL` 만 있는 외부 조인 형태는 파생 `(s.c IS NULL or …)` 이 그 테이블의 sarg 로 붙는데, 이 항이 조인 전에 평가되면 결과가 달라진다 — 코드는 안전하지만 PR 의 스모크 목록(pr-body:33)에 외부 조인 케이스가 없다.
  - 왜 문제인가: `t LEFT JOIN s … WHERE (s.c IS NULL AND t.x=1) OR (s.c IS NULL AND t.x=2)` 에서 원본은 null-padded 행을 받아들이는데(IS NULL 이 TRUE), 파생 항을 s 스캔에서 먼저 평가하면 c 가 NOT NULL 인 s 행이 조인 전에 사라져 t 행이 새로 padded 되며 결과 집합이 바뀐다. 이 PR 의 가드는 `location != 0` 팩터만 건너뛰므로(4855) 이 형태는 추출 대상이다. 안전한 이유는 이 PR 이 아니라 기존 분류기에 있다 — WHERE 레벨 SARG 가 LEFT_OUTER 노드에 붙으면 `QO_TC_AFTER_JOIN` 으로 재분류돼 조인 뒤에 평가된다.
  - 제안: TC 시나리오 추가: (1) `CREATE TABLE t(x INT); CREATE TABLE s(tid INT, c INT); INSERT t 1..4; INSERT s (1,NULL),(2,7);` (2) `SELECT t.x, s.c FROM t LEFT OUTER JOIN s ON t.x = s.tid WHERE (s.c IS NULL AND t.x = 1) OR (s.c IS NULL AND t.x = 2) OR (s.c IS NULL AND t.x = 3);` 기대: x=1 (c NULL), x=3 (padded) — x=2 는 c=7 이라 제외. (3) 같은 질의를 `s` 에 인덱스 `ON s(c)` 를 만든 뒤 반복해 파생 항이 키 범위로 채택되는 경로도 덮는다. 플랜 덤프에 파생 항이 `after join` 절에 있는지 확인.
  - 검증: [static] query_graph.c(b319ce1) 6495~6515: `QO_TERM_CLASS == QO_TC_SARG` 이고 ON 조건 항이 아닌데 노드의 `PT_JOIN_TYPE` 이 LEFT_OUTER/FULL_OUTER 이면 `QO_TC_AFTER_JOIN` 으로 재분류한다. 파생 항은 location 0 · 단일 노드 SARG 이므로 원본 WHERE sarg 와 같은 경로를 탄다 — 결과 보존. 실행 확인은 하지 않았다(TC 제안으로 게시).
