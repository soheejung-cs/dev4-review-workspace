# PR #7724 리뷰 보고서 — [CBRD-27138] 조인이 너무 넓어 최적화를 포기했음을 알린다

PR: https://github.com/CUBRID/cubrid/pull/7724 · HEAD `f41f50080` · JIRA CBRD-27138 · **이미 머지됨**
리뷰: 2026-09-22, 하네스 `0bb73c9`, 검증 빌드 develop `87b25579e` (release, .50)
결론: **막을 것 없음.** 유효 지적 4건 모두 non-blocking — 🟡 2, 🟢 1, 자동 MEAS 1(해당 없음).

## 변경의 요지

`qo_discover_partitions ()` 가 파티션 노드 수 27(64비트) 초과에서 `QO_ABORT` 로 최적화를
통째로 포기하는 동작은 그대로 두고, 그 사실을 두 곳에 남긴다. 하나는 에러 로그의
notification(`ER_QO_SET_SIZE_EXCEEDED`, -470), 다른 하나는 플랜 덤프의
`Query plan: (not generated -- cost-based optimization was skipped for this query)` 한 줄이다.
한계 자체는 바뀌지 않는다.

## 확인한 것

세 가지를 실제로 돌려 확인했다.

* **알림이 클라이언트 에러 상태를 남기지 않는다** — PR 본문의 주장대로다. `er_set` 은
  notification severity 일 때 마지막에 `crt_error.clear_error ()` 를 호출한다. 28테이블 질의는
  에러 없이 완료되고 결과도 27테이블과 같다.
* **-470 은 정의만 있고 쓰이지 않던 코드가 맞고, 메시지도 상황에 들어맞는다.** en_US·ko_KR
  모두 인자 없는 형식이라 `er_set (..., 0)` 과 짝이 맞는다.
* **새 덤프 문구의 파급이 좁다.** `where 1=0` 이나 `select 1` 같은 흔한 형태는 종전과 같고,
  `SET OPTIMIZATION LEVEL 512` 는 문법 오류로 거부된다. 다만 노드 64개 초과는 새로 이 문구를
  찍는다(아래 2번).

## 지적

### 1. 🟡 [코드] 포기한 테이블 수와 한계값이 릴리스에서 어디에도 남지 않는다

`src/optimizer/query_graph.c:8008`

이 변경의 목적은 27→28 경계에서 최적화가 사라졌다는 사실의 발견 가능성인데, 릴리스 기본
설정에서 사용자가 실제로 얻는 것은 `Query involves too many items for optimizer.` 한 줄뿐이다.
몇 개가 한계를 넘었는지도, 한계가 27 인지도 알 수 없어 "테이블을 하나 줄이면 최적화가
돌아온다"는 조치로 이어지지 않는다.

숫자를 담은 상세 줄은 `er_log_debug` 로 나가는데, 이 매크로는
`if (prm_get_bool_value (PRM_ID_ER_LOG_DEBUG))` 로 전개되고(`error_manager.h:311`) 그 파라미터
기본값은 NDEBUG 빌드에서 false 이며 `PRM_HIDDEN` 이라 문서에도 없다
(`system_parameter.c:1070-1074`).

검증(dynamic): 릴리스 `87b25579e` 에서 28테이블 체인 조인 2회 → `csql.err` 에 `CODE = -470` 2건,
`cost-based optimization skipped: a join partition has` 0건.

제안 — 숫자를 사용자가 보는 경로에 올린다. 가장 싼 방법은 초과 노드 수와 한계를 `env` 에
남기고 덤프 문구에 붙이는 것이다. 또는 -470 을 쓰는 곳이 여기 하나뿐이므로 메시지 형식을
인자 2개로 바꿔 `er_set (..., ER_QO_SET_SIZE_EXCEEDED, 2, nodes, limit)` 로 넘긴다
(로케일 msg 4개 + CCI 헤더 갱신이 따라온다).

### 2. 🟢 [코드] 새 덤프 문구가 덮는 범위가 주석의 열거보다 넓다

`src/parser/xasl_generation.c:18355`

주석은 이 경로를 "파티션 초과·할당 실패·내부 assertion 실패" 셋으로 설명하는데,
`qo_validate` 의 `OPTIMIZATION_LIMIT` 64 초과도 같은 줄을 찍는다. 이 경우 -470 알림이 없어서,
나중에 이 문구를 보고 에러 로그를 뒤지는 사람이 "로그에 아무것도 없으니 다른 원인"으로
잘못 좁히게 된다.

검증(dynamic): 65노드 체인 등가조인 → 덤프에 `(not generated ...)` 출력, 같은 시각 `-470` 없음.
질의 자체는 정상 수행됐다.

제안 — 주석 열거에 노드 수 상한을 추가하고, 에러 로그에 항목이 남는 경우는 첫 번째뿐임을
한 구절로 덧붙인다.

### 3. 🟡 [코드] 이 동작을 고정하는 회귀 TC 가 없다

`src/optimizer/query_graph.c:8007`

산출물이 "로그 한 줄 + 덤프 한 줄"이라 기능 회귀 테스트가 건드리지 않는다. 지금 상태로는
이 관측성이 다음 리팩터링에서 없어져도 CTP 가 잡지 못한다.

→ **이번에 만들어 검증했다.** CTP sql 케이스(`cases/cbrd_27138.sql` + `answers/cbrd_27138.answer`)를
`87b25579e` 에서 생성해 연속 2회 `Success:1` 을 확인했고 CBRD-27138 에 첨부했다. 통제군인
3테이블 조인은 플랜 본문이, 28테이블은 `(not generated ...)` 가 답안에 박힌다. `--@queryplan`
지시자는 질의 바로 앞 줄마다 필요하고 `/*+ recompile */` 이 없으면 플랜 캐시에 걸려 빈 플랜이
나온다는 것도 확인했다.

### 4. (자동) MEAS-04 — 이 PR 에는 해당 없음

하네스가 PR 본문의 표를 성능 측정표로 보고 반복 횟수를 요구했지만, 그 표는 27/28테이블의
덤프·로그 유무를 적은 정성 표다. 시간 수치가 없으므로 이 지적은 적용하지 않는다.
