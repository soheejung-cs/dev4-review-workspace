## 4. TC `cbrd_27369.sh` 검토

### 4-1. 답지가 없는 것이 맞나 — 맞다

shell 계열은 판정 방식이 두 갈래다.

| 방식 | 스크립트 수 |
|---|---|
| `write_ok`/`write_nok` 자체 판정 | 2,287 |
| `.answer` 파일과 diff | 100 |

`cases` 디렉터리 374개 중 `.answer` 보유는 102개(27%)다. 같은 디렉터리
`_06_issues/_26_2h` 의 형제 11개는 **전부** 자체 판정이고 `.answer` 가 없다.
이 TC 는 `write_ok` 6회로 자체 판정하므로 형식이 맞다. 답지를 만들 자리가 아니다.

카탈로그를 직접 조회해 판정하는 선택도 적절하다. B 의 메시지("Statistics updated
successfully")는 편승했을 때도 출력되므로 답지 비교로는 결함을 잡을 수 없다.
`_db_class.checked_time` 과 `_db_histogram.null_frequency` 로 본 것이 맞는 판단이다.

### 4-2. 스테이블한가 — 실행 근거로는 그렇다

**PR head `1b4781493` 를 빌드해 그 설치본으로** 3회 반복. CTP 헬퍼는 최소 스텁으로 대체.
(앞서 캐시 `8dbaf15f5` 로도 3회 돌려 같은 결과를 얻었다 — 10·11·10초, 12/12 OK.)

| 회차 | 결과 | 소요 |
|---|---|---|
| 1 | 12/12 OK | 9초 |
| 2 | 12/12 OK | 9초 |
| 3 | 12/12 OK | 9초 |

시각 문자열을 뺀 판정 줄이 세 회차 모두 완전히 같았다. case1 의 `checked_time` 은 매회
4초 진행해 1초 해상도에 4배 여유가 있다.

의심했다가 **아닌 것으로 확인**한 것 두 가지.

- **csql 출력 버퍼링**: 성공 메시지는 `fprintf(stdout,...)`이고 `csql_Output_fp`(=stdout)의
  flush 는 입력 루프에서 다음 줄을 읽은 뒤에 일어난다(`csql.c:875`). 그래서 fifo 로
  한 줄만 보내면 마커가 안 보일 수 있다고 봤으나, 별도 실험에서 **0.5초 안에 보였다**
  (53바이트 파일에 마커만 있는 상태 확인).
- **`Blocked_mode = *X_LOCK` 패턴**: 메시지 형식이 `Blocked_mode = %10s`(우측 정렬)이라
  실제 출력은 `=` 뒤에 공백 5개다. BRE `= *X_LOCK` 이 이를 매칭한다. `SIX_LOCK` 은
  매칭되지 않으므로 X 대기만 잡는다.

남는 위험 세 가지(모두 오검출이 아니라 **거짓 NOK** 방향이다).

1. 차단 판정이 "아무 X_LOCK 대기"다. B 를 특정하지도, 자원(`_db_class`)을 특정하지도
   않는다. 지금은 세션이 A·B 둘뿐이라 실害가 없지만, 케이스를 늘리면 앞 케이스의 잔류
   대기를 B 의 것으로 볼 수 있다.
2. 폴링 예산은 60초이고 실측 소요는 전체 10초다. 여유는 충분하나 shell_heavy 와 같은
   포화 상태에서 같이 돌면 `a_wait_for`·`b_start_and_wait_blocked` 가 먼저 만료된다.
3. `do_cleanup` 의 `rm -f csql.err *.log` 가 CWD 의 모든 `.log` 를 지운다. CTP 가 케이스
   디렉터리에 로그를 두면 함께 지워진다.

`hist_rows` 가 2를 기대하는 것은 현재 엔진이 컬럼 2개(`a INT`, `b VARCHAR`) 모두에
히스토그램을 만드는 데 의존한다. 실험에서 "1 table, 2 columns" 로 확인했다. 기본 수집
대상 정책이 바뀌면 이 상수가 깨진다.

### 4-3. 목적과 형식에 맞게 테스트하나 — 절반이다

**잘 하는 것.** 리뷰에서 나온 두 결함(롤백한 홀더의 chn 을 증거로 오인, 클래스 통계
신선도를 히스토그램 신선도로 오인)을 케이스 1·3·4가 정확히 고정한다. 진입 순서(A 가
쓰고 B 가 기다리고 A 가 끝남)를 `lockdb` 로 확인한 뒤 홀더를 풀어 **경합을 우연에
맡기지 않는다**. 판정을 B 의 메시지가 아니라 카탈로그로 한다. 이 셋은 잘 설계됐다.

**빠진 것 네 가지.**

1. **편승 자체를 검증하지 않는다.** 케이스 2는 최종 카탈로그가 최신인지만 본다. 그건
   A 의 커밋만으로도 성립하므로, 편승이 완전히 망가져 B 가 항상 직접 수집해도 통과한다.
   PR 의 핵심 주장(동시 N 건의 전수 스캔이 1회로)을 고정하는 케이스가 없다.
2. **직렬화와 데드락 부재를 검증하지 않는다.** JIRA 의 원 증상은 오토커밋 ON 다중 세션의
   붕괴인데, 이 TC 는 오토커밋 OFF 2세션만 다룬다. 원 증상 회귀는 shell_heavy
   `cbrd_21362` 에 전적으로 의존한다.
3. **게이트가 SELECT·DML 을 막지 않는다는 성질**을 검증하지 않는다. PR Remarks 의 주장이고
   수동 실측만 있다. 케이스 하나로 고정할 수 있다.
4. **`ON ALL CLASSES` 경로**가 없다. X-first 가 적용되는 유일한 경로인데 비어 있다.

**형식 지적 두 가지.**

- `DESCRIPTION` 블록에 PR 리비전 해시(`f79eda483`, `8dbaf15f5`)와 리뷰 회차 서사가 있다.
  브랜치가 rebase·force-push 되면 가리키는 대상이 사라지고, 지금 head 는 `1b4781493` 이라
  이미 어긋났다. TC 헤더는 무엇을 왜 고정하는지 적는 자리다.
- `Expected results: Before the fix ... case 1 fails` 는 CTP 관점의 기대 결과가 아니다.
  CTP 기대는 항상 전부 OK 다. 이 문장은 "수정 전 빌드로 돌리면 NOK 가 정상"으로 읽혀
  QA 가 판정 기준을 오해할 수 있다. 회귀 확인 절차라면 따로 표기해야 한다.

## 5. 오토커밋 OFF 에서의 게이트 거동 (head 실측)

회귀 테스트 `cbrd_21362` 가 오토커밋 OFF 라는 사용자 지적에 따라 head 빌드로 직접 측정했다.
65,000행 · 해시 파티션 10 · 조건부 복합 인덱스 테이블. 상세 초안은
`JIRA코멘트초안-오토커밋OFF-락거동.txt`.

홀더가 `UPDATE STATISTICS ON t` 을 미커밋으로 들고 있는 동안 다른 세션:

| 문장 | 소요 |
|---|---|
| `SELECT COUNT(*) FROM t` | 0.03초 |
| `INSERT INTO t` 1행 | 0.02초 |
| `SHOW INDEXES FROM t` | 0.02초 |
| `SELECT /*+ RECOMPILE */` 컴파일 | 0.03초 |
| 다른 테이블 `UPDATE STATISTICS ON t2` | 0.02초 |
| 같은 테이블 `UPDATE STATISTICS ON t` | 대기 (30초에 클라이언트에서 끊음) |

홀더 종료 방식별 대기자 소요:

| 홀더 종료 | 대기자 소요 |
|---|---|
| COMMIT | 0.00초 (편승) |
| ROLLBACK | 0.14초 (직접 수집) |
| (비교) 단독 수집 | 0.16초 |

세 가지가 확인됐다.

1. **게이트는 조회·DML·컴파일을 막지 않는다** — PR Remarks 의 주장이 head 의 실제
   `_db_class` 행 게이트에서도 성립한다. `8dbaf15f5` 의 합성 OID 로는 검증할 수 없던 성질이다.
2. **대기의 단위가 문장이 아니라 트랜잭션이다.** `lock_timeout` 기본값이 -1(무제한)이라
   서버 쪽 대기는 끊기지 않는다. `cbrd_21362` 의 워커는 JDBC `queryTimeout=10` 이므로
   홀더 트랜잭션이 10초를 넘기면 클라이언트에서 끊긴다.
3. **롤백한 홀더 뒤의 대기자는 편승하지 못한다.** `cbrd_21362` 는 커밋과 롤백이 반반이라
   대기자 절반가량이 직접 전수 스캔을 한다. 오토커밋 ON 대비 스캔 횟수가 늘어난다.

게이트 간 데드락은 성립하지 않는다 — 대상 테이블이 하나이므로 역순 획득이 없다.

## 6. 빌드 환경에서 새로 겪은 것

- **develop 머지가 3rdparty 를 openssl 3.x 로 올렸고(#7905), 이 호스트에는 Perl
  `IPC::Cmd` 가 없어 openssl configure 가 죽는다.** sudo 없이 순수 Perl 모듈 6개를
  `~/dev/utils/perl5` 에 받아 `PERL5LIB` 로 넘겨 해결했다. 항구적으로는
  `perl-IPC-Cmd` 설치가 맞다(sudo 필요).
- **빌드트리에 openssl 1.1.1w 헤더가 남아 있어** 새 소스와 섞여
  `OPENSSL_API_COMPAT expresses an impossible API compatibility level` 로 깨졌다.
  `3rdparty/{Build,Source,Stamp,Download}/libopenssl` 과 `3rdparty/include/openssl`,
  `lib/libssl.a`, `lib/libcrypto.a` 만 지우고 다시 빌드하면 된다(전체 클린 불필요).
- **`goto` 의 캐시 히트 판정이 설치 디렉터리 존재 여부다.** 빌드가 실패해 `databases/`·
  `tmp/` 만 있는 껍데기가 남으면, 다음 `goto <같은rev>` 가 "cache hit" 으로 판정하고
  `~/CUBRID` 를 **바이너리 없는 디렉터리로 바꿔 버린다**. 실패한 빌드의 캐시는 지워야 한다.
- **`goto` 로 리비전을 옮기면 서브모듈 포인터가 매번 dirty 해진다.** 다음 `goto` 는 그걸
  이유로 거부하므로, 빌드 직전에 `git submodule update --init --recursive` 와
  `git submodule foreach --recursive 'git reset --hard'` 를 한 번 돌려야 한다.
