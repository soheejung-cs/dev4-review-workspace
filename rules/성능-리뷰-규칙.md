합성: Claude(정소희 세션) 2026-09-16 · 근거: `references/C-Cpp-성능규칙집.md`(§0·§10~§20·§18·§19, ID 보존), `claude-workspace/memory/rules/측정-규칙.md`·`howto/벤치마크-실행.md`·`rules/JOB옵티마이저-규칙.md`·`rules/테스트TC-규칙.md`. 영문 장별판: `imports/xmilex-git/skills/cpp-perf-rules/`(xmilex-git). **§1~§9(MEAS·MEM·COH·ALIAS·BR·ALLOC·FP·GLOB·PAR) 본문 요약과 외부 배경(Lakos·HFT·서버사이드) 요약은 미완 — 그 축은 아래 §18 체크리스트 항목이 대신하며, 깊이가 필요하면 원문 장을 편다.**

## 0. 사용 규약 (규칙집 L10~23)
- [사용규약1, L12] 측정 데이터 없는 최적화 제안은 금지 — 병목 근거가 없으면 '측정 먼저'라고 답한다. 코드를 읽고 '느릴 것 같다'는 판단은 근거가 아니다(MEAS-01).
- [사용규약2, L13] 규칙 적용 전에 핫패스/콜드패스를 먼저 구분한다. 콜드패스(에러 처리·초기화·종료)에는 이 규칙집을 적용하지 않고 가독성을 우선한다. 아래 rules 의 hot_only=true 항목은 콜드패스에서 지적하지 않는다.
- [사용규약3, L14] 규칙 충돌 시 우선순위: 정확성 > 메모리 안전성 > 가독성 > 성능. 성능을 위해 UB 를 도입하는 제안은 금지.
- [사용규약4, L15] 지적·제안에는 정량 근거를 붙인다 — '빠르다'가 아니라 '캐시 미스 N회 감소', '분기 M개 제거' 형태.
- [사용규약5, L16] 규칙집의 수치 임계값(64B, 사이클 표 등)은 기준선이다. 아키텍처·워크로드에 따라 다르므로 실측으로 조정한다고 명시한다.
- [사용규약6, L17~18] C 코드(.c)에는 C 규칙만 적용한다. 모던 C++ 관용구(shared_ptr, RAII, 템플릿)를 제안하지 않는다 — CUBRID 는 .c 가 C++17 로 컴파일돼도 C 스타일을 유지한다. C 에서는 ALIAS/CLOW 절이 CPP 절을 대체한다.
- [사용규약7, L19~20] 이식성 없는 기법(computed goto, __builtin_*, __attribute__ 등 GCC/Clang 확장)을 제안할 때는 폴백 경로를 함께 제시한다.
- [사용규약8, L21~22] 원자적 연산 관련 제안·지적에는 항상 COH-10(약한 메모리 모델)을 함께 언급한다 — x86 에서 도는 락프리 코드가 ARM64 에서 깨지는 것은 흔하다.
- [L26] 성능 경로 코드를 리뷰할 때는 18장 체크리스트를 먼저 훑고, '이 저장소에서 반복 적발된 축'(cubrid_case 가 붙은 rules)을 우선 확인한다.
- [19장, L2266] 성능 문제는 PRIO-01→PRIO-09 순서로 검토하고, 위 단계에서 해결되면 아래 단계로 내려가지 않는다. 단계 3(메모리 접근 패턴)이 가장 중요하다(L2315).
- [18장, L2147] '필수' 절(MEAS-01/04/05/06/07, CHK-06)은 모든 성능 관련 변경에 적용한다. 나머지 절은 변경이 건드리는 축만 연다. '물리 설계' 절(PHYS-*)은 리팩터링·모듈 분리 리뷰에서만 연다(L2184).
- [0장, L46] 비용 판정은 절대값이 아니라 자릿수 비교로 한다.
- **규칙은 ID 로 인용한다** (`MEM-03 위반`). 번역하기 어려운 용어는 원문 그대로.

## 1. 리뷰 순서
1. **핫패스인가** — 행/페이지/튜플 루프, 스캔·조인·집계 내부, 락·래치 획득 경로, 병렬 워커 루프면 핫패스. 에러 처리·초기화·종료·DDL 은 콜드패스 → 이 문서를 적용하지 않는다(가독성 우선).
2. **§18 체크리스트(아래 2절 의무 항목)를 먼저 훑는다.** 성능 주장이 있으면 §6 의 측정 규칙으로 근거를 판정한다.
3. 해당 축의 표(3절)를 diff 옆에 두고 ID 로 지적한다. 다수 지적이면 §19 우선순위(5절)로 순서를 정한다.
4. 리팩터링·모듈 분리·헤더 정리면 PHYS(4절) — 핫패스와 부딪히면 성능 장 우선(PHYS-05).
5. 새로 확인한 사실은 `record` 스킬대로 남긴다.

- 측정 근거 없는 성능 주장에는 '측정 먼저'로 답한다 — 수치가 있어도 호스트 게이트·run 반복(n≥3)·순서 반전·계약 조건 명시 넷 중 하나가 빠지면 근거로 세지 않는다.
- 결정적 증거(플랜 덤프·조인 순서·`Statistics updated successfully` 카운트)와 확률적 증거(벽시계)를 나눠 검증한다 — 전자는 호스트 상태와 무관하게 유효하고(MEAS-R-26), 후자에만 MEAS-R-01~14 가 전부 걸린다.
- 정확성 > 성능 — 플랜 변화 판정은 결과값 동일 확인이 먼저고 그다음 fetch/시간이다(MEAS-R-37).
- 판정은 산출물로 한다 — 스크립트 종료코드, '완료' 보고, `buckets: 300` 표시 하나로 판정하지 않는다(MEAS-R-18·19).
- 요구 순서는 메커니즘 지표(perf c2c/stat) → 플랜 대조 → 벽시계 A/B 다 — 벽시계가 가장 비싸고 가장 시끄럽다(MEAS-R-07).
- 재현을 요청하기 전에 벤치·하네스가 어느 컨테이너에 있는지 확인한다(MEAS-R-24·25) — TPC-H 는 .50 만, JOB 하네스 판정 로직은 컨테이너마다 갈릴 수 있다.
- 규칙은 ID(MEAS-R-nn)로 인용한다 — 성능규칙집 1장의 MEAS-nn(측정 원칙)과 별개 문서다.

## 7. 리뷰에서 벤치를 고르는 법 (JOB vs TPC-H vs CTP)
| PR 이 바꾸는 것 | 먼저 돌릴 것 | 어디서 | 이유 |
|---|---|---|---|
| 조인 순서·조인 선택도·히스토그램·비용 상수 (옵티마이저) | **JOB 113** (PG 조인 순서 일치가 지표) → 플랜 변화 질의만 median-of-N 확정 | .51/.52 (JOB 원본 .51) | JOB 은 조인 순서 문제의 표준 벤치, PG 레퍼런스가 있다 |
| 스캔·집계·정렬·해시조인 실행기, 병렬 실행, 임시파일 | **TPC-H SF10 22** (q1·q6 풀스캔, q15 집계) | .50 (TPC-H 보유) | 대용량 스캔·집계 비중이 높다 |
| 통계 수집·카탈로그·락·MVCC·복구 | **CTP sql/medium/shell 코어 여부** + 동시성 시나리오 스크립트(재현 스크립트) | 어느 컨테이너나 | 벤치가 아니라 정확성 문제. 벤치는 히스토그램 표준 재생성 후 회귀 유무만 |
| 파서·타입·함수 | CTP sql (답안 정렬은 CI 몫, 로컬은 코어만) | — | 성능 축 아님 |
