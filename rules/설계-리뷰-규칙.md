# 설계 리뷰 규칙 — 설계를 볼 때 여는 한 문서

합성: Claude(정소희 세션) 2026-09-16 · 근거: `references/cubrid-사전설계문서.md`(1·3·4·7·8·13장) + `skills/design-review`. 원문 요약 워크플로가 세션 한도로 중단돼 **1차 판본**이다 — 표의 "원문" 열로 깊이를 확인한다. 번역 어려운 용어는 원문 그대로.

## 0. 사용 규약 — 설계 리뷰가 필요한 신호
하나라도 해당하면 코드 리뷰와 별개로 이 문서를 연다: 모듈 경계를 넘는 변경(다른 계층 헤더 새 include, 반대 방향 호출) · 클라이언트/서버 경계(`SERVER_MODE`·`CS_MODE`·`SA_MODE` 가드) · 공유 자료구조에 필드·락·원자 연산 추가, 격리→공유 전환 · 새 컴포넌트·데몬·스레드풀 · WAL·MVCC·Vacuum·latch 프로토콜 근처 · 리뷰 중 "여기가 맞는 자리인가"가 떠오름.
판정 문장은 **"이 변경은 [X] 영역이고 ~를 흔든다/흔들지 않는다"** 로 시작한다.

## 1. 영역 판정 4단계 (코드를 보기 전에)
| 단계 | 질문 | 판정 재료 | 원문 |
|---|---|---|---|
| ① 컴포넌트 | 어느 계층의 책임인가 | 아래 [A]~[I] 표. 한 기능이 여러 계층에 걸치면 계층마다 따로 검토 | 3장 |
| ② 불변조건 | 5개 중 하나를 흔드나 | 아래 2절. 흔들면 "고칠 문제"가 아니라 설계 재검토 | 1장 |
| ③ 임계도 | Tier-0/1/2 어느 경로인가. Tier-2 작업의 부작용이 Tier-0/1 을 오염하나 | 5절 | 7장 |
| ④ 공유·격리 | 공유 자원이면 등급(S/A/B/C)과 3요소 계약(불변식·허용 동시성·완화 기법)이 적혀 있나 | 4절 | 13.2 |

### 컴포넌트 [A]~[I]
| 영역 | 디렉터리 | 책임 | 리뷰 초점 |
|---|---|---|---|
| [A] 접속·중계 | `src/broker/` (broker, CAS) | 포트 리스닝·세션 배분, CAS 는 **프로세스**(크래시 격리) | 연결 churn, 왕복 지연(Tier-1) |
| [B] SQL 컴파일 | `src/parser` `src/optimizer` `src/xasl` — **클라이언트측** | 파싱·플래닝·XASL 생성·직렬화 | 서버에서 재현하려는 시도는 헛수고(불변조건 1.2). 플랜 캐시 적중률 |
| [C] 객체·스키마 | `src/object` `src/compat` | 스키마·권한·카탈로그 객체, DB_VALUE | **중앙 허브**(4장 사이클 4) — 헤더 변경 파급 |
| [D] 통신 | `src/connection` `src/communication` | CSS 프로토콜·요청 디스패치(상수표+핸들러 3파일 계약) | 새 요청 추가 시 3파일 동시 변경 |
| [E] 서버 실행 | `src/query` `src/thread` `src/session` | XASL 실행·스캔·집계·병렬(px) | 행당 함수 호출 수(Tier-0), 리스트파일 스필 |
| [F] 트랜잭션 | `src/transaction` | MVCC·WAL·락·복구·Vacuum | WAL append 직렬화점(S등급), 락 테이블·스냅샷(A등급) |
| [G] 스토리지 | `src/storage` | 버퍼풀·힙·B+tree·카탈로그 파일·통계 | latch 순서, fix/unfix 짝, 페이지 포맷 호환 |
| [H] 확장 실행기 | `src/sp` `src/method` `pl_engine/` | SP/Java/PL 호출 경계 | 별도 프로세스·연결 보유(락 잔존) |
| [I] 횡단·운영 | `src/base` `monitor` `executables` `loaddb` | 에러 모델·메모리·유틸리티 | 전 모듈 관통 규약(에러코드, free_and_init) |

## 2. 불변조건 5개 — 흔드는 변경의 형태와 지적 문구
| ID | 불변조건 | 흔드는 변경(예) | 지적 문구 |
|---|---|---|---|
| INV-1 | **3-Tier**: 드라이버 ↔ 브로커/CAS ↔ cub_server. CAS 는 프로세스 | 드라이버가 서버에 직결, CAS 를 스레드로 | "브로커 경로가 필수 경로라는 1.1 을 우회한다" |
| INV-2 | **클라이언트 사이드 컴파일**: 파서·옵티마이저는 CS/SA 에서 돌고 서버에는 XASL 만 간다 | 서버가 SQL 텍스트를 받아 플래닝, 통계 수집 순서를 서버로 이동 | "1.2 를 흔든다 — 조율은 클라이언트에 남기고 서버에는 자원만" (CBRD-27369 게이트가 이 원칙으로 설계됨) |
| INV-3 | **One Source, Three Binaries**: 같은 소스가 SERVER/CS/SA 로 세 번 컴파일 | 한 모드에서만 정의되는 함수를 공용 헤더에 노출, 가드 없는 서버 전용 코드 | "가드 누락 — SA 빌드에서 어떻게 되나" |
| INV-4 | **MVCC + 전용 Vacuum(로그 구동)**: 버전은 행 in-place + `prev_version_lsa`, 회수는 로그 구동 데몬 | 스냅샷 없이 힙을 읽는 경로 추가(NULL snapshot = 가시성 검사 생략), Vacuum 을 힙스캔으로 | "가시성 규칙을 명시하라 — snapshot fn 이 무엇인가" |
| INV-5 | **ARIES WAL**: 페이지 수정과 로그 append 의 원자 순서, undo+redo 통합 | 로그 없이 페이지 수정, 관문(log_append) 밖 쓰기 | "WAL 규칙 위반 — 복구 시 재현 불가" |
동결 권장(8장): 위 5개 + DB_VALUE, OID/VPID/VFID 체계, 온디스크 볼륨·로그 구조, 카탈로그 클래스 체계 — 바꾸면 다른 DB 가 된다.

## 3. 책임 경계·의존 방향 (4장)
- 허용 의존은 **아래 방향**: 전 모듈 → [I]base, [C]compat(DB_VALUE). 위 방향 새 의존(base 가 query 를 include)은 거부.
- 공식 사이클 4개만 인정: ① storage ↔ transaction ② query ↔ storage(콜백 역호출) ③ parser ↔ optimizer ④ object 중앙 허브. **새 양방향 사이클을 만드는 변경은 설계 재검토**.
- "이 함수가 왜 여기 있나": 계층 책임 표와 어긋나면 옮길 자리를 제안한다(예: 통계 갱신 조율은 [B] 클라이언트, 자원(락)은 [F] 서버).
- 어휘: 깊은 모듈·seam·adapter(`imports/xmilex-git/skills/codebase-design`, xmilex-git) — 인터페이스가 구현만큼 복잡하면 얕은 모듈.

## 4. 동시성 도메인 (13장)
| 등급 | 자원 | 리뷰 요구 |
|---|---|---|
| **S** 직렬화 지점 | WAL append | 임계구역을 넓히는 변경은 근거 필수 |
| **A** 고경합 핫 | 핫 페이지 latch, 락 테이블 버킷, LRU victim, MVCC 활성 테이블(스냅샷), temp 할당자, serial | 단일 스레드 재현으로 "없다" 판정 금지 — 동시성 재현 필수 |
| **B** read-mostly | XASL 캐시, filter pred 캐시, **카탈로그/통계**, 클래스 표현 캐시, 세션 테이블, ACL | 쓰기 폭주가 들어오면(예: 히스토그램 기본 수집) RW 분리·버전 스왑으로 푼다 — 읽기가 쓰기를 기다리게 두지 않는다 |
| **C** 백그라운드 | vacuum, flush/checkpoint, 데드락 감지기, px 워커풀 | 포그라운드 우선 백오프 |
- **P2**: 공유 자원 항목마다 **불변식 + 허용 동시성 + 완화 기법** 3요소 계약을 적는다. 없으면 리뷰에서 요구한다.
- **P3**: 관문(pgbuf_fix/unfix · lock_object · log_append · 메모리 quota · 워커풀 제출) 밖에서 공유 상태를 만지는 코드는 거부.
- **P4**: px 워커는 트랜잭션 문맥(스냅샷·락)을 코디네이터와 공유, THREAD_ENTRY·프라이빗 힙은 각자.
- 13.5 간섭 시나리오 카탈로그와 대조한다 — 새 공유 자원은 어느 시나리오를 새로 만들 수 있나.

## 5. 성능 임계도 (7장) — 설계 우선순위
Tier-0(사이클 단위): 버퍼풀 fix/unfix·latch, btree 탐색/삽입, 힙/슬롯, WAL append, 락 테이블·스냅샷, 실행기 내부 루프. Tier-1: CAS 배정, XASL 직렬화 왕복, 플랜캐시, temp 스필, 병렬 스케일, vacuum 지연. Tier-2: 파싱·플래닝 1회 비용, 유틸리티, SP.
규칙: **Tier-2 작업(통계 수집·loaddb·DDL)이 Tier-0/1 자원을 커밋까지 쥐는지** 본다 — 관리 작업이 서비스 경로를 막으면 격리가 목표다(속도가 아니라).

## 6. 타 DBMS 대조 (6장) — 발명인가 이식인가
같은 문제를 PG/Oracle/InnoDB 가 어떻게 푸는지 한 줄씩 적는다. 표준 동작의 이식이면 근거가 되고, 아키텍처가 달라 옮길 수 없는 것(서버 플래닝 vs 클라이언트 컴파일, 힙 MVCC 방식, DDL 트랜잭션 여부)은 그 사실을 적는다. PG 참조 규약은 `skills/pg-reference-review`(작성 예정), 소스 대응은 `dev4-ai-source/reference-dbms/`.

## 7. 산출물 형식
1. 영역 판정 문장(1절) 2. 아이디어마다 비유 한 줄 + 계약 3요소 3. **대안표**(대안 | 장점 | 왜 택하지 않았나, 채택안·사용자 제안 대안 포함) 4. 락/자원 수준 전·후 표 5. 남은 위험(수용/결정) 6. **결정 요청 Q1~Qn**(닫힌 질문, 선택지별 비용). 덱은 `examples/설계리뷰-덱-CBRD-27369.html`. 아티팩트는 사용자 명시 허용 시만.

## 9. B-tree 동시성 판정표 (BTL)

근거: Graefe, *A Survey of B-Tree Locking Techniques*, ACM TODS 35(3), 2010 (DOI 10.1145/1806907.1806908, **유료**).
해설·절 지도는 `references/B트리락킹-Graefe서베이.md` — **표가 diff 에 안 맞을 때만** 연다.
`BTL-03 위반` 형태로 인용한다.

| ID | 판정 문장 | 근거 | 축 / 불변조건 |
|---|---|---|---|
| BTL-01 | 새 동기화 객체·보호 구간이 **트랜잭션 간 DB 내용 보호(lock)** 인지 **스레드 간 인메모리 구조 보호(latch)** 인지 PR·설계문서에 적혀 있지 않으면 지적한다. | 서베이 §3·§7(Fig.2) — 두 층을 가르지 않으면 이후 판정이 전부 무근거가 된다 | §4 전제 / INV-4·INV-5 |
| BTL-02 | 이름이 latch 인데 **트랜잭션 종료까지 보유**하거나 **데드락 탐지에 의존**하면 분류가 깨진 것으로 지적한다. | §3.1 판별 5축(보호 대상·모드 수·데드락 처리·보유 기간·관리 위치). latch 는 탐지가 아니라 규율로 회피한다 | §4 S/A 등급 |
| BTL-03 | **형제(좌↔우) 포인터를 따라가는 래치 커플링을 무조건 대기로 획득**하면 지적한다 — 반대 방향 스캔과 공존하는 순간 탐지되지 않는 데드락이다. 조건부 획득 실패 시 **잡은 리프를 놓고 루트부터 재탐색**하는 경로를 요구한다. | §4.1 이슈③ + §4.2 — 이웃 추적은 부모→자식과 **다른 문제로 분류**된다 | Tier-0 (PR#7899 판정 근거) |
| BTL-04 | 분할·병합이 leaf→root 로 래치를 잡아 올라가는데 **획득 순서 규약(latch leveling)이 문서화돼 있지 않으면** 지적한다. | §4.1 이슈④·§4.2 — 선택지가 정해져 있다(전면 배타 / 업그레이드 / 예약 / B-link 2단계) | §4 P3 |
| BTL-05 | **I/O 대기 구간에 래치를 보유**하는 경로가 있으면 지적한다 — 재진입 시 **LSN 으로 조상 페이지 무변경을 검증**하고 탐색을 재개하는 계약을 요구한다. | §4.1 이슈①② · §4.2 | 버퍼풀 fix/unfix, Tier-0 |
| BTL-06 | 노드 제거·부하 균형·재조직처럼 **논리적 내용을 바꾸지 않는(contents-neutral) 연산**을 사용자 트랜잭션 안에서 트랜잭션 락으로 처리하면, 시스템 트랜잭션·비동기로 분리 가능한지 답하도록 요구한다. | §4.4 | **INV-4** / §4 C등급 |
| BTL-07 | 범위 질의의 팬텀 방지를 주장하면서 **경계 키(next/prior)와 이웃 간격(gap)** 의 처리를 밝히지 않으면 지적한다. ghost 키를 락 대상에서 빼거나, 보유자가 있을 수 있는 시점에 ghost 를 물리 제거하면 지적한다. | §5.1~§5.3(키+갭 계층 락), §5.2 | **INV-4** / §4 A등급 |
