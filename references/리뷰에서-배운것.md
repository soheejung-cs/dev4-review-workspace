# 리뷰에서 배운 것

리뷰 코멘트(사람·봇)에 답하면서 **확정한 사실과 다시 밟지 않을 함정**을 누적한다.
답글을 게시할 때마다 한 항목씩 append 한다(규약: `skills/review-response/SKILL.md` §7).

- 항목은 **최신이 위로**. 형식: `## <날짜> PR#<n> (<JIRA>) — <한 줄 교훈>`
- 각 항목에 ① 리뷰어가 지적한 것 ② **검증 방법과 결과**(어느 파일·함수를 읽었나, 무엇을 돌렸나)
  ③ 고친 것 ④ **일반화한 규칙**(다음에 어디서 같은 실수를 하나) 을 적는다.
- 코드 사실은 여기서 끝내지 않고 `dev4-ai-source` 해당 모듈로도 보낸다(중복이 아니라 역할 분담 —
  여기는 "리뷰가 나를 어떻게 고쳤나", 거기는 "이 코드가 어떻게 동작하나").
- 리뷰어 지적이 **틀렸던** 경우도 적는다. 무엇을 근거로 반박했는지가 다음 반박의 재료가 된다.

## 2026-09-29 TC PR#4244 (CBRD-27484, 리뷰어 측) — CTP shell TC 의 함수 지역 변수는 전역이다; 판정은 `.result` 파일로 확인한다

**지적** (내가 낸 것, `cbrd_27484.sh` `check_results()`): `result_file="$2"` 가 CTP `init.sh` 의 전역 `result_file`(`$case_name.result`) 을 덮어써 케이스 2~7 의 `write_ok/write_nok` 가 TC 의 임시 로그로 가고 `do_cleanup` 이 지운다.
**검증**: 수정 전 빌드에서 TC 실행 → stdout 은 NOK 4건, `.result` 는 `1 : OK` 한 줄. 변수명만 바꾼 사본은 NOK 4건 기록, 수정 후 빌드에선 7 OK. `init.sh:840` `result_file=`, `write_ok` 가 `${cur_path}/$result_file` 에 쓰는 것 확인.
**고친 것**: 🔴 코멘트 게시(suggestion `res_file`). 다른 두 지적(케이스 7 플랜 미확인 🟡 / assert grep 대상 🟢)은 사용자 결정으로 미게시.
**일반화**
- **shell TC 리뷰는 stdout 이 아니라 `.result` 파일을 본다.** stdout 의 NOK 는 CTP 판정과 무관하다. 리뷰 때 TC 를 수정 전 빌드로 한 번 돌려 `.result` 에 NOK 가 실제로 남는지 확인하는 것이 최소 검증이다(이번엔 11초).
- **POSIX sh 함수의 변수는 전역이다.** `init.sh` 전역(`result_file`, `case_no`, `cur_path`, `case_name`, `begin_time`…)과 이름이 겹치면 조용히 깨진다 — TC 변수는 접두어를 붙인다.
- 정리 루틴(`rm -f *.log`)이 TC 의 증거 파일을 지우면 실패 원인 추적이 불가능하다 — 결과 파일과 임시 파일의 이름 공간을 분리한다.

## 2026-09-22 PR#8006 (CBRD-27143, 자기 리뷰) — "가격 불가" 경계는 호스트변수 캐스트 시점까지 따라가 동적으로 확정한다

**지적** (자기 리뷰 F3, `histogram_cl.cpp` `bind_fp_walk()` LIKE 분기): NULL·비문자열 패턴 바인딩 경계에 TC 가 없다.

**검증**: TC `[3-1]` 을 추가해 CI 와 같은 `conf/sql.conf` 설정의 CTP 로 돌렸다. NULL 은 예측대로(재플랜 없음, 0행).
정수 123 은 예측과 달리 **재플랜됐다** — SQL PREPARE 경로는 `do_reexecute…`/`do_recompile_and_execute_prepared_statement()`
가 `do_cast_host_variables_to_expected_domain()` 을 지문 계산 **앞**에 두므로, 지문·플래너가 보는 값은 이미 컬럼 문자열 도메인의

**고친 것**: TC 주석을 실측대로 정정(NULL: 가격 불가 / 정수: 캐스트 뒤 보통 패턴으로 가격). 코드 변경 없음(동작이 맞다).

**일반화**
- **"이 값 타입은 가격 매길 수 없다" 는 판정은 값이 그 함수에 도달하는 경로의 캐스트를 먼저 본다.** 호스트변수는 `expected_domain`

- 자기 리뷰의 "테스트 제안" 은 정적 예측을 답으로 박지 말고 **실행 결과를 기대로 삼는다** — 예측이 틀린 절반이 TC 의 진짜 가치였다.
- 자기 리뷰 지적 3건은 모두 🟢 였고 blocking 이 없었다. 팩이 ctags 폴백으로 비어 있어(`codegraph_complete=false`) 판정 근거가
  세션 기억이었다 — .52 에 tree-sitter `langs.so` 를 만들기 전까지 자기 리뷰의 독립성은 낮다고 봐야 한다.

## 2026-09-18 PR#7977 (CBRD-27251) — DB_VALUE 를 만드는 `db_make_*` 는 버퍼를 빌린다, 복사하지 않는다

**지적** (greptile-apps, `histogram_cl.cpp`): 재패딩한 값의 수명을 설명한 주석이
"`db_make_varchar () below copies it out before that`" 라고 적었는데, 그 함수는 복사하지 않으므로
소유권 계약을 반대로 설명한다는 것.

**검증**: `db_make_varchar()`(`src/compat/dbtype_function.i`) → `db_make_db_char()` 로 내려가고,
거기서 `value->data.ch.medium.buf = str` 로 **호출자의 포인터를 그대로 넣고** `value->need_clear = false`
로 둔다. 복사 없음. 지적이 맞았다.

**고친 것**: 주석을 실제 안전 조건으로 다시 썼다 — 안전한 이유는 복사가 아니라 **소비 시점**이다.
`db_string_like()` 가 같은 호출 안에서 값을 다 쓰고 반환하고, `pad_buf` 를 다시 채우는 것은
호출자의 다음 반복이다. 같은 파일의 `rlike_match_string()` 은 `std::string (value)` 로 진짜 복사하므로
기존 주석("copy by length")을 유지했다 — **두 경로가 다르다는 것을 확인하고 각각 다르게 적었다.**

**일반화**
- **수명·소유권을 주석에 쓸 때는 그 API 가 복사하는지 빌리는지 정의를 열어 확인한다.** 이름(`make`, `set`,
  `assign`)으로 추측하지 않는다. CUBRID 의 `db_make_*` 계열은 대체로 **빌린다**(`need_clear=false`);
  복사를 원하면 호출자가 `std::string`·`db_private_alloc` 으로 따로 떠야 한다.
- 지역 버퍼(`std::string pad_buf`)를 루프 밖에 두고 재사용하는 패턴은 성능상 맞지만, 그 버퍼를 가리키는
  `string_view`·`DB_VALUE` 가 **다음 반복 전에** 소비되는지를 주석에 남긴다. "복사된다" 로 뭉개면
  다음 사람이 그 view 를 밖으로 들고 나간다.
- 틀린 주석은 틀린 코드보다 오래 산다. 리뷰에서 주석 지적이 오면 **코드를 다시 읽어 사실을 확정한 뒤**
  고친다(이 건은 봇 제안 문구를 그대로 받지 않고, 확인한 사실에 맞춰 다시 썼다).

## 2026-09-21 PR#7899 (CBRD-27401, 리뷰어 측) — "통계를 갱신하라" 는 CUBRID 의 DDL 정책부터 확인한다

**지적**: 내가 `xbtree_compact_overflow()` 끝에서 카탈로그 `BTREE_STATS.pages/leafs` 를 `pages_freed` 만큼 감산하자고

전까지 통계를 갱신하지 않지요" 한 줄로 반박·resolve 했다.

**검증**: `catalog_copy_btree_statistic()`(system_catalog.c) 은 새 표현을 쓸 때 **BTID 가 같은 것만** 이전 값을 복사한다.
REBUILD 는 drop+create 라 새 BTID → `leafs/pages` 가 0(읽을 때 `MAX(1,…)`)으로 시작. `sm_add_constraint()` 가 부르는
`sm_update_statistics_without_gathering_stats()` 는 이름과 달리 **카탈로그를 다시 읽기만** 한다(`stats_get_statistics`).
매뉴얼 `ko/sql/tuning.rst` "통계 정보 갱신": DDL·DML 로 자동 갱신되지 않고 UPDATE STATISTICS 가 유일한 방법. **작성자가 맞았다.**

**고친 것**: 감산 제안 철회, COMPACT 매뉴얼 절에 "다른 DDL 과 같이 통계는 자동 갱신되지 않음" 한 구절만 요청.

**일반화**
- 통계·카탈로그 갱신을 제안하기 전에 ① `tuning.rst` 의 정책 문장 ② `catalog_copy_btree_statistic()` 의 BTID 매칭
  ③ 비교 대상 명령(REBUILD)이 실제로 무엇을 하는지 — 셋을 먼저 본다. "정확하고 싸다" 는 정책 예외의 근거가 못 된다.
- 반박이 한 줄이어도 근거를 열어 확인하고, 맞으면 **무엇을 열어 확인했는지 적으며 철회**한다. 그 확인이 다음 리뷰의 재료다.

- **③ 고친 것**: 측정을 `qexec_batch_scan_chain ()` 안으로 옮겨 `qexec_batch_trace_begin/end ()` 로 배치 구간만 자른다(루프 진입 begin → 행 경로 직전 end → 행 경로 끝 begin → 루프 나올 때 end). 체인 안 오류 반환 둘은 `chunk = S_ERROR; break` 로 루프 뒤 end 하나를 모두 지나게.
- **④ 일반화**: **새 실행 경로가 기존 경로를 안에서 부르면 기존 경로의 계측이 그대로 따라온다** — 바깥 계측은 "안쪽이 세지 않는 구간" 만 세고, 구간을 자르는 코드는 조기 반환마다 닫혀야 하므로 출구를 하나로 만든다. 이중 집계는 "스캔 줄 > 문장 합계" 한 줄로 드러난다.

### 7. SA/CS 재현에서 REC_BIGONE 을 만들려면 `enable_string_compression=no` (A9 · G9b 재현)
- **① 지적**(내가 발견): G9b 재현 `repro4.sql` 이 `UPDATE t SET pad = REPEAT('z', 18000)` 으로 REC_BIGONE 행을 만든다고 가정했는데, 수정 후 서버에서 `batch pages: 194 (row path: 0)` — 행 경로 페이지가 **하나도 없었다**. 어제 SA 로 돌린 G9b 4개 시도도 전부 행 경로 없이 돈 것.
- **② 검증**: CUBRID 는 255B 를 넘는 문자열을 LZ4 로 압축해 저장(`enable_string_compression` 기본 yes)하므로 REPEAT 값은 몇십 바이트의 REC_HOME 에 머문다. conf 에 `enable_string_compression=no` 를 넣자 두 빌드 모두 `batch pages: 190 (row path: 4, last: … relocated, overflow …)` — `heap_page_collect_visible ()` 의 `rec.type != REC_HOME → S_DOESNT_FIT`.
- **③ 고친 것**: `run_install.sh` 가 conf 에 넣고 원복, 재현 SQL 머리에 `;get enable_string_compression` 과 전제 주석. 이 상태의 수치로 T48 답글을 씀.
- **④ 일반화**: **SA/CS 재현에서 REC_BIGONE(오버플로)·REC_RELOCATION 을 만들려면 `enable_string_compression=no`** — 반복 문자열은 압축돼 홈 레코드에 남는다. 재현이 "그 레코드 타입을 전제" 하면 `;plan detail` + `;trace on` 의 `row path: N` 같은 **경로 도달 증거를 먼저 읽고** 수치를 믿는다(도달 0 인 재현은 통과가 아니라 무효).

### 8. 워커가 공유하는 카운터는 태스크 로컬에 두고 반납 때 한 번 합친다 (A14 · T52)
- **① 지적**: `hjoin_rtf_pass ()` 가 행마다 `rtf->rows`·`rtf->dropped` 에 `__atomic_add_fetch`, 두 카운터는 같은 행에서 읽는 slots/used/mask 와 56B 구조체 안이라 같은 64B 라인 — on_trace 와 무관하게 항상.
- **② 검증**: 정적 분석뿐이었으나 같은 함수의 다른 스레드(T64)에 `perf c2c` 실측(HITM 82~94%, 병렬 1.45~1.89배 느림)이 있어 "측정 먼저" 대신 모양 결정으로 답했다. 수정 후 서버 모드 `parallel(4)`(`parallel_scan_page_threshold=16`, trace `(parallel workers: 4)`)에서 배치 리프·행 경로 모양 모두 `rows: 40000, dropped: 39978` 로 직렬과 같은 수, COUNT 22. 시간·c2c 는 측정 묶음으로.
- **③ 고친 것**(`a2578d999`): 카운터를 필터 구조체에서 빼 `XASL_NODE.rtf_rows/rtf_dropped` plain 으로 — 직렬은 리더 노드, 워커는 자기 클론 노드, 배치 리프는 청크 합을 체인 호출부가. `hjoin_rtf_pass ()` 는 `bool (const rtf*, const DB_VALUE*)` 순수 조회. 합치는 자리는 `hjoin_rtf_unbind_clone (clone, orig)` 하나(태스크당 `__atomic_add_fetch` 1회), `hjoin_rtf_release ()` 는 `wait_for_workers ()` 뒤라 plain 읽기.
- **④ 일반화**: **워커가 같은 워드에 더하는 카운터는 태스크(클론 노드) 로컬에 plain 으로 두고 반납(unbind) 때 한 번 합친다**(PAR-01). 라인 분리만 하는 최소안은 RMW 경쟁이 남으니 택하지 않는다. 측정 요청을 쓰기 전에 **같은 PR 의 다른 스레드에 이미 측정이 있는지** 본다 — 있으면 "측정 먼저" 가 아니라 "측정이 있으니 모양을 정하자".

### 9. 새 allocator 를 짜기 전 `memory_alloc.h` 의 fixed/ostk/private 힙부터 (T10 · xmilex-git)
- **① 지적**: 서버 코드에 맨 malloc/free 51/45곳.
- **② 검증**: `git diff -U0` 추가 줄만 세어 52/47(그중 3 은 develop 이동). `db_create_fixed_heap`(fixed_alloc.c + heaplayers: `LockedHeap<SpinLock, FreelistHeap<ZoneHeap<MallocHeap>>>`)과 `db_create_ostk_heap`(SizeHeap·ObstackHeap, `db_ostk_free` 는 컴파일 아웃)을 코드로 열어 내 슬랩·아레나와 대조 — 슬랩은 기능 동일(free list 링크가 첫 워드를 덮는 규약·16 정렬까지), 아레나는 되감기 없음·8 정렬·OOM 크래시 세 가지 차이.
- **③ 고친 것**(`f109c02fe`, 10 파일 +310/−393): 슬랩 → fixed heap(OOM er_set 은 래퍼에서), 범프 아레나 둘 → ostk(파티션마다 destroy/재생성, 64B 는 63B 더 받아 맞춤), 나머지 → `db_private_*`(실패 er_set 은 `hl_lea_alloc` 이 하므로 호출자 중복 제거, 런타임 필터만 "없으면 필터 없이" 라 에러 지움). 차이는 주석·답글에 기록. 남긴 raw 는 develop 이동분과 clone pool 로 스레드를 건너는 expr_compile 산출물.
- **④ 일반화**: **엔진에 새 allocator 를 짜기 전에 `memory_alloc.h` 의 세 힙(fixed/ostk/private)부터 연다** — "고정 크기 + free list" 는 fixed, "범프 + 통째 해제" 는 ostk, 나머지는 private. 새로 짜도 되는 것은 그 셋이 못 하는 것뿐(64B 정렬·되감기)이고 그때도 먼저 그 차이를 적는다. 봇·사람이 "맨 malloc" 을 세면 내 쪽도 `git diff -U0` 로 같은 기준으로 세어 수를 맞춘 뒤 답한다.

### 10. px 코드의 `db_private` 는 "누가 free 하나" 를 함수가 아니라 스레드로 적는다 (T10)
- **① 지적**(같은 스레드의 전제): `db_private_*` 로 바꾸려면 alloc/free 가 같은 스레드여야 한다.
- **② 검증**: `db_private_free_release → hl_lea_free (thread_p->private_heap_id, ptr)` = `mspace_free`, 힙은 thread_entry.cpp:198 에서 스레드마다. px 경로를 자리마다: 워커는 자기 clone 의 스캔을 `thread_ref` 로 열고 닫고(px_scan_task.cpp 480-534·634·655), 리더 소유물(rtf·reader·px)은 워커가 읽기만 하고 리더가 drain 뒤 놓는다 — 스레드를 건너는 포인터 없음(조사표 `alloc_survey.md`).
- **③ 고친 것**: `thread_p` 없던 free 함수 4개(`expr_batch_plan_free`·`hjoin_rtf_release`·`qexec_batch_gby_create`·`qexec_batch_gby_map_destroy`)에 추가. 단위 suite 두 개의 hooks.cpp 에 TU 의 `db_private_*_release` 를 malloc/free 위에 **강한 정의**로 둠(unitseam 자동 stub 이 죽이므로).
- **④ 일반화**: **px 가 있는 코드에서 사설 힙을 쓰려면 "누가 free 하나" 를 함수가 아니라 스레드로 적는다** — alloc 자리마다 "어느 스레드의 heap_id 로 alloc, 어느 스레드가 free" 한 줄. clone 의 산출물(expr_compile 프로그램처럼 pool 로 다른 스레드에 가는 것)은 raw 로 남기고 이유를 주석에. 단위 suite 는 `db_private_*` 를 malloc/free 위의 강한 정의로 바꿔 끼운다.

### 11. 새 실행 경로는 기존 행 경로의 행별 검사를 전부 가졌는지 대조한다 — 빠진 것은 리프로, 못 넣으면 거절 (A7 · 새 인라인)
- **① 지적**(내가 발견): 페이지 배치의 project 체인이 해시 조인 런타임 필터를 보지 않았다 — `qexec_batch_eligible ()` 이 `xasl->rtf` 를 가르지 않고 `emit_row ()`·`qexec_batch_emit_row ()` 에 `hjoin_rtf_pass ()` 가 없어, probe 의 바깥 힙 스캔이 배치를 타면 필터가 무효. 결과(COUNT 22)는 같고 `RUNTIME FILTER (… rows: 0, dropped: 0)` 로만 보여 **오류 없이 효과만 사라지는** 모양.
- **② 검증**: 서버 모드 `;plan detail` + `;trace on` — 배치 모양 `o.v > 0` 은 `rows: 0, dropped: 0`, 행 경로 모양 `MOD(o.v, 5) > 0` 은 `rows: 40000, dropped: 39978`. `parallelism` 이 켜진 서버는 두 입력을 px 부질의로 동시에 돌려 `!xasl->px_executor` 에서 필터를 아예 만들지 않으므로 재현에 `NO_PARALLEL_SUBQUERY` 가 필요했다(설계 확인 사항으로 남김).
- **③ 고친 것**: 필터를 배치 필터의 리프(`EB_KID_RTF`)로 — `scan_batch_open ()` 이 블록을 받고 `eb_build_rtf_leaf ()` 가 AND 사슬 마지막에 항 하나를 더해 `eb_rtf_kid ()` 가 선택 행마다 `hjoin_rtf_contains ()` 조회(NULL·미존재 키 탈락 기준은 `hjoin_rtf_pass ()` 와 같게, 앞 항이 UNKNOWN 인 행은 조회 안 함). `expr_batch.c` 는 불투명 포인터 + 콜백(`EXPR_BATCH_RTF_CONTAINS`)만 받아 해시 조인 타입을 모르고, 키 컬럼을 배치가 못 놓거나 같은 비교가 안 되는 타입이면 플랜 거절 → 행 경로. 직렬 체인의 폴백 행 경로에도 `hjoin_rtf_pass ()` 한 줄. 수정 후 `rows: 40000, dropped: 39978`, 스캔 줄 `rows: 22, batch pages: 114 (row path: 0)`.
- **④ 일반화**: **새 실행 경로(배치)를 열 때는 기존 행 경로의 행별 검사(필터·런타임 필터·MVCC 가시성…)를 표로 적고 하나씩 "배치가 같은 기준으로 하는가" 를 대조한다** — 빠진 검사는 결과를 바꾸지 않고 효과만 지우므로 답안 diff 로는 안 잡히고 trace 카운터로만 보인다. 못 넣는 검사는 "플랜 거절 → 행 경로" 로 닫고, 새 경로의 폴백 행 경로에도 같은 한 줄을 둔다. 재현 SQL 에는 그 검사가 실제로 만들어지는 조건(`NO_PARALLEL_SUBQUERY`)을 힌트로 박고 이유를 적는다.
