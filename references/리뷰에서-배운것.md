# 리뷰에서 배운 것

리뷰 코멘트(사람·봇)에 답하면서 **확정한 사실과 다시 밟지 않을 함정**을 누적한다.
답글을 게시할 때마다 한 항목씩 append 한다(규약: `skills/review-response/SKILL.md` §7).

- 항목은 **최신이 위로**. 형식: `## <날짜> PR#<n> (<JIRA>) — <한 줄 교훈>`
- 각 항목에 ① 리뷰어가 지적한 것 ② **검증 방법과 결과**(어느 파일·함수를 읽었나, 무엇을 돌렸나)
  ③ 고친 것 ④ **일반화한 규칙**(다음에 어디서 같은 실수를 하나) 을 적는다.
- 코드 사실은 여기서 끝내지 않고 `dev4-ai-source` 해당 모듈로도 보낸다(중복이 아니라 역할 분담 —
  여기는 "리뷰가 나를 어떻게 고쳤나", 거기는 "이 코드가 어떻게 동작하나").
- 리뷰어 지적이 **틀렸던** 경우도 적는다. 무엇을 근거로 반박했는지가 다음 반박의 재료가 된다.

## 2026-09-18 PR#7977 (CBRD-27251) — DB_VALUE 를 만드는 `db_make_*` 는 버퍼를 빌린다, 복사하지 않는다

**지적** (greptile-apps, `histogram_cl.cpp`): 재패딩한 값의 수명을 설명한 주석이
"`db_make_varchar () below copies it out before that`" 라고 적었는데, 그 함수는 복사하지 않으므로
소유권 계약을 반대로 설명한다는 것.

**검증**: `db_make_varchar()`(`src/compat/dbtype_function.i`) → `db_make_db_char()` 로 내려가고,
거기서 `value->data.ch.medium.buf = str` 로 **호출자의 포인터를 그대로 넣고** `value->need_clear = false`
로 둔다. 복사 없음. 지적이 맞았다.

**고친 것**: 주석을 실제 안전 조건으로 다시 썼다 — 안전한 이유는 복사가 아니라 **소비 시점**이다.
`db_string_like()` 가 같은 호출 안에서 값을 다 쓰고 반환하고, `pad_buf` 를 다시 채우는 것은
호출자의 다음 반복이다. 같은 파일의 `rlike_match_string()` 은 `std::string (value)` 로 진짜 복사하므로
기존 주석("copy by length")을 유지했다 — **두 경로가 다르다는 것을 확인하고 각각 다르게 적었다.**

**일반화**
- **수명·소유권을 주석에 쓸 때는 그 API 가 복사하는지 빌리는지 정의를 열어 확인한다.** 이름(`make`, `set`,
  `assign`)으로 추측하지 않는다. CUBRID 의 `db_make_*` 계열은 대체로 **빌린다**(`need_clear=false`);
  복사를 원하면 호출자가 `std::string`·`db_private_alloc` 으로 따로 떠야 한다.
- 지역 버퍼(`std::string pad_buf`)를 루프 밖에 두고 재사용하는 패턴은 성능상 맞지만, 그 버퍼를 가리키는
  `string_view`·`DB_VALUE` 가 **다음 반복 전에** 소비되는지를 주석에 남긴다. "복사된다" 로 뭉개면
  다음 사람이 그 view 를 밖으로 들고 나간다.
- 틀린 주석은 틀린 코드보다 오래 산다. 리뷰에서 주석 지적이 오면 **코드를 다시 읽어 사실을 확정한 뒤**
  고친다(이 건은 봇 제안 문구를 그대로 받지 않고, 확인한 사실에 맞춰 다시 썼다).

## 2026-09-18 PR#7977 (CBRD-27251) — 상수를 답안에 박는 TC 를 거절할 때는 대안을 형태까지 제시한다

**지적** (greptile-apps, `histogram_reader.hpp`): 저장측 정규화·프로브 정규화·HLL 해시·LIKE/REGEXP
재패딩의 공통 계약을 바꾸면서 자동 회귀 테스트가 없다. 정확한 selectivity 상수 대신 **매칭 관계나
기대 범위**를 검증하는 안정적인 테스트를 넣으라는 것.

**판단**: TC 미추가는 사용자 결정이었다(선택도 상수는 버킷 수·MCV 임계·NDV 추정기가 바뀔 때마다
흔들려 답안 유지 비용이 계약보다 커진다). 실제로 같은 시기 PR#7976 의 CI 실패 상당수가 그런
상수 베이스라인이었다 — 거절의 근거가 실측으로 있었다.

**답글에 넣은 것**: 거절 이유만 적지 않고, 지적이 가리킨 방향(상수 대신 관계)을 **부등식 판정 shell TC
3항목**으로 구체화해 제시했다 — ① VARCHAR 에서 `c='abcd '` 추정 < `c='abcd'` ② CHAR 에서
`LIKE 'abcd %'` 추정이 실제 행수와 같은 자릿수 ③ `ignore_trailing_space` on/off 에서 CHAR 등가 추정 동일.
세 항목 모두 구현 상수가 바뀌어도 방향이 유지되고 수정 전 빌드에서 실패한다.

**일반화**
- 제안을 받지 않을 때 "유지 비용" 만 말하면 같은 지적이 다음 PR 에 다시 온다. **그 지적이 지키려는
  계약을 값이 아닌 관계로 옮기는 형태**까지 제시하면 논의가 한 번에 닫힌다.
- TC 를 안 만들기로 했으면 **재현 스크립트와 전/후 표를 JIRA 에 첨부**해 "검증을 안 했다" 와
  "자동화를 안 했다" 를 구분한다.
