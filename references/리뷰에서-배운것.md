# 리뷰에서 배운 것

리뷰 코멘트(사람·봇)에 답하면서 **확정한 사실과 다시 밟지 않을 함정**을 누적한다.
답글을 게시할 때마다 한 항목씩 append 한다(규약: `skills/review-response/SKILL.md` §7).

- 항목은 **최신이 위로**. 형식: `## <날짜> PR#<n> (<JIRA>) — <한 줄 교훈>`
- 각 항목에 ① 리뷰어가 지적한 것 ② **검증 방법과 결과**(어느 파일·함수를 읽었나, 무엇을 돌렸나)
  ③ 고친 것 ④ **일반화한 규칙**(다음에 어디서 같은 실수를 하나) 을 적는다.
- 코드 사실은 여기서 끝내지 않고 `dev4-ai-source` 해당 모듈로도 보낸다(중복이 아니라 역할 분담 —
  여기는 "리뷰가 나를 어떻게 고쳤나", 거기는 "이 코드가 어떻게 동작하나").
- 리뷰어 지적이 **틀렸던** 경우도 적는다. 무엇을 근거로 반박했는지가 다음 반박의 재료가 된다.

## 2026-09-18 PR#7977 (CBRD-27251) — DB_VALUE 를 만드는 `db_make_*` 는 버퍼를 빌린다, 복사하지 않는다

**지적** (greptile-apps, `histogram_cl.cpp`): 재패딩한 값의 수명을 설명한 주석이
"`db_make_varchar () below copies it out before that`" 라고 적었는데, 그 함수는 복사하지 않으므로
소유권 계약을 반대로 설명한다는 것.

**검증**: `db_make_varchar()`(`src/compat/dbtype_function.i`) → `db_make_db_char()` 로 내려가고,
거기서 `value->data.ch.medium.buf = str` 로 **호출자의 포인터를 그대로 넣고** `value->need_clear = false`
로 둔다. 복사 없음. 지적이 맞았다.

**고친 것**: 주석을 실제 안전 조건으로 다시 썼다 — 안전한 이유는 복사가 아니라 **소비 시점**이다.
`db_string_like()` 가 같은 호출 안에서 값을 다 쓰고 반환하고, `pad_buf` 를 다시 채우는 것은
호출자의 다음 반복이다. 같은 파일의 `rlike_match_string()` 은 `std::string (value)` 로 진짜 복사하므로
기존 주석("copy by length")을 유지했다 — **두 경로가 다르다는 것을 확인하고 각각 다르게 적었다.**

**일반화**
- **수명·소유권을 주석에 쓸 때는 그 API 가 복사하는지 빌리는지 정의를 열어 확인한다.** 이름(`make`, `set`,
  `assign`)으로 추측하지 않는다. CUBRID 의 `db_make_*` 계열은 대체로 **빌린다**(`need_clear=false`);
  복사를 원하면 호출자가 `std::string`·`db_private_alloc` 으로 따로 떠야 한다.
- 지역 버퍼(`std::string pad_buf`)를 루프 밖에 두고 재사용하는 패턴은 성능상 맞지만, 그 버퍼를 가리키는
  `string_view`·`DB_VALUE` 가 **다음 반복 전에** 소비되는지를 주석에 남긴다. "복사된다" 로 뭉개면
  다음 사람이 그 view 를 밖으로 들고 나간다.
- 틀린 주석은 틀린 코드보다 오래 산다. 리뷰에서 주석 지적이 오면 **코드를 다시 읽어 사실을 확정한 뒤**
  고친다(이 건은 봇 제안 문구를 그대로 받지 않고, 확인한 사실에 맞춰 다시 썼다).

## 2026-09-18 PR#7977 (CBRD-27251) — 상수를 답안에 박는 TC 를 거절할 때는 대안을 형태까지 제시한다

**지적** (greptile-apps, `histogram_reader.hpp`): 저장측 정규화·프로브 정규화·HLL 해시·LIKE/REGEXP
재패딩의 공통 계약을 바꾸면서 자동 회귀 테스트가 없다. 정확한 selectivity 상수 대신 **매칭 관계나
기대 범위**를 검증하는 안정적인 테스트를 넣으라는 것.

**판단**: TC 미추가는 사용자 결정이었다(선택도 상수는 버킷 수·MCV 임계·NDV 추정기가 바뀔 때마다
흔들려 답안 유지 비용이 계약보다 커진다). 실제로 같은 시기 PR#7976 의 CI 실패 상당수가 그런
상수 베이스라인이었다 — 거절의 근거가 실측으로 있었다.

**답글에 넣은 것**: 거절 이유만 적지 않고, 지적이 가리킨 방향(상수 대신 관계)을 **부등식 판정 shell TC
3항목**으로 구체화해 제시했다 — ① VARCHAR 에서 `c='abcd '` 추정 < `c='abcd'` ② CHAR 에서
`LIKE 'abcd %'` 추정이 실제 행수와 같은 자릿수 ③ `ignore_trailing_space` on/off 에서 CHAR 등가 추정 동일.
세 항목 모두 구현 상수가 바뀌어도 방향이 유지되고 수정 전 빌드에서 실패한다.

**일반화**
- 제안을 받지 않을 때 "유지 비용" 만 말하면 같은 지적이 다음 PR 에 다시 온다. **그 지적이 지키려는
  계약을 값이 아닌 관계로 옮기는 형태**까지 제시하면 논의가 한 번에 닫힌다.
- TC 를 안 만들기로 했으면 **재현 스크립트와 전/후 표를 JIRA 에 첨부**해 "검증을 안 했다" 와
  "자동화를 안 했다" 를 구분한다.

## 2026-09-21 PR#7899 (CBRD-27401, 리뷰어 측) — "통계를 갱신하라" 는 CUBRID 의 DDL 정책부터 확인한다

**지적**: 내가 `xbtree_compact_overflow()` 끝에서 카탈로그 `BTREE_STATS.pages/leafs` 를 `pages_freed` 만큼 감산하자고
설계 코멘트를 냈고(플래너 `qo_iscan_cost()` 가 `leafs` 로 리프 I/O 를 잡으므로), 작성자가 "CUBRID 는 UPDATE STATISTICS
전까지 통계를 갱신하지 않지요" 한 줄로 반박·resolve 했다.

**검증**: `catalog_copy_btree_statistic()`(system_catalog.c) 은 새 표현을 쓸 때 **BTID 가 같은 것만** 이전 값을 복사한다.
REBUILD 는 drop+create 라 새 BTID → `leafs/pages` 가 0(읽을 때 `MAX(1,…)`)으로 시작. `sm_add_constraint()` 가 부르는
`sm_update_statistics_without_gathering_stats()` 는 이름과 달리 **카탈로그를 다시 읽기만** 한다(`stats_get_statistics`).
매뉴얼 `ko/sql/tuning.rst` "통계 정보 갱신": DDL·DML 로 자동 갱신되지 않고 UPDATE STATISTICS 가 유일한 방법. **작성자가 맞았다.**

**고친 것**: 감산 제안 철회, COMPACT 매뉴얼 절에 "다른 DDL 과 같이 통계는 자동 갱신되지 않음" 한 구절만 요청.

**일반화**
- 통계·카탈로그 갱신을 제안하기 전에 ① `tuning.rst` 의 정책 문장 ② `catalog_copy_btree_statistic()` 의 BTID 매칭
  ③ 비교 대상 명령(REBUILD)이 실제로 무엇을 하는지 — 셋을 먼저 본다. "정확하고 싸다" 는 정책 예외의 근거가 못 된다.
- 반박이 한 줄이어도 근거를 열어 확인하고, 맞으면 **무엇을 열어 확인했는지 적으며 철회**한다. 그 확인이 다음 리뷰의 재료다.

## 2026-09-21 PR#7899 (CBRD-27401, 리뷰어 측) — "N 회마다 양보" 를 제안할 때는 재진입 위치와 경계의 부수효과 순서를 함께 적는다

**지적(내가 낸 것과 그 결과)**: 리프 WRITE 래치가 체인 전체에 걸린다고 지적하며 `max_merges` 마다 리프를 놓고
"체인 처음부터 다시 훑어도 이미 채운 페이지는 건너뛰므로 멱등" 이라고 스케치했다. 작성자가 그대로 구현했다(`b4efbd595`).

**검증(반영 코드 재독)**: ① `(*pages_freed)++` 가 `if (++merges >= max_merges) goto exit` **뒤**에 있어 라운드 경계의
전체 병합 1건이 카운트에서 빠진다(카운터만 틀림, 데이터 무사). ② `pairs_skipped` 는 라운드마다 첫 페이지부터 다시 세어
호출부에서 중복 누적된다 — 마지막 라운드(`more == false`) 값만 더하면 정확. ③ 재순회가 첫 페이지부터라 라운드마다 이미
채운 페이지를 전부 WRITE fix — 추가 fix ≈ 64·R(R+1)/2 = O(병합²/64). N=2,000 에선 +6.7k 로 보이지 않지만(작성자 실측
"불변" 과 부합) N=20,000 이면 +610k, N=100,000 이면 15M.

**고친 것**: 새 인라인 3건 게시(🟡 카운터 순서 / 🟢 `if (!more)` suggestion / 🟡 `btree_ovf_dir_locate()` 로 재개 위치
라우팅 또는 매뉴얼). 원인이 내 스케치라는 점을 답글에 적었다.

**일반화**
- 배치 양보(yield every N)를 제안하면 **세 가지를 같은 코멘트에** 적는다: (a) 재진입 위치를 어떻게 넘기나(처음부터 = O(N²)),
  (b) 경계에서 "커밋됨" 과 "집계됨" 의 순서 — 집계는 `goto`/`break` 앞에, (c) 라운드마다 다시 세는 카운터가 있는가.
- 내 제안이 반영된 커밋은 **제안이 맞았는지가 아니라 코드가 맞는지**를 다시 읽는다. 반영 커밋에서 결함 3건이 나왔다.

## 2026-09-21 · PR#7993 (CBRD-27126 비용 단가 파라미터화) · greptile P1 — 플랜에 영향 주는 파라미터와 XASL 캐시 키
- **① 지적**: `system_parameter.c` 새 비용 파라미터 5종이 `PRM_FOR_CLIENT | PRM_USER_CHANGE` 만 갖고 `PRM_FOR_QRY_STRING` 이 없어, 값을 바꿔도 XASL 캐시가 옛 단가로 컴파일된 플랜을 재사용한다.

- **④ 일반화**: **옵티마이저 결정에 들어가는 클라이언트 파라미터를 추가하면 `PRM_FOR_QRY_STRING` 을 같이 켠다** — 기본값과 다른 값만 키에 붙으므로 무회귀 비용은 0. 그리고 **파라미터 효과 검증을 `/*+ recompile */` 로만 하면 캐시 경로가 가려진다** — 같은 SQL 을 힌트 없이 두 번(변경 전/후) 실행하는 케이스를 항상 넣을 것. 시스템 파라미터 추가 시 새 플래그 조합은 같은 성격의 기존 파라미터(여기선 `max_hash_list_scan_size`)에서 베낀다.
