- 계기: 11-03 #8314·#4614 메시지를 이전 초안 파일만 보고 써서 본문 첫 줄 JIRA 링크를 빠뜨렸다.

## 0. 먼저 — 머지할 수 있나
- claude-workspace `tools/merge_gate.py <엔진 PR>` 가 **PASS** 여야 메시지를 쓴다. 검사 항목은 다음 넷이다.
  - 엔진 승인
  - TC PR 의 사람 승인·draft 아님
  - 세 PR 의 답하지 않은 스레드 0
  - TC PR 본문·제목이 봇 기본값 아님
- FAIL 이면 목록을 사용자에게 보이고 멈춘다(정본 메모리 `PR브랜치-규칙` §5).
- **머지 순서**(TC Merge Gate):
  1. 바뀐 파일이 0 인 Draft TC PR 을 닫는다(사용자 몫).
  2. `Check TC PRs` 를 다시 돌린다.
  3. TC PR 을 머지한다(private-ex·testcases).
  4. 엔진 PR 을 바로 이어서 머지한다.
- 머지 승인을 요청할 때, 밖에서 보이는 동작이 바뀌면 끝에 `스펙 변화 확인:` 블록을 단다(메모리 `스펙변화-리마인드`).

## 1. 세 리포 공통
- **제목**: `[CBRD-XXXXX] <영어 한 줄> (#<그 리포의 PR 번호>)`.
  - 지라 키로 시작하고, 끝에 그 리포의 PR 번호를 붙인다(엔진 번호 아님).
  - PR 제목을 그대로 쓰지 않는다. 본문 Remarks 와 대조해 **철회·분리된 항목이 제목에 남지 않게** 한다(PR#7622: 철회된 `plan-comparator band` 가 제목에 남았다).
- **본문 첫 줄은 JIRA 링크다**: `http://jira.cubrid.org/browse/CBRD-XXXXX`.
  - 11-03 실측으로 세 리포 develop 최근 스쿼시 커밋이 거의 모두 이렇게 시작한다(`Refer to http://…` 꼴도 있다).
  - 예외는 봇 커밋(서브모듈 bump)과 본문 없는 커밋뿐이다.
- **본문은 영어**다. 100자 안팎에서 줄을 바꾼다. 평서문으로 "무엇이 틀렸나/느렸나 → 무엇을 바꿨나 → 결과" 순서로 쓴다.
- **PR 본문만 요약한다** — 소스를 다시 열지 않는다. 머지 직전에는 리뷰가 끝난 본문이 정본이다.
- **쓰지 않는 것**:
  - 다른 DB 이름·비교 문장. PR 본문의 「다른 DB 대비 성능 (머지 메시지에 넣지 않음)」 절도 옮기지 않는다 — 정본 메모리 `참조DB-표기`. 엔진 리포에서 직접 squash 커밋을 만들면 guard 규칙 9 가 검사한다.
  - 로컬 경로·로컬 도구(`goto`, `~/bin/*`, `/home/cubrid/…`, `file://`).
  - 내부 라벨(리뷰 지적 id, 대기열 H-NN)·리뷰 스레드 경과·사람 이름.
- **수치는 develop 대비만 쓴다**(before -> after). CTP 통과 건수는 쓰지 않는다.

## 2. 엔진 (cubrid)
```
[CBRD-XXXXX] <무엇을 하나 — 철회 항목 뺀 것> (#N)

http://jira.cubrid.org/browse/CBRD-XXXXX

<문제 문단: 어떤 조건에서 무엇이 틀렸나/느렸나, 사용자가 겪는 결과>

- <바뀐 함수·규칙 한 줄씩 — 무엇을 하게 됐고 왜 그게 맞나>
- <안 건드리는 것(범위의 경계)이 중요하면 한 줄>

<결과 문단: 질의 결과·오류가 같은지, 수치 before -> after(develop 대비, 빌드 모드)>

Not in this change: <분리·철회한 항목과 그 이슈 키·PR>
```
- 변경 축은 항목마다 한 줄이다. 벤치 수치는 PR 본문에서 develop 대비만 인용한다. 리뷰에서 철회·분리된 항목은 `Not in this change:` 에 쓴다.
- 실제 예(develop `80b84317d`, #8343):
  ```
  [CBRD-27852] Close the subsessions earlier executions of an EXECUTE left before compiling the next one (#8343)

  http://jira.cubrid.org/browse/CBRD-27852

  An SQL-level EXECUTE that compiles its prepared text again at every execution (a SELECT whose
  PREPARE left no plan, e.g. a VARCHAR column compared without a histogram, every DML, and an
  execution that ends in an error) hung each compilation (a subsession) on the client session
  that ran it until the session closed. A client that executes the same EXECUTE handle again
  ... grew by about 150 KB per execution, and a CAS restarted on its size limit every few hundred executions.

  do_recompile_and_execute_prepared_statement () closes, before it opens this execution's
  subsession, the subsessions that earlier executions left on the client session's chain. ...
  Query results and errors are unchanged. Client memory per execution (release, before -> after):
  C API VARCHAR-column SELECT ~160 KB -> 0, C API UPDATE ~147 KB -> 0, CAS through CCI ~160 KB -> 0;
  CHAR- and INT-column SELECT stay 0.

  Not in this change: the recompilation at every EXECUTE of a VARCHAR-column SELECT itself (CBRD-27143, #8006).
  ```

## 3. TC 리포 (cubrid-testcases · cubrid-testcases-private-ex)
- **제목**: PR 제목을 쓴다. 스쿼시 머지는 PR 제목을 develop 커밋 제목으로 쓴다.
  - private-ex 는 룰북(`shell/AGENTS.md` 「The PR」)대로 '무엇을 더하거나 바꾸나'를 쓰고, 봇 관용구 `Draft: TC changes for PR …` 를 남기지 않는다.
  - develop 이력에는 엔진 PR 제목을 그대로 쓴 TC 커밋도 많다. 둘 다 키로 시작한다.
- **새 TC**:
  ```
  [CBRD-XXXXX] Add a shell TC: <무엇을 확인하나> (#N)

  http://jira.cubrid.org/browse/CBRD-XXXXX

  Add <TC 경로>: <실행 방식과 표 — 기대값이 기대는 것만>.

  1. <조건>: <기대>
  2. ...

  Verdict: before the fix NOK <n> (<어느 케이스가 어떻게>) and OK <m>; after the fix OK <all>.
  <의존·환경 제약 한 줄>
  ```
- **답안·케이스 변경**: 넣을 것은 다음과 같다.
  - 왜 답안이 바뀌었나(플랜 변화 등)
  - 판정 방법(실측 fetch·시간 비교)
  - 개선·중립·회귀 건수
  - **케이스 수정**(답안이 아니라 `.sh`·`.sql` 을 고친 것)은 따로 쓴다.
  - **안 바꾼 것**과 그 이유
- 실제 예(private-ex develop `ad4baf7ba`, #4669): 제목 `[CBRD-27852] Add a shell TC: a repeated EXECUTE handle keeps no compilation per execution (#4669)`, 본문 첫 줄 JIRA 링크, 케이스 1~4, `Verdict: before the fix NOK 3 (cases 1, 2, 4 …) and OK 1; after the fix OK 4.`

## 3-1. 백포트 (release/11.x 의 엔진 PR)
사용자 지시 2026-11-09 PR#8459 "백포트 할때 스쿼시메시지 양식 확인해서". 형식은 release/11.4 이력에서 확인한다(`git log upstream/release/11.4`).
- **제목**: `[CBRD-XXXXX] [Backport] <develop 커밋 제목> (#<develop PR>) (#<백포트 PR>)`.
  - 실제 예: `db9ed9a4e` `[CBRD-27142] [Backport] Bound the partial join search by an enumeration budget, not a table-count staircase (#7721) (#8228)`, `88360b4ac`(#8010 → #8230).
  - 팀에는 `[Backport-11.4.7]`(대상 릴리스, 백포트 PR 번호만) 꼴도 있다(`a9af05dbe` #8294). PR 제목이 정한 꼴을 따른다.
- **본문**: 첫 줄 JIRA 링크, 다음 문단은 `Backport of #<develop PR> to release/<ver>.` 로 시작해 develop 메시지의 문제·수정을 요약한다. 끝에 목록:
  - `- cherry-picked from <develop 스쿼시 커밋> without changes (<파일>)` — 충돌을 풀었으면 무엇을 어떻게(`88360b4ac`: "the conflict with … is resolved in the same order as develop").
  - 릴리스에 영향이 생긴 시점(회귀면 원인 이슈와 버전)처럼 release 쪽 사람에게 필요한 한 줄.
- develop PR 이 아직 머지 전이면 백포트 PR 은 그 PR 의 커밋을 가져온다. 메시지에는 그 커밋을 적어 두고, develop 머지 뒤 백포트를 머지할 때 develop 스쿼시 커밋 해시로 바꾼다.

## 4. 남기는 곳과 넘기는 법
- **파일**: claude-workspace `projects/<JIRA>/머지메시지-YYYYMMDD.md`(비공개)에 남긴다. 담을 것은 머지 순서, merge gate 결과, 세 메시지(리포마다 제목 블록과 본문 블록)다.
- **넘기는 법**: 사용자에게 보이고, 사용자가 GitHub 스쿼시 머지 창의 제목·본문에 붙인다(머지는 사용자 승인 순간).
- **게시 전 스캔**: `grep -cP '\bgoto\s+\w|~/bin/|/home/cubrid/|file://' <파일>` 가 0 이어야 한다.
- **머지된 뒤**: `/post-merge <PR>` 로 정리한다(브랜치·goto 캐시·tc/pr-N·보드·현황).
