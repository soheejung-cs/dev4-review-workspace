## 1. 원칙 — 다섯 가지

1. **결론부터.** 첫 문장은 독자가 관찰할 수 있는 결과다 — 어떤 입력이 어떤 오답·정지·비용을 내나, develop 과 무엇이 다른가.
   그다음 재현, 원인, 제안. 원리 설명을 결과 앞에 두지 않는다. 첫 두 문장만 읽고 "고칠지" 정할 수 있어야 한다.
2. **주어는 행위자, 동사는 행동.** "X 의 흡수가 일어난다" 가 아니라 "`qo_apply_range_intersection ()` 이 X 를 지운다".
   수동태("재작성되고", "놓입니다")를 쓰면 누가 했는지가 사라진다 — 함수·세션·사용자를 주어로 세운다.
3. **이름을 새로 짓지 않는다.** 코드·SQL·설정 키·독자가 이미 쓰는 말만 쓴다. 분석하며 붙인 이름("닿는 조건", "파생 절", "사용자 범위",
   "방어로")은 밖으로 내보내지 않는다. 꼭 필요하면 처음 나올 때 예와 함께 한 번 정의한다. 명사는 두 개까지만 잇는다.
   번역하기 어려운 용어는 원문 그대로(`SCH_S`, `prev_version_lsa`) — 억지 번역 금지(2026-09-16).
4. **지우기 시험.** 문장마다 "지우면 독자가 잃는 게 있나?" — 없으면 지운다. 유보("~로 보입니다")는 실제로 모르는 곳에만,
   한 번, 무엇을 확인하면 확실해지는지와 함께 쓴다. 사소한 것을 크게 말하지 않는다.
5. **분량 상한.** 코멘트 본문은 다섯 문장 안팎 + 재현. 인과 사슬 전체가 필요하면 `<details>` 로 접는다(voice-guide §6: 부연 6줄).
   PR 하나에 코멘트가 많으면 독자는 전부를 기계 글로 본다 — 🔴 는 하나씩, 🟡 는 8건을 넘으면 같은 파일·같은 원인끼리 묶고, 🟢 는 늘 한 코멘트로 모은다(결정 3).

- 질문: "~지 않나요?", "~할 수 있지 않을까요?" · 부드러운 단언: "~로 보입니다", "~인 것 같습니다" — 단언을 피하려고 확인한 사실까지 흐리지 않는다.
- 자기 사전지식은 드러내도 된다("~로 알고 있습니다"). 기존 함수·매크로를 가리켜 설명한다.

## 4. 고친 예 하나

**전** (PR#8375 1번, 첫 문단 + 꼬리표 4개, 약 600단어):
> 외부 조인 ON 에 상수 범위와 OR-of-AND 를 함께 쓴 부질의가 UPDATE·DELETE 안에 있으면, 자동 파라미터화가 꺼진 문맥에서 사용자 ON 조건(`i.b >= 2`)이 사라져 고치거나 지우면 안 되는 행이 바뀝니다.
> 왜 문제가 되는지: 이제 ON 인자에서도 파생 절을 만들고 … 파생 절 `i.b range (1 =, 3 =)` 가 사용자 범위 `i.b >= 2` 보다 앞에 놓입니다. …
> 닿는 조건: …

**후**:
> 아래 UPDATE 가 이 PR 에서 고치면 안 되는 행을 고칩니다. develop 은 (1, NULL)(2, 2), 이 PR 은 (1, 1)(2, 2) 입니다. 자동 파라미터화가 꺼질 때만 생기고(PL/CSQL 정적 SQL, `max_plan_cache_entries=0` 등), 같은 부질의를 SELECT 로만 돌리면 둘 다 맞습니다.
> (재현 SQL)
> UPDATE 는 부질의를 두 번 재작성합니다(xasl_generation.c:25273). 두 번째 재작성에서 `qo_apply_range_intersection ()` 이 사용자가 쓴 `i.b >= 2` 를 OR 에서 뽑아 낸 `i.b range (1 =, 3 =)` 에 합칩니다. 그런데 인덱스가 받지 않은 OR 파생 조건은 `make_pred_from_plan ()` 이 버리므로(plan_generation.c:1990) `i.b >= 2` 도 함께 사라집니다.
> (제안 + 코드)
