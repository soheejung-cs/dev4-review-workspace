# 근거 기반 설명·설계 — 연구와 전공 지식으로 받치기

"왜 이 구조가 맞나"를 **우리 측정 + 확립된 연구 + 전공 교과 지식** 세 겹으로 받친다.
목적은 읽는 사람이 결론을 믿게 하는 것이 아니라 **확인할 수 있게** 하는 것이다.
(사용자 지시 2026-10-23: "저 문서 만들 때 쓴 방법을 설계할 때도, 설계문서 넣을 때도" — 예시는 맨 아래.)

쓰는 곳: 설계문서(`skills/design-doc`)의 아이디어·대안표·외부 근거, 설계 리뷰(`skills/design-review` §2)·덱(퍼스널 `design-deck` 12장)의 외부 근거,
팀 설명 문서(Claude Docs), PR 본문의 배경 단락.

## 1. 뼈대 — 10절

| # | 절 | 담는 것 | 형식 |
|---|---|---|---|
| 1 | 한 줄 요약 | 무엇을 바꿨나, 무엇이 얼마나 줄었나, 결과는 같은가 | 3~4문장 |
| 2 | 지금 시간을 쓰는 곳 | perf·trace 로 나눈 **시간 지도**(단계·비중·내용)와 출처 | 단계 목록 + 표 |
| 3 | 구조 그림 | 전/후 두 흐름을 **같은 단계 이름**으로 나란히, 물러나는 길(폴백)은 점선 | 그림 1 + 읽는 법 3문장 |
| 4 | 왜 맞나 | **메커니즘별 근거표**(§2) + "교과서에서는" 문단 | 표 + 목록 |
| 5 | 정확성 | 물러나는 단위(레코드·청크·스캔 등) 표 + 의미 보존 목록(NULL·콜레이션·수치형·순서·가시성) + 확인한 것 | 표 + 목록 |
| 6 | 실측 | 조건(빌드 해시·하드웨어·계약·회수)과 함께, **좋아진 것과 나빠진 것 둘 다**. 흔들린 회는 표시 | 표 2개(합계·항목별) |
| 7 | 이득이 작은 곳 | 일반 법칙(암달의 법칙·루프라인·연구의 반례)으로 설명 + 지금 나빠진 것 | 목록 |
| 8 | 다른 선택지 | 연구에서 정리된 대안 축 표 + 연구의 결론 + **우리 설계와 같은 모양의 선례 논문** | 표 + 문단 |
| 9 | 앞으로 | 하위 태스크·측정 계획 | 목록 |
| 10 | 용어와 참고 문헌 | 용어표 + 서지(§3 형식) + 읽는 순서 | 표 + 번호 목록 |

설계문서(아직 구현 전)면 6절은 "검증 계획"(무엇을 어떤 계약으로 잴지), 7절은 "예상 한계"가 된다. 나머지는 같다.

## 2. 근거표 쓰는 법

```
| 이유(메커니즘) | 지금 생기는 일 | 바꾸면 달라지는 것 | 근거 |
| 1. 해석·호출 비용 상각 | 연산자 사이 next() 호출·식 트리 해석이 행마다 | 청크 전체에 한 번의 루프 | 저자, 학회 연도: 발견 한 문장 + 수치(조건) |
```

- 행 하나 = 메커니즘 하나. "빠르다"가 아니라 **무엇이 몇 번에서 몇 번으로** 바뀌는지(행마다 → 청크마다).
- 근거는 두 층이다. (a) **연구 논문** — 측정·실험으로 보인 것. (b) **전공 교과·고전** — 그것이 보편 지식임을 보인다:
  강의 노트(CMU 15-445 처리 모델), *Computer Systems: A Programmer's Perspective*(5장 최적화·6장 메모리 계층),
  *Computer Architecture: A Quantitative Approach*(암달의 법칙·메모리 계층·분기 예측·SIMD), Lampson "Hints for Computer System Design",
  해석기 디스패치(Ertl·Gregg 2003), 루프라인(Williams 외 2009).
- **한계도 같은 근거로** 쓴다(7절): 몫이 작으면 암달의 법칙, 메모리 대역폭이면 루프라인, 계산이 무거우면 연구의 반례.
- **같은 모양의 선례**를 찾아 "발명이 아니라 이식·확장"을 보인다(예: 행 저장소의 블록 처리 Padmanabhan 외 ICDE 2001,
  벡터 스캔 + 행 단위 파이프라인 혼합 Lang 외 SIGMOD 2016).
- 근거표는 "왜 그럴 것인가", 실측 절은 "실제로 그런가"다. 근거표만으로 성능을 주장하지 않는다(측정-규칙).

## 3. 인용 확인 — 빠뜨리면 틀린다

1. 후보는 기억으로 나열해도 되지만, **서지는 검색으로 확인**한다(WebSearch standard → DBLP·출판사·저자 페이지): 저자 순서, 학회/저널, 권호, 쪽, 연도.
2. **수치·문장을 인용하면 원문에서 그 문장을 찾는다.** PDF 는 새 빈 디렉터리(잡 tmp)에 받고, 다른 곳에서
   `python3 -I tools/pdf_text.py <pdf> --find "<문구>"` 로 찾는다(이 컨테이너엔 pdftotext·pdftoppm 이 없다).
   글자 사이에 공백이 낀 PDF 는 `--despace`.
3. 원문에서 못 찾은 수치는 쓰지 않는다 — 결론만 일반적으로 쓰거나 뺀다. 요약 사이트·AI 요약은 **찾는 데만** 쓰고 근거 열에 넣지 않는다.
4. "한두 자릿수" 같은 모호한 말 대신 **배수와 조건**으로 쓴다: "TPC-H 100GB 에서 10~100배", "최대 10배(Xeon Phi 기준, 일반 CPU 는 약 2배)".
5. 링크는 **확인한 것만**(DOI·저자 PDF·강의 사이트). 확인 못 한 DOI 는 넣지 않는다.
6. 서지 형식: `저자. 제목. *학회/저널* 권(호):쪽, 연도. [doi](…)` — 한 줄 설명(왜 읽나)을 붙인다.

2026-10-23 사례에서 원문 대조로 바로잡은 것(기억으로 쓴 표현이 틀렸던 것):
- Boncz·Zukowski·Nes(CIDR 2005): "기존 기술 대비 한두 자릿수" → 원문 "between one and two orders of magnitude higher than previous technology"(TPC-H 100GB) → "10~100배".
- Ailamaki 외(VLDB 1999): "L1 명령어 캐시 정체가 큰 몫" → 원문 "half the execution time is spent in stalls", "90% of the memory stalls are due to second-level cache data misses … and first-level instruction cache misses", "Significant stalls (e.g., 20%) … branch mispredictions".
- Polychroniou 외(SIGMOD 2015): "스칼라 대비 한 자릿수" → 원문 "up to an order of magnitude faster", 본문 "on Haswell, vector code is about twice faster".

## 4. 쓰지 않는 것

- 경쟁 DBMS 제품명과 "그 구조를 따왔다"는 표현(메모리 `참조DB-표기` — 비교가 필요하면 "database-reference 참고").
  논문 제목에 들어간 **연구 시스템 이름은 서지 그대로** 둔다.
- 공식 논문이 아닌 출처를 근거로 이름을 달지 않는다(코드 주석은 더 엄격: 주석에는 참조 구현을 언급하지 않는다).
- 측정 없이 "빨라진다", 근거 없이 "업계 표준".

## 5. 만드는 순서와 형식

- 팀이 읽을 문서 → **Claude Docs**(문서 커넥터): 뼈대(제목 + pending 10개) 먼저 만들고, 절마다 채운다. 사용자에게는 절이 바뀔 때 한 줄로만 알린다.
  그림은 위젯 — 글자마다 literal `data-claude-text-id`, 상자마다 `data-claude-anchor`, 화살표 마커 하나; 게시 후 스크린샷으로 글자 넘침을 본다.
- 저장소 문서(`projects/CBRD-n/설계문서.md`) → 같은 절을 마크다운으로, 그림은 mermaid 또는 그림 1개.
- 순서: 2절(시간 지도) → 4절 근거표의 "지금 생기는 일" 열 → 후보 논문 나열 → §3 확인 → 근거 열 채움 → 7·8절 → 10절 서지 → 3절 그림 → 1절 요약(맨 마지막에 고쳐 쓴다).
