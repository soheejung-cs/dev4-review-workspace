## Part 1. 왜 물리 설계인가 (Chapter 0)

### 1.1 목표: Faster, Better, Cheaper — 동시에

소프트웨어 개발의 사업적 목표는 3차원(일정/제품/비용)입니다. 보통 이건 트레이드오프라고 봅니다. 저자의 주장은 **설계 공간 자체를 이동시키면 세 축을 동시에 개선할 수 있다**는 것. 방법은 개발 프로세스의 산출물(소프트웨어)이 다시 프로세스로 **피드백**되게 만드는 것, 즉 실질적 재사용입니다.

이상적 종착점: 필요한 컴포넌트가 이미 다 있어서, 애플리케이션 개발이 "필요한 조각을 찾아 조립하는 것"에 가까워지는 상태. 저자는 이 접근을 **long-term greedy**라고 부릅니다.

현재 업계의 증상들(저자가 나열): 개발 일정의 예측 불가능성, 재사용의 위험성, 사소한 프로그램인데 엄청난 빌드 시간과 실행 파일 크기, **기존 제품에 자명한 개선조차 시도할 때 느끼는 두려움**.

### 1.2 애플리케이션 vs 라이브러리 — 근본적으로 다른 일

| | 애플리케이션 | 라이브러리 |
|---|---|---|
| 방향 | 하향식(top-down) | 상향식(bottom-up) |
| 목표 | 빠르게 문제 해결, 나중에 고칠 수 있게 | 제대로 해결, 이후 변경 없게 |
| 수명 | 짧고 계속 변함 | 길다 (의존하는 모든 앱의 수명을 포괄) |
| 좋은 코드의 성질 | **malleable** (변경 쉬움) | **stable** (변하지 않음) |
| 트레이드오프 | 구현 편의 우선 가능 | **구현 편의를 희생해 사용 편의를 취함** |

핵심 통찰: **재사용 가능한 것은 안정적인 것뿐입니다.** 상위 레벨이 세운 가정이 나중에 무효화되지 않아야 하니까요. 기존 컴포넌트의 동작을 비호환적으로 바꾸는 대신, 유사한 것을 새로 만들어 나란히 두는 게 나을 때가 많습니다. 반대로 malleable한 코드는 **최상위에 있어야 하고 공유되면 안 됩니다**. 안정적이지도 malleable하지도 않은 소프트웨어가 최악입니다.

### 1.3 협업적 재사용 vs 계층적 재사용 (이 책의 핵심 은유)

문제를 최소한으로만 쪼개면(minimal decomposition) 인터페이스 경계마다 불규칙성이 넘치는 **깨진 접시(cracked plate)** 같은 소프트웨어가 됩니다. 조각들이 서로를 의식하고 있어서 따로 떼어 쓸 수 없죠.

저자의 유명한 예시: **ToasterToothbrush**(토스터칫솔). 이걸 Toaster + Adapter + Toothbrush로 분해하면 **고전적 재사용(classical reuse)** 달성. 하지만 여기서 멈추면 부족합니다. 각각을 다시 (Case + Chassis), (Arm + Joint), (Handle + Bristles)로 **선제적으로** 분해해야 — 그때 비로소 ToasterScrubbrush를 Toaster + Adapter + Handle + Bristles로 조립할 수 있습니다. 이게 **계층적 재사용(hierarchical reuse)**.

교훈: 재사용은 "만들어놓고 기다리는" 게 아니라 **집요한 세분화(aggressive factoring)** 의 결과.

파라미터 6개 함수 예시도 같은 논리입니다. 6개 파라미터 함수를 만들었다면 아마 하나를 빠뜨렸을 것이고, 나중에 추가하려면 기존 함수를 수정(open-closed 위반)하거나 통째로 새로 만들어야 합니다. 애초에 파라미터 1개 함수 6개를 만들어 조합했다면, 7번째를 기존 6개에 영향 없이 추가할 수 있었습니다.

### 1.4 Software Capital (소프트웨어 자본)

애플리케이션 코드를 가능한 한 안정적인 라이브러리로 **밀어 내려(demote)** 정제하고 재사용 가능하게 만든다 → 이 저장소는 시간이 갈수록 배당을 주는 **기업의 자본 자산**이 됩니다.

- 1차 목적: 향후 제품의 **time-to-market 단축**. 품질 향상과 유지비 절감은 부수 효과.
- 초기 몇 개 프로젝트는 이득이 거의 없습니다. 반복되는 비즈니스 니즈를 관찰하며 자본을 쌓습니다.
- 성숙한 조직에서는 개발되는 코드의 대부분이 그 애플리케이션 고유의 것이 되고, 자본에 대한 재투자는 소액이 됩니다.
- **품질 기준이 비상식적으로 높아야 합니다.** 불만 있는 개발자가 할 수 있는 최악의 험담이 "너무 잘 만들어서 내가 직접 쓸 가치가 없다, 근데 이미 있으니 쓰겠다" 정도라면 재사용에 필요한 품질에 도달한 것.
- Software Capital이 없으면? 없어진 재사용 코드를 대체하는 중복 코드의 폭발이 전체 개발 노력을 압도할 수 있습니다.

### 1.5 컴포넌트: 물리적으로 균일한 소프트웨어

- **컴포넌트 = 논리 설계와 물리 설계의 원자 단위.** C++에서는 `.h` + `.cpp` (+ 반드시 `.t.cpp` 테스트 드라이버).
- 두 가지 세분화 축: **finely graduated**(수직 — 추상화 레벨 간 "거리"를 작게), **granular**(수평 — 도메인 기능의 "면적"을 작게).
- **벽돌 은유**: 컴포넌트는 집의 벽돌처럼 미시적으로는 다 다르지만 거시적 물리 형태는 동일. 멀리서 보면 벽돌을 구별하는 유일한 특성은 **물리 계층에서의 상대적 위치**. 상위 벽돌이 더 많은 일을 하는 건 크기 때문이 아니라 **하위에 의존해 위임할 수 있기 때문**.
- 균일성의 이득: 인간 인지 단순화, 도구 작성 가능, 하위 시스템 간 상호운용성, **개발자 이동성(developer mobility)** — 조직 내 어디로 옮겨도 코드 구조가 같으니 즉시 적응.

### 1.6 논리 설계 vs 물리 설계

- **논리 설계**: 기능적 측면(클래스, 함수, 상속 관계).
- **물리 설계**: 소스를 파일과 라이브러리로 어떻게 패키징하는가.
- 저자의 도발적 주장: **물리 설계는 논리 설계의 전제 조건**입니다. 문제를 하위 문제로 처음 분해하는 순간부터 고려해야 함. 나쁜 물리 설계는 곧 모듈 간 순환을 만들고, 순환 의존 모듈은 대규모에서 사실상 유지 불가능.

## Part 2. 컴파일러·링커·컴포넌트 (Chapter 1)

> 이 장은 "설계는 언어와 도구에 독립적이다"라는 통념을 정면 반박합니다. 도구 밑단에서 무슨 일이 벌어지는지 모르면 물리적 기반 없이 대규모 설계를 하는 셈이라는 것.

### 2.1 빌드 2단계

**컴파일**: 각 `.cpp`가 `#include`를 재귀 전개해 **번역 단위(translation unit)** 로 합쳐지고 → 이진 표현으로 번역되어 `.o` 파일로 저장.
**링크**: 각 `.o`의 미정의 심볼을 다른 `.o`의 정의로 해소. 모든 외부 심볼 참조가 **유일하게** 해소되어야 성공.

실무상 중요한 함의들:

- 역사적으로 `.o`는 **원자적으로** 프로그램에 포함되었습니다. 그래서 논리적으로 관련된 함수라도 같이 두면 불필요한 `.o` 의존이 끌려와 실행 파일이 커지므로 일부러 분리하기도 했습니다.
- 현대 플랫폼은 컴파일러가 중복 정의를 여러 `.o`에 만들고 링커가 하나만 취하는 방식을 지원(inline 함수, 암시적 인스턴스화). 단 플랫폼·배포 의존적이므로 **설계할 때는 여전히 `.o`가 원자적이라고 가정**합니다.
- **라이브러리 아카이브(`.a`)의 함정**: 직접 준 `.o`는 무조건 포함되지만, 라이브러리로 준 `.o`는 미해소 심볼이 있을 때만 포함됩니다. 이 차이가 동작을 바꿀 수 있습니다(런타임 초기화되는 파일 스코프 static 변수를 쓰는 "Singleton 레지스트리" 예시). 그리고 라이브러리 간 상호 의존을 만들면 플랫폼에 따라 **링크 라인에 라이브러리를 반복 명시**해야 하고, 그 순서·횟수가 사소한 변경에도 바뀝니다.

### 2.2 Linkage vs Bindage — 이 책의 독창적 개념

C++ 표준의 **linkage**(논리적)와 실제 플랫폼의 결합 메커니즘(물리적)을 구별하기 위해 저자는 후자를 **bindage**라고 새로 명명합니다.

| Linkage (논리, 표준 용어) | 의미 |
|---|---|
| external linkage | 다른 번역 단위의 엔티티를 지칭할 수 있는 이름 |
| internal linkage | 같은 번역 단위 내에서만 지칭 가능 |
| no linkage | 지칭 불가 |

| Bindage (물리, 저자 명명) | 의미 |
|---|---|
| **internal bindage** | 이름 사용과 정의의 결합이 **항상 컴파일 타임**에 이루어짐 (예: enum, 클래스 정의) |
| **external bindage** | 정의가 프로그램의 **한 번역 단위에만** 나타나야 함 (다중 정의 링크 에러 회피) |
| **dual bindage** | 정의가 여러 번역 단위에 안전하게 중복 가능하고, 링크 타임에 결합 가능 (예: inline 함수, 템플릿) |

왜 중요한가: external/dual bindage 엔티티는 정의를 클라이언트 컴파일러가 볼 필요가 없습니다 → 링커가 해소합니다 → 따라서 **로컬 `extern` 선언이 특히 위험**합니다. 잘못된 로컬 선언이 컴파일 에러가 아니라 링크 에러, 최악의 경우 런타임 오류가 되니까요. (이게 Component Property 4의 근거)

ODR(One Definition Rule) 요약: 번역 단위 내에는 어떤 변수/함수/클래스/enum/템플릿의 정의도 하나만. 프로그램 전체로는 bindage에 따라 다름 — external bindage(비inline 함수, 변수)는 전역 유일해야 하고, internal/dual bindage는 **동일한 토큰 시퀀스**로 **본질적으로 같은 의미**라면 중복 가능.

### 2.3 논리 관계 표기법 (설계 논의의 어휘)

| 관계 | 의미 |
|---|---|
| **Is-A** | public 상속 |
| **Uses-In-The-Interface** | 함수 시그니처나 반환 타입에 타입이 등장. 클래스의 (public) 멤버 함수 인터페이스에 등장하면 그 클래스의 인터페이스에 사용된 것 |
| **Uses-In-The-Implementation** | 함수/클래스 정의 안에서만 참조 (데이터 멤버 선언, private 상속 포함) |
| **Uses-In-Name-Only** | 인터페이스에 이름만 등장하고 정의는 컴파일·링크·테스트에 불필요 → **opaque pointer**와 **protocol**의 근거 |

**Protocol class 정의**: (1) 비인라인 virtual 소멸자(`.cpp`에 정의) 외에는 순수 가상 함수만, (2) 데이터 멤버 없음, (3) protocol이 아닌 클래스로부터 (직·간접) 파생하지 않음.

### 2.4 Depends-On 관계와 레벨 번호

**정의**: 컴포넌트 y가 x를 **Depends-On** 한다 = y를 컴파일하거나 링크하려면 x가 필요하다.
- **컴파일 타임 의존**: `y.cpp`를 컴파일하려면 `x.h`가 필요.
- **링크 타임 의존**: `y.o`에 `x.o`가 있어야 해소되는 미정의 심볼이 있음.
- **관찰**: 컴파일 타임 의존은 흔히 링크 타임 의존을 낳는다. **Depends-On은 전이적(transitive)이다.**

**레벨 번호(level number)** — 순환이 없을 때만 부여 가능:
- **Level 0**: 비지역(non-local) 컴포넌트
- **Level 1**: 다른 지역 컴포넌트에 물리적으로 의존하지 않는 것 = **leaf component**
- **Level N**: 레벨 N−1의 지역 컴포넌트에 최소 하나 의존하고, N 이상에는 의존하지 않는 것

레벨 번호를 부여할 수 있는 시스템을 **levelizable**하다고 합니다. 레벨 번호의 1차 목적은 **순환을 조기에 발견하고 제거하는 것**.

### 2.5 컴포넌트의 4가지 필수 속성 (암기 대상)

1. **Property 1**: `.cpp`는 자신의 `.h`를 **첫 실질 코드 줄**로 include한다.
   → 물리 인터페이스와 구현의 일관성을 컴파일러가 검증. **include 순서 의존 결함을 영구히 제거**.
2. **Property 2**: `.cpp`에 정의된, 외부 링키지를 갖는(그리고 컴포넌트 외부에서 안 보이게 처리하지 않은) 각 논리 구조는 `.h`에 선언된다.
   → 모든 내보낸 심볼이 소스 레벨에 표현되고 헤더로 접근 가능해짐.
3. **Property 3**: `.h`에 선언된, external/dual bindage를 갖는 각 논리 구조는 (정의된다면) 그 컴포넌트 내에서 정의된다.
   → 이게 없으면 `.h`/`.cpp` 같은 이름 쌍이 함의하는 모듈성이 공허해짐.
4. **Property 4**: 컴포넌트의 기능은 그 헤더의 `#include`로만 접근하고, 로컬 `extern` 선언으로는 절대 접근하지 않는다.
   → 함수 이름/시그니처/반환형 변경을 클라이언트가 **컴파일 타임에** 감지. 그리고 **`#include` 지시문만 파싱해서 물리 의존성 전체를 추출**할 수 있게 됨(C++ 소스 파싱 대비 수십~수백 배 빠름 — Perl 스크립트로 가능).

**관찰**: 시스템이 컴파일된다면, `#include` 지시문만으로 컴포넌트 간 모든 실제 물리 의존성을 연역할 수 있다.

### 2.6 헤더 파일과 include 가드

- 헤더는 번역 단위 간 공통 소스(클래스 정의, inline 함수, 템플릿, typedef, 매크로)를 공유하는 모듈 메커니즘.
- **internal include guard 필수**. **external("redundant") guard는 이제 deprecated** — 과거엔 컴파일러가 헤더를 두 번 열지 않게 해 빌드 시간을 줄였지만 현대 플랫폼에선 효용이 미미.
- `struct` vs `namespace`: 단일 컴포넌트에 국한된 스코프에는 **struct**, 컴포넌트를 넘나드는 스코프에는 **namespace**. namespace를 쓸 땐 정의를 namespace **외부**에 정규화된 이름으로 작성 → 선언·정의 불일치를 컴파일 타임에 잡음.
- `#include <...>`가 GOOD IDEA, `#include "..."`는 BAD IDEA (표준이 의미 있는 구별을 정의하지 않으며, 후자 실패 시 전자로 폴백하므로 후자가 더 원시적).

## Part 3. 패키징과 설계 규칙 (Chapter 2) — 규칙의 본체

### 3.1 물리적 집약(Physical Aggregation) 3계층

**정의**: *aggregate*(집약체)는 논리적 내용을 담는 응집적 물리 설계 단위.
- **컴포넌트** = 물리 집약의 **최내층**
- **UOR (Unit of Release, 릴리스 단위)** = **최외층**
- **패키지** = 컴포넌트보다 크면서 아키텍처적으로 유의미한 가장 작은 집약체
- **패키지 그룹** = 패키지들의 응집적 집합 (3번째이자 최상 레벨)

**Architecturally significant(아키텍처적으로 유의미함)의 정의**: 논리적/물리적 엔티티의 이름(심볼)이 그것이 정의된 UOR **외부에서 의도적으로 보이는** 경우.

**핵심 규칙**: 아키텍처적으로 유의미한 모든 엔티티의 이름은 **전사적으로 유일**해야 한다. (→ 따름정리: 모든 패키지명, 모든 라이브러리 컴포넌트 파일명, 컴포넌트 헤더에 선언된 모든 논리 엔티티의 정규화된 이름이 전사 유일)

**왜 3계층인가**: 적절히 균형 잡힌 물리 집약이 3레벨을 넘으면 거의 항상 불필요하고 문제를 일으킨다는 관찰. 수천만 줄 규모까지 3레벨로 지탱된다는 경험적 근거. 더 큰 하위 시스템은 **여러 UOR을 쓰고 그들 간 관계를 개별 표현**합니다.

**균형(balance)의 중요성**: 인간 인지를 최대화하려면 한 집약체 내의 동급 엔티티들이 **비슷한 물리적 복잡도**(= 같은 집약 레벨)를 가져야 합니다. 컴포넌트와 패키지가 한 그룹에 섞여 있으면 안 됩니다.

**Manifest와 Allowed Dependency**:
- *manifest*: 그 집약체에 속하기로 의도된 물리 엔티티들의 명세(외부 메타데이터로 표현)
- *allowed dependency*: 그 물리 계층에서 **존재가 허용된** 물리 의존성(메타데이터로 표현)
- **관찰**: 모든 물리 집약체의 정의는 (1) 집약하는 엔티티들과 (2) **직접 의존이 허용된** 외부 엔티티들의 명세를 포함해야 한다.
- 컴포넌트 간 의존은 `#include`에서 직접 추론되지만, **상위 집약 레벨의 예상 의존 범위(envelope)는 코딩 시작 전에 메타데이터로 명시**되어야 합니다.

### 3.2 Design Imperative — 반드시 지켜야 할 것들

부록에서 뽑은 6개 imperative. "규칙"보다 강한 층위입니다.

1. 물리 집약체 간 (명시된) **허용 의존성은 비순환(acyclic)이어야 한다.**
2. **컴포넌트 간 순환 물리 의존은 허용되지 않는다.**
3. 논리 구조의 private 세부에 대한 접근은 그것이 정의된 **물리 집약체의 경계를 넘을 수 없다** — 즉 "장거리(컴포넌트 간) friendship"은 허용되지 않는다.
4. 패키지 간 순환 물리 의존(허용 의존성으로 정의됨)은 허용되지 않는다.
5. UOR 간 허용 의존성은 비순환이어야 한다.
6. **Hierarchical Testability Requirement**: 모든 물리 엔티티는 **이미 철저히 테스트된 다른 물리 엔티티만으로** 철저히 테스트 가능해야 한다.

> 3번(friendship 제약)이 의외로 파급력이 큽니다. 이것 때문에 다중 컴포넌트 wrapper가 일반적으로 불가능해지고, Chapter 3의 escalating encapsulation 같은 기법이 필요해집니다.

### 3.3 논리/물리 정합성 (Logical/Physical Coherence)

논리적 캡슐화가 **물리적 실체를 반영해야** 합니다. 아키텍처적으로 유의미한 물리 집약체가 광고하는 각 논리 구조의 **직접 구현이 그 물리 모듈 안에 있어야** 하고, 각 모듈은 허용된 의존성에 따라 하위로만 위임합니다.

**Guideline**: 아키텍처적으로 응집된 논리 엔티티는 물리 엔티티 안에 **긴밀히 캡슐화**되어야 한다.

### 3.4 명명 규칙 (Logical and Physical Name Cohesion)

이 책에서 가장 논쟁적이면서 실용적 가치가 큰 부분입니다. 목표는 하나: **사용 지점만 보고 정의 위치를 즉시 알 수 있게 하라.**

**Guideline**: 패키지 namespace 스코프에 선언된 각 논리 엔티티의 *사용*만으로 그것이 정의된 **컴포넌트, 패키지, UOR을 식별할 수 있어야** 한다.

구체적 규칙 체계:

| 규칙 | 내용 |
|---|---|
| 컴포넌트 파일명 | `.h`/`.cpp`는 컴포넌트와 **같은 루트 이름** (확장자만 다름) |
| 컴포넌트 소속 | 모든 컴포넌트는 패키지 안에 있어야 함 |
| 컴포넌트명 | (전부 소문자) **패키지명 + 언더스코어**로 시작 |
| namespace | 각 논리 엔티티는 **패키지명과 같은 이름의 namespace** 안에 |
| 상위 namespace | 각 패키지 namespace는 **전사 유일 namespace** 안에 중첩 |
| 논리 구조명 | 패키지 namespace 스코프의 모든 논리 구조명은 (free operator와 `swap` 같은 aspect 함수 제외) **정의 컴포넌트의 base name을 접두사로** 가져야 함. 매크로(전부 대문자)는 **패키지 접두사 포함 컴포넌트 전체 이름**을 대문자로 접두 |
| 스코프 제한 | 컴포넌트 `.h`의 패키지 namespace 스코프에는 **클래스, struct, free operator(및 aspect 함수)만** 선언 가능 |
| free operator 제약 | free operator/aspect 함수는 **파라미터 중 하나가 같은 컴포넌트에 정의된 타입**일 때만 선언 가능 |
| `using` 금지 | 컴포넌트 내에서 **함수 스코프 밖의 `using` 지시/선언 금지** |
| include guard | `INCLUDED_PACKAGE_COMPONENTBASE` (예: `INCLUDED_BDLT_DATETIME`) |

**구체 예시**: `bdlt::Date`를 코드에서 보면 → 파일 `bdlt_date.h`/`bdlt_date.cpp`가 있고, 패키지 `bdlt`, 패키지 그룹 `bdl`에 있음을 즉시 압니다. 사람도 도구도 찾기 쉽습니다.

**왜 이름을 짧게 하는가**: `using`의 유혹을 없애기 위해서입니다. `std`처럼 극도로 짧으면 아무도 `using`을 쓰지 않습니다. "literate programming"식 긴 descriptive namespace명을 저자는 반대합니다 — 길면 `using`을 쓰게 되고, 그러면 사용 지점에서 위치를 알 수 없게 되니까요.

**중요한 함의**: 비순환 의존성을 가진 컴포넌트 집합이 있어도, **임의로 패키지에 배정하면 패키지 의존에 순환이 생길 수 있습니다.** 즉 패키지 무순환은 컴포넌트 무순환보다 강한 조건입니다.

**비용의 정직한 인정**: 이 명명 규칙 때문에 논리 엔티티를 다른 물리 위치로 옮기면 클라이언트가 코드를 고쳐야 합니다. 완화책은 **같은 라이브러리 버전에서 두 위치의 두 버전이 공존**할 수 있어 리팩토링을 기간에 걸쳐 진행할 수 있다는 것.

### 3.5 컴포넌트 설계 규칙 (Chapter 2.6 — 실무 체크리스트)

- 컴포넌트 = `.h` 하나 + `.cpp` (최소) 하나, 같은 루트 이름, 4가지 속성 만족.
- `main`을 정의하는 파일 외의 **모든 논리 구조는 컴포넌트 안에** 있어야 함.
- **inline 함수 본문을 클래스 스코프 안에 정의하지 않는다** (계약과 구현 분리 목적).
- free 함수/함수 템플릿 정의는 **선언된 namespace 밖에** → 선언·정의 불일치를 무료로 컴파일 타임 검증.
- **파일/namespace 스코프 static 객체의 런타임 초기화 금지.**
- 모든 컴포넌트 헤더는 **단독 컴파일 가능**해야 함(따름정리).
- **Guideline**: 헤더에는 헤더 자체 컴파일에 필요한 `#include`(또는 로컬 전방 선언)만 둔다.

**헤더가 다른 헤더를 include해야 하는 5가지 경우** (외우면 유용):
**(a) Is-A** (public 상속) / **(b) Has-A** (값 데이터 멤버) / **(c) Inline** (인라인 본문에서 사용) / **(d) Enum** / **(e) Typedef**
(공변 반환 타입 등 예외적 경우 소수 존재)

**Transitive include 금지** (따름정리): 다른 헤더가 대신 include해주는 것에 의존하지 않는다. **유일한 예외는 직접 include한 타입의 public 기반 클래스** — 그 의존이 본질적(intrinsic)이기 때문. 이유: `Has-A`나 `Inline` 사용으로 시작한 구현이 나중에 그 타입에 컴파일 의존이 없게 리팩토링되면 중첩 include가 제거되고, 거기에 기댔던 코드가 깨집니다.

**Guideline**: 컴포넌트당 **public 클래스 하나**를 목표로 하되, 엔지니어링적 정당성이 있으면 예외. (colocation이 정당한 경우는 Part 4에서)

**중첩 클래스**: 정의를 감싸는 클래스의 렉시컬 스코프 안에 두지 말 것(Guideline). 아예 **선언조차 피할 것**(Guideline).

### 3.6 언더스코어 규약 — component-private와 subordinate component

`_`는 순수 구분자로 쓰지 않습니다(단, 전부 대문자 단어 사이, 그리고 확립된 접두/접미사 `d_`, `s_`, `e_`, `k_`, `_p`는 예외).

- **component-private class**: 패키지 namespace 스코프에 정의되지만 **그 컴포넌트 외부에서 직접 쓰면 안 되는** 클래스. 이름에 *추가* 언더스코어가 있으면 그 표시입니다. 추가 언더스코어 앞부분(소문자화)이 컴포넌트 base name과 정확히 일치해야 합니다. 예: 컴포넌트 `xyza_list`의 `List_Link`.
  - 왜 C++ private 중첩 클래스를 안 쓰는가: 저자는 그게 여러 면에서 열등하다고 봅니다(문서화, 전방 선언, 템플릿 특수화 등에서 불편).
- **subordinate component**: base name에 언더스코어가 있는 컴포넌트는, **같은 패키지 내에서 그 이름이 접두사가 되는 컴포넌트만** `#include`할 수 있는 종속 컴포넌트임을 표시. 한 컴포넌트는 최대 하나의 비종속 컴포넌트에 종속.

### 3.7 애플리케이션 패키지의 특수성

- `.m.cpp` 파일을 하나 이상 가짐 — `main`을 정의하거나 전사 namespace 밖에 기능을 구현할 수 있는 **유일한** 파일(테스트 드라이버 제외).
- 이름이 라이브러리 패키지와 **구문적으로 구별**됨 (예: `m_` 시작).
- **애플리케이션 패키지 내부의 것은 외부에서 참조 금지** — 앱은 본질적으로 malleable하므로.

### 3.8 계층적 테스트 가능성 (2.14) — 테스트 드라이버 규칙

- 모든 컴포넌트마다 **같은 루트 이름의 유일한, 물리적으로 분리된 테스트 드라이버**(`.t.cpp`)가 있어야 한다.
- 테스트 드라이버는 **테스트 대상 컴포넌트와 같은 디렉터리**에 위치.
- **테스트 드라이버의 계층적 직접 의존성은 테스트 대상 컴포넌트의 것을 초과할 수 없다.** 초과가 불가피하면 컴포넌트 `.cpp`에 "dummy" `#include`를 주석과 함께 추가해 의존을 명시화.
- 외부 데이터/장치(DB, 텍스트 파일)에 대한 의존도 대상 컴포넌트를 초과 금지 — 자기완결적이지 않고 이식성이 떨어지므로.
- 여러 컴포넌트를 한 테스트 드라이버로 테스트하려는 시도는 일반적으로 비현실적. **한 파일에서 테스트 가능해야 한다는 요구가 컴포넌트 복잡도에 자연스러운 상한을 부여**합니다. (이게 컴포넌트 크기의 실질적 제약)
- **Guideline**: 테스트 드라이버 호출 인터페이스에 전사 표준 부분집합이 있어야 하고, "사용자 경험"도 표준화되어야 한다(개발자 이동성).

### 3.9 개발 vs 배포 (2.15) — 배포는 절대 아키텍처가 아니다

- 개발 중과 배포 시의 조직 구조는 다릅니다. 같은 패키지 그룹의 하위 패키지들이 개발 중엔 별 라이브러리일 수 있고, 다른 그룹은 뭉쳐서 한 라이브러리일 수 있습니다.
- 그래서 **컴포넌트 파일명이 전사 유일해야** 유연성이 확보됩니다(디렉터리와 무관하게).
- 규칙: **`#include`에 상대/절대 경로(디렉터리명) 사용 금지.**
- 규칙: **배포 목적만을 위한 추가 분할은 아키텍처적으로 유의미해서는 안 된다.** 빌드/릴리스 엔지니어는 최적화로 UOR을 임의의 levelizable 하위 영역으로 쪼개 별 라이브러리로 배포할 수 있지만, **개발자는 그런 최적화에 의존해선 안 됩니다.**
- **관찰**: 개발 중에 (아키텍처적으로) 가정해야 하는 UOR의 조립도(granularity)는 배포된 소프트웨어의 것보다 흔히 더 거칩니다.

### 3.10 메타데이터 (2.16)

메타데이터는 개발자가 작성하는 **엔지니어링 산출물**이며 코드에서 발견 가능합니다. 설계·정책·빌드 의도를 사람과 도구가 모두 읽을 수 있는 압축 형태로 담습니다.

| 종류 | 역할 |
|---|---|
| **Dependency metadata** | **가장 중요**. 무순환 설계 보장 + 설계 의도 소통. weak dependency, 집약 레벨별 의존성 표현 |
| **Build requirements** | 로컬/전역 정의, capabilities |
| **Membership** | 집약체 구성원 명세 |
| **Policy** | 조직 특유 제약을 boolean 술어로 (예: private dependency 정책) |

## Part 4. 물리 설계와 팩토링 (Chapter 3) — 가장 실용적인 장

### 4.1 물리적으로 사고하기 (3.1)

- 소프트웨어 설계 공간에는 **방향(direction)** 이 있습니다. 컴포넌트의 상대적 위치가 의미를 가집니다. 인터페이스와 구현의 상대적 물리 위치를 **뒤집는 것**만으로 더 유연하고 안정적인(lateral) 설계가 나옵니다.
- 소프트웨어에는 **절대적 위치(absolute location)** 도 있습니다. 기능을 "무엇을 하는가"만이 아니라 "**전사 라이브러리 어디에 둘 것인가**"를 결정해야 합니다. 라이브러리 개발자는 새 기능 구현뿐 아니라 **그것이 저장소에 제대로 편입되는 것**에 대해서도 책임이 있습니다.
- Colocation 기준은 **본질적(substantial)** 이어야 하고 표면적(superficial)이면 안 됩니다.
- **패키지 접두사는 스타일이 아닙니다**: 설계를 초기에 더 전역적으로 생각하게 만들고, 패키지 의존성을 처음부터 고려하게 강제합니다. 불투명한 접두사도 시간이 지나면 중요한 의미를 획득합니다.

### 4.2 나쁜 물리 모듈화 회피 (3.2) — Primitiveness

이 절의 핵심 개념 하나: **primitive**.

**정의**: 어떤 타입에 대해 연산이 효율적으로 구현되기 위해 **본질적으로 그 타입 객체의 private 접근을 요구**한다면, 그 연산은 그 타입의 *primitive* 연산이다.

여기서 나오는 설계 지침 체계:

- **Guideline**: 재사용 컴포넌트가 제공하는 기능은 **complete(완전)하면서 minimal(최소)** 이어야 한다.
- **Guideline**: 인스턴스화 가능 타입을 정의하는 컴포넌트 안의 (도메인 특정) 기능은 **거의 전부 primitive**여야 한다.
- **Guideline**: primitive가 아닌 기능 대부분은 **상위 레벨 utility struct**에 구현해야 한다.
- **Guideline**: 각 컴포넌트는 **좁게 집중된 목적**을 가져야 한다.

왜냐: "유용한 모든 연산은 클래스의 메서드여야 한다"는 사고방식은 불안정성을 낳고 확장되지 않습니다. 컴포넌트가 시간이 지나며 감당 불가능하게 커집니다. Primitive만 남기면 **open-closed 원칙**을 지원할 수 있습니다 — 임의의 애플리케이션 기능을 컴포넌트 소스를 고치지 않고 상위 컴포넌트에서 구현 가능해집니다.

- **관찰**: **Iterator는 명백히 primitive로 보였던 연산들을 극적으로 줄여줍니다.** (순회를 노출하면 대부분의 연산이 외부 구현 가능해짐)
- **관찰**: 구현의 유연성 정도가 무엇을 primitive로 볼지에 영향을 줍니다.
- **Guideline**: 문법(syntax)보다 **의미(semantics)와 물리 의존성**을 모듈화 기준으로 선호하라 — 특히 패키지 레벨에서.

**실패 사례 (저자의 자기 반성)**: 초기에 value type만 모은 패키지에 `t` 접미사(`bdet`), utility만 모은 패키지에 `tu` 접미사(`bdetu`)를 썼는데 실패했습니다. 이유: (1) 클라이언트가 유용한 기능을 발견하기 어려워졌고, (2) `bdet`의 다른 value type이 `bdetu`의 비primitive 기능에 의존할 수 없게 됐습니다(패키지 레벨화 위반). **C++은 다중 패러다임 언어이므로 특정 패키지에 들어갈 논리 구조의 종류를 인위적으로 제한하는 건 무의미합니다.**

**Guideline (매우 중요)**: 특정 애플리케이션을 위해 만든 범용적으로 유용한 기능은 **항상 팩토링하고, 시간이 허락하면 선제적으로 demote하여** Software Capital의 적절한 위치로 옮겨라. 이 **지속적 demotion을 안 하면 코드가 "Big Ball of Mud"로 퇴화합니다.**

### 4.3 Colocation의 4가지 정당한 이유 (3.3.1)

기본은 public 클래스/struct마다 별 컴포넌트입니다. 같은 컴포넌트에 둘 이상을 두는 것이 정당한 경우는 **딱 4가지**:

1. **Friendship이 필요할 때** (가장 흔한 이유)
2. **순환 의존이 발생할 때** (거의 항상 불필요하지만, 불가피하면)
3. **Single solution** — 각각 작고 "동료(peer)"인 엔티티들이 **함께여야 유용한 전체**를 구성할 때
4. **Flea on an elephant** (코끼리 위의 벼룩) — 아주 작은 클래스(`ScopedGuard`)나 함수(`operator==`)가 (a) 추가 의존성을 안 만들고, (b) 같은 컴포넌트의 무거운 클래스(예: logger)에 의존하며, (c) 그 컴포넌트의 일반적 사용에 필수적인 부분일 때

**Guideline**: **함께 변해야 하는 소프트웨어는 colocate하라.** 이건 클래스·함수부터 컴포넌트·패키지·패키지 그룹·UOR까지 모든 레벨에 적용되는 모듈성의 오래된 공리입니다.

**Guideline**: 긴밀한 상호 협업은 **단일 UOR 내로 제한**하라.

실전 예시들:
- 템플릿 특수화들은 일반 템플릿과 같은 컴포넌트(최소한 같은 패키지)에. 일반 템플릿이 변하면 특수화가 lock-step으로 변해야 하니까.
- 느리게 늘어나는 named entity 열거(예: day-count convention)와 그것을 아는 manager utility는 lock-step으로 변합니다. 다른 UOR에 두면 매번 두 UOR을 동시 릴리스해야 하고, 사이에 낀 UOR들까지 동시 릴리스해야 합니다 — 문제가 무한히 심각해집니다.
- encoder/decoder 쌍: 인코딩 전략이 변하면 둘 다 영향받습니다.

## Part 5. 레벨화 기법 9종 (3.5) — 순환을 깨는 도구 상자

> 이 절이 책의 실무적 정수입니다. 1996년 초판에서 제시된 9가지 기법이 20여 년 후에도 유효하고, **새로운 기법이 발견되지 않았다**고 저자가 밝힙니다. 다만 상대적 중요도는 변했습니다 — callback이 "최후의 수단"에서 일급 전략으로 승격.
>
> 실무 빈도: **escalation → demotion**이 압도적으로 자주 쓰이는 조합. dumb data가 opaque pointer보다 유용한 경우가 많다는 게 저자의 최신 견해.

### 5.1 Escalation (승격) — 가장 자주 쓰는 기법

**상호 의존적 기능을 물리 계층의 더 높은 곳으로 옮기기.**

두 컴포넌트가 서로를 참조하려 할 때, 한쪽 또는 양쪽의 어떤 측면을 **상위 레벨로 올려** 껄끄러운 *상호* 의존을 반가운 *하향* 의존으로 바꿉니다.

**전형 예시 1 — 상호 변환**: `Rectangle`과 `Box`가 같은 값을 다른 내부 표현으로 담습니다. 상호 변환 생성자를 넣으면 즉시 순환. 해법: 변환 기능을 **상위의 새 컴포넌트 `convertutil`로 escalate** → 두 타입이 상호 독립이 됩니다.

**전형 예시 2 — factory**: 추상 기반 클래스 `Widget`과 파생 `WidgetN`들이 있을 때, static factory 메서드를 `Widget`에 두면 기반↔파생 순환이 생기고, 전이성 때문에 **모든 파생 클래스들 사이에도** 순환이 생깁니다. 해법: factory를 상위 `widgetutil`로 escalate. 논리 기능 손실 전혀 없이 모든 물리 순환이 사라집니다.
> 저자의 지적: 파생 타입을 생성하는 기능을 사용하는 컴포넌트와 같은 곳에 두면 **순수 인터페이스 상속의 실질적 이점이 거의 다 사라집니다** — 타입으로 switch하는 것과 다를 바 없어지니까요.

**전형 예시 3 — 무거운 의존성 격리**: 단순한 `Date`(year/month/day 속성만) 클래스에 `isValidYearMonthDay`를 두면 특정 캘린더(Gregorian/proleptic Gregorian)에 묶이고 성능 이점도 없습니다 → 상위 `dateutil`로. 더 나아가 `DayOfWeek` 같은 새 타입이 인터페이스에 필요한 기능은 또 상위 `dayofweekutil`로.

**단, 여기서 저자가 자기 규칙에 제동을 겁니다.** 리뷰어 Jeffrey Olkin의 반론을 그대로 인용합니다: "day-of-week 함수를 찾을 때 나는 `DateUtil`을 볼 것이다. `DayOfWeekUtil`이 존재하는지도 모를 수 있다." → **지나친 세분화는 발견성(discoverability)을 해칩니다.** 그리고 이 경우엔 물리적으로도 불필요합니다: `Date`가 이미 `DayOfWeek::Enum`을 인터페이스에 쓰고 있고, serial-date 구현에서 `dayOfWeek()`는 `d_serialDate % 7` 한 번의 모듈러 연산으로 끝나므로 **본질적으로 primitive**입니다. 외부 구현으로는 그 성능이 불가능합니다.
> 교훈: 팩토링 세분도는 과학이면서 **기예(art)** 입니다. 규칙을 기계적으로 적용하면 안 됩니다.

**escalation 3단 요약**:
1. 비primitive 기능을 같은 패키지의 상위 *utility*로 → **표준 관행이어야 함**
2. utility 인터페이스에 (같은 패키지라도) 추가 타입이 들어오면 → 그 타입을 지원하는 별도 상위 utility 고려
3. UOR을 넘는 과도한 커플링이 생기면 → 상위 UOR의 또 다른 utility로

### 5.2 Demotion (강등)

**공통 기능을 물리 계층의 더 낮은 곳으로 옮기기.**

`xyz`가 내부적으로 쓰는 저수준 기능 F를, `xyz`가 의존하는 `rst`도 필요하게 되었다면 → F를 더 낮은 패키지 `abc`로 demote. 그러면 양쪽 다 순환 없이 의존할 수 있고, F의 다른 클라이언트도 `xyz`/`rst`에 의존하지 않게 됩니다.

객체 레벨 예시: `EventQueue`가 `Event`들을 관리하는데 `Event`가 부모 전체를 포인터로 들고 있으면 순환. 실제로 `Event`가 필요한 건 **공통 정보 부분**뿐 → `CommonEventInfo`를 분리해 하위 컴포넌트로 demote하면 순환이 사라집니다.

> **Software Capital과의 관계**: demotion은 단순 기법이 아니라 조직의 지속적 습관이어야 합니다(4.2절 Guideline 참조).

### 5.3 Opaque Pointers (불투명 포인터)

**객체가 다른 객체를 "이름으로만" 사용하기.**

타입을 로컬 선언(전방 선언)하되 컴파일·링크·테스트에 정의가 전혀 필요 없게 합니다 → Uses-In-Name-Only 관계.

**Manager/Employee 예시**: `Employee`에 `numStaff()` 메서드를 두면 `Manager` 정의가 필요해져 순환. 해법: `Employee`는 `Manager*`를 **불투명하게** 들고 있고(헤더 include 없음), 상위 클라이언트 함수가 `employee.manager()`로 주소를 받아 (`Manager` 정의를 아는 문맥에서) `manager->numStaff()`를 호출합니다.
> 하위 엔티티는 상위에게 직접 명령할 수 없지만, **주소로 지목하는 것은 가능**하다는 발상.

**Graph/Node/Edge 예시**: `Node`는 불투명 `Edge*`들의 컬렉션, `Edge`는 데이터 + 불투명 `Node*` 2개(head/tail). **서로의 정의를 본 적 없이 각각 독립적으로 철저히 테스트 가능**합니다. 일관성 유지는 상위 `Graph`(manager)의 책임.

**const 정확성 주의**: opaque pointer 접근자를 하나만 두면 const 우회가 생깁니다.
```cpp
// BAD IDEA — const 정확성 위반
EventQueue& stripConst(const EventQueue& q) {
    return *q.firstEvent()->parent();  // const 객체에서 non-const 참조 획득
}
```
→ const/non-const 두 버전의 parent 접근자를 병행 제공해야 합니다.

**주의**: 자원을 관리하지 않는 raw pointer이므로, 가리키는 객체의 수명을 넘겨 실질적으로 사용되지 않도록 관리해야 합니다. 저자는 "처음부터 설계한다면 1순위 선택은 아니다"라고 솔직히 밝힙니다 — 기존 순환 설계를 개선할 때나, 외부 명세가 불행한 Uses-In-The-Interface를 강제할 때 유용합니다.

### 5.4 Dumb Data (멍청한 데이터)

**동료 객체에 대한 의존을 나타내지만, 상위 객체의 문맥에서만 의미를 갖는 데이터를 사용하기.**

opaque pointer의 대안. 타입 안전성은 떨어지지만 **완전히 값 의미론(value semantic)** 을 가집니다.

같은 Graph 예시: `Node`는 (어떤 미지의) Edge 시퀀스에 대한 **정수 인덱스 배열**, `Edge`는 weight + 인접 Node를 가리키는 **정수 인덱스 2개**. 여기엔 상대 타입의 전방 선언조차 없습니다. `Graph`가 인덱스 가능한 시퀀스를 들고 일관성을 유지하며, 인덱스의 해석은 전적으로 부모의 손에 있습니다(음수를 미연결로 매핑하는 것도 자유).

**opaque pointer와의 차이**:
- opaque pointer: 클라이언트 함수가 `Node`, `Edge` 정의만 알면 됨 (부모 불필요)
- dumb data: 데이터를 해석할 문맥이 필요 → **`Graph`가 클라이언트 함수 시그니처에 들어와야 함**

**dumb data가 유리한 결정적 이유**: 값이 실행 중 프로세스와 무관하게 독립적이므로 **직렬화(serialization)로 외부화 가능**합니다. 포인터는 불가능하죠. 저자는 실무에서 dumb data(특히 음이 아닌 정수 인덱스)가 opaque pointer보다 의존성을 **완전히 제거**하는 데 여러 차례 매우 유용했다고 밝힙니다.

### 5.5 Redundancy (의도적 중복)

**커플링을 피하려고 소량의 코드나 데이터를 의도적으로 반복하기.**

저자 본인이 "기법이라기보다 기본 상식"이라고 표현합니다. 모든 코드가 재사용 가능한 것도 아니고, 가능해도 **현재 위치에서 재사용할 가치가 없을 수 있습니다.**

판단 기준 (비대칭성에 주목):
- 무거운 Subsystem A(클라이언트 20개)가 가벼운 Subsystem B(클라이언트 200개)의 기능을 필요로 함 → **A→B 의존은 대체로 괜찮습니다.**
- 반대로 가벼운 B가 무거운 A의 기능을 필요로 함 → **거의 확실히 복제가 낫습니다.** B와 그 200개 클라이언트 전부가 무거운 의존성을 상속하게 되니까요. (단, A의 것이 **vocabulary type**이면 예외 — 함수 인터페이스에 널리 쓰이는 타입은 의존할 만합니다.)
- 상위 시스템에 더 완전하게 구현된 기능의 **아주 작은 부분집합**만 하위가 필요하다면, 그 최소한만 추출하고 상위의 완전한 버전은 그대로 둡니다. 미래 클라이언트는 필요에 따라 선택.

**강한 경고**: 이 기법의 존재가 일상적 copy-paste를 정당화하지 않습니다. demotion이 실행 가능하면 거의 항상 demotion이 낫습니다. 복제된 기능이 원본과 **lock-step으로 유지되어야 한다면 이 기법 사용은 매우 의심스럽습니다.** 다른 모든 방법을 검토한 후 집단적 판단으로만 적용.

> 저자의 각주가 균형 잡힌 시각을 보여줍니다: "재사용에 광적으로 집착하는 코드베이스"와 "중복이 표준 절차인 코드베이스"를 다 경험한 사람들은 전자의 단점이 후자에 비하면 새 발의 피라고 말합니다. 저자도 동의하지만, 조언은 그보다 미묘하다고 — **한 번에 아주 조금의 중복이 큰 설계 순환을 피하는 유일한 방법일 때만** 쓰라는 것.

### 5.6 Callbacks (콜백) — 위상이 가장 크게 올라간 기법

**(보통 하위) 하위시스템이 더 전역적 문맥에서 특정 작업을 수행하게 하는, 클라이언트가 제공하는 함수.**

원래는 잘못 배치된 멤버 함수의 의존 방향을 표면적으로 뒤집는 "최후의 수단"이었는데, 이제는 함수와 함수 객체(functor) 모두를 포함하고, 런타임(추상 기반 클래스) 또는 컴파일 타임(메서드 템플릿) 결합이 가능한 **일급 설계 전략**입니다. (C++11 lambda가 이를 크게 촉진)

5가지 유형:

| 유형 | 내용 |
|---|---|
| **Data callback** | 상위에서 유지되는 저장 공간의 주소를 하위 함수에 전달. 결과 객체를 첫 인자로 주는 흔한 패턴 — 공급자와 소비자를 분리. (저자도 "data는 callable이 아니라 명칭이 혼란스럽다"고 인정) |
| **Function callback** | 함수 포인터. 콜백이 `main`과 함께 살게 하여 프레임워크의 상향 의존을 제거 |
| **Functor callback** | 상태를 가질 수 있는 함수 객체. 임의의 Event를 EventMgr에서 분리 |
| **Protocol callback** | 순수 추상 인터페이스를 통한 콜백. **매우 낮은 레벨에 상당한 기능을 주입** 가능 (Logger-Transport-Mail 하위시스템 수리 예시) |
| **Concept callback** | 템플릿 + concept으로 컴파일 타임 결합. 바이트 스트림 표준화 4개 대안(단일 구상 클래스 / 중복 / 추상 인터페이스 / **concept**)의 비교 |

### 5.7 Manager Class (관리자 클래스)

**하위 객체들을 소유하고 조율하는 클래스를 세우기.**

고전 예시 — 단일 연결 리스트: `Link` 클래스 하나로 리스트를 구현하는 게 타당한가? 즉 `Link`의 소멸자가 **같은 타입의 다른 객체**를 파괴하는 게 합당한가? 저자의 답: **단호히 아니오.**
```cpp
Link::~Link() { delete d_next_p; }  // "우아한" 재귀 파괴 — BAD IDEA
```
저자의 각주: 이 기법은 터무니없이 느릴 뿐 아니라, **충분히 긴 리스트에서 조만간 스택 오버플로를 일으킵니다.**

올바른 구조: `List<T>`(manager)가 `Link<T>`의 할당·생성·파괴·해제와 올바른 구성을 **전적으로 책임**집니다. `Link<T>`는 자기 `T` 인스턴스만 관리하고 다른 `Link<T>`의 수명에는 절대 관여하지 않습니다. 메모리 풀에 대한 의존도 manager가 가집니다.

핵심 원칙: **계층적 소유 관계가 런타임 객체 구성이 아니라 타입 시스템에 의해 통제되어야 합니다.** 이건 저자가 건전한 물리 설계의 근본으로 봅니다.

Graph를 `Node`+`Edge` 두 타입만으로 만들려는 시도는 왜 실패하는가: `addNode()`를 어디 둘 것인가? 새 노드를 누가 추적하는가? 노드들을 어떻게 순회하는가? **무엇이 그래프 전체를 대표하는 객체인가?** `removeNode()`는 `Node`의 멤버가 될 수 없습니다(연결된 Edge에 dangling pointer가 남으므로). `Edge`를 "Graph처럼" 취급하면 `Link`=`List` 문제가 재발합니다. → **3개 타입(Graph manager 포함)이 필요합니다.**

### 5.8 Factoring (팩토링)

**과도한 물리 커플링에 얽힌 복잡한 컴포넌트의 구현에서 독립 테스트 가능한 하위 동작을 빼내기.**

이 기법이 다루는 현실: 우리가 만드는 소프트웨어의 모든 측면이 우리 통제하에 있는 건 아닙니다. 표준화되었거나 외부 명세로 정해진 컴포넌트의 **인터페이스에 있는 순환은 불변일 수 있습니다.** 그래도 **구현은 분해 가능할 수 있습니다.**

인터페이스가 계약상 순환 의존인 A, B, C가 있고 한 컴포넌트에 다 넣기엔 너무 크다면 → 독립 테스트 가능한 구현 기능을 충분히 빼내서, 남은 순환 부분만 한 컴포넌트에 들어가게 합니다. **구현을 잘 팩토링할수록 테스트 가능성이 올라갑니다** — 계층적 재사용까지는 못 가더라도.

Stroustrup 인용: "인터페이스와 구현의 의존성은 별도로 고려해야 한다. 둘 다 DAG가 이상적이지만, **인터페이스에 대해 훨씬 더 중요하고 훨씬 더 자주 달성 가능하다.**"

템플릿 팁: 템플릿 구현에서 **비템플릿 기능을 최대한 빼내면** 컴파일 시간과 코드 크기를 줄일 수 있습니다.

### 5.9 Escalating Encapsulation (캡슐화의 승격) — 가장 정교한 기법

**구현 세부가 클라이언트로부터 숨겨지는 지점을 물리 계층의 더 높은 곳으로 옮기기.**

이 기법이 해결하는 딜레마: 컴포넌트보다 큰 구현 세부를 숨기고 싶은데, (a) 컴포넌트 간 friendship 금지 규칙을 위반하거나(BAD), (b) 단일 컴포넌트를 무한히 크게 만들어야(BAD) 하는 상황.

**핵심 발상**: 하위 구현 컴포넌트들을 **공개 시야에서 숨길 필요가 없습니다. 숨겨야 하는 것은 그것들의 *사용*입니다.** 하위 컴포넌트가 클라이언트 대면 하위시스템의 **프로그래밍적으로 접근 가능한 인터페이스에 기여하지 않는 한**, 그것들은 사실상 캡슐화된 것이며 동시에 다른 하위시스템의 재사용에도 열려 있습니다.

**Car/Engine/SparkPlug 은유**:
- `Car`가 `Engine`을 인터페이스에 노출 → `Engine`을 `MyEngine`으로 바꾸면 클라이언트가 코드를 고쳐야 함
- `Engine`이 `SparkPlug`를 인터페이스에 노출 → 엔진에 접근 가능하면 스파크 플러그에도 접근 가능 → **점화 플러그 타입조차 못 바꿈**
- 개선: `Car`가 `Engine`을 **구현에서만** 사용 → 클라이언트는 `Engine`에 프로그래밍적 접근이 없으므로, `Engine`이 `SparkPlug`를 인터페이스에 쓰든 상관없음
- 더 개선: `Car`는 `Fuel`만 인터페이스에 노출(주유는 필요하니까), `Engine`은 구현에만. → **같은 `Fuel`을 쓰는 다른 엔진으로 교체해도 클라이언트 코드 변경 불필요**

**Graph 예시의 일반해**: `Graph`의 인터페이스에는 **값 타입 `NodeData`, `EdgeData`만** 통과시키고, `Node`, `Edge`, `std::vector`는 구현 전용 컴포넌트에 둡니다. 그러면 (1) opaque pointer를 dumb data로 바꾸는 등 구현을 자유롭게 변경 가능, (2) `Node`/`Edge`에 제공할 수 있는 기능이 제약받지 않음. `Node`/`Edge`를 노출하면 클라이언트가 `Graph`와 동일한 접근권을 갖게 되어, 불변식 유지를 위해 **아무 클라이언트도 못 하게** 심하게 제약해야 합니다.

**단일 컴포넌트 wrapper (facade)**: 하위시스템 전체의 사용을 캡슐화하는 한 컴포넌트. 공개 소비를 쉽고 안전하게 만들고, 하위 구현을 폭넓게 재작업할 유연성을 줍니다.
- **오버헤드 주의**: wrapper 경유는 런타임 오버헤드가 있고, 컴파일 타임 커플링까지 없애는 **insulating wrapper**는 오버헤드가 극적으로 커집니다. 그래서 wrapper는 성능 저하가 수용 가능한 **충분히 높은 레벨**에 위치해야 합니다.
- **확장 한계**: 임의 크기의 하위시스템으로 확장되지 않습니다(단일 컴포넌트에 다 못 들어감).

**다중 컴포넌트 wrapper (shadow class 기법)** — 저자가 "이단적(heretical)"이라 부르는 신기법:
1. 각 클라이언트 대면 타입의 컴포넌트를 복제
2. 원본들을 구현 타입으로 개명(`NodeImp`, `EdgeImp`, `GraphImp`)
3. 새 클라이언트 대면 타입의 데이터 멤버를 **대응 구현 타입의 임베디드 멤버 하나로** 교체
4. 노출할 각 메서드를 (보통 inline) "magic" 포워딩 함수로 구현 — `reinterpret_cast`로 하위 타입 접근

이건 **패키지 수준 friendship의 매우 제한된 형태를 시뮬레이션**하는 것입니다. 저자 본인이 "sketchy but legal(수상하지만 합법)"이라고 인정하고, 각주에서 이렇게 씁니다: *"이상적으로는, C++ 모듈 기능이 언젠가 이런 우아하지 못한 문법적 '해킹'이 헛되이 시도하는 것을 훨씬 잘 해내기를 바란다."* — C++ 표준위원회 위원인 저자의 솔직한 심정.

## Part 6. Lateral vs Layered 아키텍처와 CCD (3.7)

### 6.1 초고층 빌딩 비유 (책 최고의 은유)

왜 대도시 초고층 빌딩은 100층 정도를 넘지 않는가? 답은 물리적(하중)이 아니라 **논리적**입니다.

건물이 높을수록 발자국(footprint) 면적당 사람 수가 늘어납니다 → 그들을 일정 지연 내에 수직 이동시키려면 면적당 엘리베이터가 더 필요합니다 → 어느 높이에서 **엘리베이터 샤프트 대비 사용 가능 면적 비율이 경제성을 잃습니다.** 심지어 단순한 수확 체감이 아닙니다: 어느 지점을 넘으면 **층을 하나 더 올릴 때 건물 전체의 면적당 사용 가능 공간이 오히려 줄어듭니다.**

→ 대도시엔 높은 건물이 많지만 극단적으로 높은 건물은 없습니다. **소프트웨어도 수직보다 수평(lateral)으로 더 잘 확장됩니다.**

### 6.2 고전적 계층(Layered) 아키텍처의 문제

전형적 4층: DB/데이터피드(기반) → 비즈니스 객체(Account, Security) → 비즈니스 서비스(getAccountBalance) → 프레젠테이션.

문제: `Account`가 DB에 직접 묶이면, `Account`에 의존하는 `getAccountBalance`도 **전이적으로** DB에 의존합니다. 결과적으로 **모든 것이 물리적으로 DB에 의존**합니다.

파생 문제들:
- 노트북에 비즈니스 객체 몇 개만 올려놓고 새 서비스를 실험할 수 없습니다. 모든 개발이 하위 구상 설비의 문맥에서만 가능합니다.
- 하위 설비가 구상(concrete)이므로 논리 인터페이스가 **현재 구현에 은근히 영향받습니다** → 나중에 기술을 교체하는 게 비싸고 위험해집니다.

**1차 개선(순수 조합 설계 내에서)**: 무거운 의존성(DB)을 하위 비즈니스 객체에서 **escalate해 `main` 쪽으로** 올립니다. 그러면 저수준 vocabulary 객체를 자유롭게 재사용할 수 있고, 그것들을 다루는 서비스도 무거운 인프라 없이 개발·배포할 수 있습니다.

### 6.3 CCD (Cumulative Component Dependency) — 정량 지표

**정의(요지)**: 하위시스템 내 각 컴포넌트마다 독립 테스트 드라이버를 만들 때의 **총 링크 타임 비용과 상관되는 지표**. 각 컴포넌트가 (자신 포함) 링크해야 하는 컴포넌트 수의 합.

3개 컴포넌트 시스템의 CCD 비교 (직관을 잡는 예):

| 구조 | CCD | 계산 |
|---|---|---|
| 수평(전부 독립) | **3** | 1+1+1 |
| 트리형 (leaf 2 + level 2) | **5** | 1+1+3 |
| 수직(체인) | **6** | 1+2+3 |
| 순환(규칙 위반) | **9** | 3+3+3 |

**계층 패턴 3종의 CCD** (각 하위시스템 15개 컴포넌트 가정):

| 패턴 | 설명 | CCD |
|---|---|---|
| **Light layering** | S의 최상위 컴포넌트만 R에 의존 | **85** |
| **Corresponding layering** | U의 leaf가 V 전체에서 쓰이지만 V 최상위만 U에 무겁게 의존 | **92** (+8%) |
| **Heavy layering** | Y의 최하위가 X의 최상위에 의존 | **190** (2배 이상) |

heavy layering은 배포 방식과 무관하게 **Y를 조금이라도 쓰면 X 전체에 물리 의존**합니다. 좁게 쓰이는 작은 하위시스템엔 수용 가능할 수 있지만, 그 외엔 회피 대상. (예외: `bsl`, `bdl` 같은 "수평" 저수준 재사용 라이브러리는 어디서나 쓰여도 됩니다.)

> **핵심 함의**: 하위시스템 *내부*의 물리 의존성만으로도 빌드 시간이 컴포넌트 수에 대해 **초선형(superlinear)으로** 증가합니다. leaf는 싸게 테스트되지만 **평균 컴포넌트당 링크 비용은 leaf로부터의 거리에 따라 급증**합니다. TDD처럼 점진적 테스트를 하는 개발자에게 특히 치명적입니다.

### 6.4 Lateral 아키텍처 — 해법

**두 가지 접근**:

**(1) Value type 중심 재구성**: 값 타입을 채우는 기능(DB에서 populate)과 그것을 쓰는 기능(비즈니스 로직)을 **독립적 동료(peer)** 로 만들고 각각 하위 값 타입에 의존하게 합니다. → populator 담당자와 business logic 담당자가 서로 영향받지 않습니다.

**(2) Protocol(순수 추상 인터페이스) 기반**: 무거운 leaf 의존성을 protocol로 교체하고, 그 protocol을 구현하는 **adapter**를 상위에 둡니다. 구상 구현은 상위 agent(예: `main`)가 생성해 주입합니다.

전형 예시: Business Object Loader가 독점 DB에 직접 의존하는 대신 `Persistor` protocol에 의존 → 상위에 `ProprietaryPersistor` adapter. Oracle로 바꾸려면 `OraclePersistor` adapter만 만들고, **소스 변경은 `main`의 구상 타입 이름 하나뿐이며 `main` 외에는 재컴파일조차 필요 없습니다.**

Protocol 활용 4패턴: (a) 상위에 있어야 할 protocol을 구현하는 협업적 하위시스템 / (b) 기존 하위시스템을 **adapt** (adapter가 별 작은 UOR에) / (c) 전사 vocabulary가 된 저수준 재사용 protocol을 직접 구현 / (d) 비협업 기술을 그 표준 protocol에 adapt.
표준화 후보: persistence, serialization, IPC, **메모리 할당**(저자 코드베이스에서 메모리 자원 관리 추상 인터페이스는 완전히 보편화됨).

**"기술에 베팅하지 않고 활용하기"**: 특정 전송 메커니즘(소켓)에 표준화하면 나중에 공유 메모리, openSSL, MQSeries, ASIO 같은 새 기술을 (심지어 같은 프로세스에서 나란히) 쓸 수 없습니다. 안정적 인터페이스에 adapt하면 **기술을 활용하면서 그것에 베팅하지 않을 수 있습니다.**

**성능 대안**: 런타임 성능이 문제면 protocol 대신 **멤버 함수 템플릿**으로 컴파일 타임 결합. 물리적으로 독립적이고 유연하며 런타임 효율적이지만, 협업적이고 컴파일 타임 커플링이 강합니다.

### 6.5 Mocking에 대한 균형 잡힌 시각

lateral 설계는 자연스럽게 **mock**(protocol을 구현하는 더미)을 가능하게 하여, 끌어내기 어려운 실패 조건을 테스트할 수 있게 합니다.

**하지만**: "mock할 수 있다는 것 자체가 protocol을 도입할 충분한 정당화가 되는 경우는 거의 없습니다." 순전히 테스트 목적으로 lateral 구조를 억지로 만들면 — Jonathan Wakely의 표현을 저자가 인용합니다 — *"설계를 조롱거리로 만들 수 있다(make a mockery of your design)"*. 더 복잡해지거나 비효율적이 되거나, 둘 다.

### 6.6 언제 layered가 옳은가

작고 잘 다듬어진, 단일 알고리즘이나 외부 자원 기반의 고성능 코드 조각에는 **layered가 이상적**입니다. 이해하기 쉽고 인라이닝과 함수 경계 넘는 최적화를 촉진합니다. 문제는 규모가 커질 때 (1) 새 기술 주입 불가, (2) CCD 증가로 컴포넌트당 개발 비용 상승 — 이 두 가지입니다.

## Part 7. Encapsulation vs Insulation (3.10~3.11)

### 7.1 두 개념의 정확한 구별 — 이 책의 중요 기여

| 개념 | 정의 |
|---|---|
| **Encapsulated** (캡슐화) | 구현 세부를 변경·추가·제거해도 클라이언트가 **코드를 고칠 필요가 없다** |
| **Insulated** (절연) | 구현 세부를 변경·추가·제거해도 클라이언트가 **재컴파일할 필요조차 없다** |

**insulation은 encapsulation의 물리적 대응물**이며 더 강한 성질입니다. (insulation은 실무상 항상 encapsulation을 함의합니다.)

**컴포넌트 관점의 예시**: 컴포넌트 `c`가 `A`(`a.h`를 `c.h`에서 include)와 `B`(`b.h`를 `c.cpp`에서만 include)를 구현에만 사용하고, `d`가 `c`를 씁니다.
- `c`는 **`A`의 *사용*을 캡슐화**합니다. (`A` 자체를 캡슐화하는 게 아닙니다 — `A`는 공개 클래스니 누구나 직접 include해 쓸 수 있습니다. `c`를 통해서는 `A` 객체를 넣거나 뺄 프로그래밍적 구멍이 없다는 뜻)
- `c`는 **`B`의 사용을 *절연*** 합니다. `b.h`가 바뀌어도 `d`는 재컴파일할 필요가 없습니다.

→ **헤더에 include를 최소화하는 것이 곧 절연입니다.** 이것이 `.cpp`로 include를 밀어내는 실질적 동기.

### 7.2 왜 insulation이 사업적으로 중요한가 — patch

- 전체 시스템을 재빌드해 critical bug를 고치는 게 릴리스 사이에 **감당 불가능**할 수 있습니다(핵심 인력 부재 등).
- **patch** = 이미 릴리스된 버전에 대한 국소적 변경. 물리 인터페이스와 계약이 변하지 않으면, 수정된 구현을 재컴파일해 **끼워 넣을(drop in)** 수 있습니다 — 다른 컴포넌트 재컴파일 없이.
- 즉 **얼마나 빠르게 패치하고 재릴리스할 수 있는지는 구현 세부가 얼마나 절연되어 있는지에 직접 비례합니다.** 주요 인터페이스 경계에서는 절연이 설계 목표여야 합니다.

### 7.3 Total vs Partial Insulation

- **Total**: 구현의 어떤 측면이 변해도 클라이언트가 재컴파일할 필요 없음 → **아키텍처에 영향을 줍니다.**
- **Partial**: 일부 (이상적으로 안정적인) 측면은 클라이언트 컴파일러에 노출, 전략적/변덕스러운 부분은 `.cpp`에 숨김 → 단일 컴포넌트의 구현 세부일 뿐 (Vol II 6.6에서 다룸).

### 7.4 Total Insulation 3대 기법

#### (1) Protocol (순수 추상 인터페이스) 클래스 — 가장 효과적

**언제**: 이미 상속을 쓸 예정이라면 거의 항상 옳은 선택.

**문제 상황 예시**: `Shape` 기반 클래스가 좌표를 `short int` private 멤버로 갖고, `Circle`/`Rectangle`이 상속하고, 클라이언트들이 `Shape` 인터페이스만 씁니다. 어느 날 좌표 범위를 늘리려고 `short int` → `int`로 바꾸면 **재컴파일해야 하는 것은?** 답: **전부.** 파생 클래스는 물리 레이아웃이 lock-step으로 변해야 하고, 클라이언트도 vtable 포인터 위치가 바뀔 수 있어 재컴파일 없이는 동작하지 않습니다. 이 개선이 필요 없는 클라이언트까지 강제로 재컴파일·재배포해야 합니다.

**해법**: 기반 클래스에서 **순수 추상 인터페이스를 추출**합니다. 기존 `Shape`를 `ShapePartialImp`로 개명하고, 새 순수 추상 `Shape` protocol에서 파생시킵니다. 클라이언트는 `Shape`를 그대로 쓰지만 공유 구현 변경에 재컴파일하지 않습니다. 보너스: 새 구상 구현(`Box`)이 protocol에서 직접 파생해 `ShapePartialImp`의 공간 오버헤드를 피할 수 있습니다.

**Bridge 패턴 대안**: 구현 상속(`ShapePartialImp`) 대신 별개 구상 클래스(`IntPoint`, `ShortPoint`)로 대체. 저자의 입장: **인터페이스 상속만이 진정한 가치를 더합니다. 구현 상속의 사용은 어떤 것이든 의심스럽습니다** — 특히 라이브러리 컴포넌트에서.

**왜 protocol이 최고의 절연체인가**: 데이터 멤버도 private 멤버 함수도 노출되지 않습니다. protected 기능(파생 클래스 작성자용)도 partial implementation이나 별도 utility로 escalate 가능하므로 **공개 클라이언트의 컴파일러가 볼 필요가 없습니다.** 생성자처럼 구현 특정 인터페이스도 추상 인터페이스로는 안 보입니다. 심지어 protocol 인터페이스에 쓰이는 타입들도 `#include` 대신 **로컬 선언**으로 처리해 절연합니다.
> 추가 이점: 클라이언트가 구현체에 대한 **링크 타임 의존조차 없습니다.** (구상 파생 타입을 생성하는 agent가 클라이언트보다 상위에 있으므로)

**중요 지침**: 상속이 관여할 때 protocol 추출은 **결과적 절연의 가치와 무관하게** 비순수 추상 기반 클래스의 인터페이스와 구현을 팩토링하는 일반 기법으로 써야 합니다.

#### (2) 완전 절연 구상 wrapper 컴포넌트

**언제**: 같은 클라이언트가 객체를 생성하고 사용해야 하는 하위시스템(상속 부적합). 이미 encapsulating wrapper가 있으면 전환이 쉽습니다.
**한계**: (a) 상당한 런타임 오버헤드, (b) 다중 컴포넌트 wrapper는 friendship 규칙 때문에 일반적으로 불가능 → **필요한 wrapper 클래스 수가 고정적(또는 매우 느리게 증가)이고 단일 컴포넌트에 들어갈 만큼 작을 때만** 가능. (c) 클라이언트는 감싼 구현의 의존성을 여전히 상속합니다.

#### (3) Procedural Interface (PI)

**언제** (3가지 경우):
1. **Legacy 하위시스템** — 크고 성숙한 코드. 내부 타입이 애초에 재사용에 적합하지 않을 수 있음. 성능은 다소 저하되지만 유지보수성·사용성 개선으로 **순이익**이 남습니다.
2. **활발히 개발 중인 (수평) 라이브러리** — 넓은 인터페이스가 여러 컴포넌트에 걸쳐 있어 단일 컴포넌트 wrapping이 비현실적. 어느 부분에 기능이 추가될 때마다 **모든 클라이언트를 재컴파일시키는 것은 나쁜 설계 선택**. PI는 멤버 함수 단위의 세분화된 수정을 허용합니다.
3. **C 언어 어댑터** — C++로 쓰인 것을 C 클라이언트가 쓰게. 이 경우 멤버 함수·inline·상속·템플릿을 애초에 쓸 수 없으므로 **절연으로 인한 재사용 손실이 없습니다.**

**PI의 8가지 필수 속성** (거의 기계적으로 생성 가능하게 만드는 규칙들):
1. 각 PI 함수는 접근 대상과 **물리적으로 분리된 컴포넌트(보통 UOR)** 에 위치
2. 각 PI 함수는 다른 모든 PI 함수와 **논리적으로 독립** (개별 승격의 유연성 확보)
3. **PI 레이어 내부에 물리 의존성이 없음** — PI 컴포넌트는 다른 PI 컴포넌트를 include하지 않음. 모두 level 1
4. **PI 레이어에 보충 기능 없음** — 번역과 절연만. 도메인 기능을 추가하지 않으면 거의 기계적으로 만들 수 있고, 부적절하게 동원되어 설계 순환에 기여할 여지가 없습니다
5. **하위 컴포넌트와 1-1 매핑** (`z_` 접두사 사용). 패키지 `abcx` → 자매 패키지 `z_abcx`. 구현 전용 컴포넌트에는 대응 PI 컴포넌트를 만들지 않음
6. PI 이름이 **예측 가능**(규칙적)
7. **C와 C++ 양쪽에서 호출 가능**
8. 실제 하위 C++ 타입을 **불투명하게(opaquely) 취급** → 따라서 PI는 설계상 **진짜 wrapper가 아닙니다**

> `z_` 접두사의 유래: 전기공학에서 Z가 임피던스(저항, 절연)를 뜻하기 때문 + "우리도 유머 감각은 있다"는 저자의 각주. 임의적 선택이며 `c_` 같은 것도 무방합니다.

**PI의 중요한 성질**: 타입을 캡슐화 목적으로 숨기는 게 **아닙니다.** 클라이언트가 하위 헤더를 직접 include하기로 선택하면 **insulation만 포기하고 encapsulation은 유지**합니다. 그래서 side-by-side 재사용을 막지 않습니다.

**PI의 대가**: 상당한 오버헤드와 충실도(fidelity) 손실 — 상속·템플릿에 대해 특히. side-by-side 재사용 가능성을 제한할 수 있는 문맥에서는 **절대 쓰지 말아야 합니다.**

### 7.5 물리적 상호운용성 (3.9) — BAD IDEA 목록

계층적 재사용을 저해하는 것들. 전부 "…는 BAD IDEA" 형태로 제시됩니다:

- **도메인 특정 조건부 컴파일** (`#ifdef`로 도메인 분기)
- **라이브러리 컴포넌트의 애플리케이션 특정 의존성**
- **재사용을 인위적으로 제약하는 논리 구조/패턴** (static 변수, **singleton 패턴**)
- **`main`을 정의하는 파일 밖에서 전역 엔티티 정의**
- **논리적 캡슐화 목적으로 헤더 파일 숨기기** — 재사용 가능한 소프트웨어를 숨기는 것도 BAD IDEA
- **비이식적(nonportable) 소프트웨어에 대한 격리되지 않은 의존** — 최소화하고 격리하라
- **라이브러리 컴포넌트에서 전역 자원을 강탈(usurp)하기**
- **Guideline**: 설계는 **우발적 오용(accidental misuse)을 막되 사기(fraud)를 막으려 하지 말라.** 악의적 우회를 막는 것은 목표가 아닙니다.

## Part 8. 규칙 빠른 참조 (부록 압축)

### 8.1 반드시 (Design Imperatives) — 6개
Part 3.2 참조. 요약: **모든 레벨에서 순환 금지 + 장거리 friendship 금지 + 계층적 테스트 가능성**.

### 8.2 핵심 Design Rules 요약
- 아키텍처적으로 유의미한 모든 이름은 **전사 유일**
- 컴포넌트 = `.h`+`.cpp` 같은 루트 이름 + 4가지 속성
- 컴포넌트는 패키지 안에, 이름은 `패키지명_`로 시작
- 논리 엔티티는 패키지 namespace 안에, 패키지 namespace는 전사 namespace 안에
- 패키지 namespace 스코프의 이름은 컴포넌트 base name 접두 (operator/aspect 제외)
- 패키지 namespace 스코프에는 class/struct/free operator만
- 함수 스코프 밖 `using` 금지
- include guard = `INCLUDED_PACKAGE_COMPONENTBASE`
- inline 등 비-internal-bindage 구조는 선언과 정의를 분리, free 함수 정의는 namespace 밖
- **파일/namespace 스코프 static의 런타임 초기화 금지**
- 직접 실질 사용하면 직접 `#include` (예외: public 상속뿐)
- `_`는 구분자로 쓰지 않음 (대문자 단어 사이, `d_`/`s_`/`e_`/`k_`/`_p` 제외)
- 패키지/패키지 그룹의 허용 직접 의존성을 **명시**
- 패키지 그룹명 = 정확히 3자 소문자 영숫자, 유효 식별자
- 그룹 내 패키지명 = 그룹명 + 1~3자
- 컴포넌트마다 유일한 `.t.cpp`, 같은 디렉터리, 의존성은 대상 컴포넌트 이하
- `#include`에 경로 금지
- 배포용 분할은 아키텍처적으로 유의미하지 않아야 함

### 8.3 자주 인용할 Guidelines
- 물리 집약체는 설계상 **원자적으로** 취급
- 컴포넌트당 public 클래스 하나 (엔지니어링 정당성 없으면)
- **클라이언트가 대체로 서로 다를(disjoint) 기능은 colocate하지 말 것**
- 재사용 컴포넌트 기능은 **complete + minimal + primitive**
- 비primitive는 상위 utility struct로
- 런타임 효율 최대 + 구현 선택지 최대한 열어두기
- 함께 변할 코드는 colocate
- 긴밀한 상호 협업은 단일 UOR로 제한
- 패키지는 가능하면 적절한 패키지 그룹에 소속
- 패키지 그룹 허용 의존성은 **최소로, 거의 늘리지 말 것**
- 공유 UOR 이름은 사용 전 **중앙 등록**
- 범용 기능은 항상 팩토링하고 선제적으로 demote

## 부록 A. 용어집

| 용어 | 뜻 |
|---|---|
| **Component** | `.h`+`.cpp`(+`.t.cpp`). 논리·물리 설계의 원자 단위. 물리 집약의 최내층 |
| **Package** | 컴포넌트보다 큰, 아키텍처적으로 유의미한 최소 집약체. 공통 namespace 공유 |
| **Package Group** | 패키지들의 응집적 집합. 3번째(최상) 집약 레벨. 3자 이름 |
| **UOR (Unit of Release)** | 물리 집약의 최외층. 독립 릴리스 단위 |
| **Architecturally significant** | 이름이 정의된 UOR 외부에서 의도적으로 보이는 것 |
| **Manifest** | 집약체 구성원 명세(메타데이터) |
| **Allowed dependency** | 존재가 허용된 물리 의존성(메타데이터) |
| **Depends-On** | 컴파일·링크(집약체는 테스트까지)에 필요한 관계. **전이적** |
| **Level number** | 물리 계층에서의 위치. leaf=1. 순환 없을 때만 부여 가능 |
| **Levelizable** | 레벨 번호 부여가 가능한 = 순환이 없는 |
| **Linkage** | (논리, 표준) external/internal/none — 다른 스코프의 엔티티를 지칭 가능한지 |
| **Bindage** | (물리, 저자 명명) internal/external/dual — 정의와의 결합이 컴파일/링크 타임 중 언제인지 |
| **ODR** | One Definition Rule |
| **Primitive** | 효율적 구현에 private 접근이 본질적으로 필요한 연산 |
| **Encapsulated** | 변경 시 클라이언트가 **코드를 고칠** 필요 없음 |
| **Insulated** | 변경 시 클라이언트가 **재컴파일할** 필요 없음 |
| **Protocol class** | 순수 추상 인터페이스 (순수 가상 함수 + 비인라인 virtual 소멸자, 데이터 멤버 없음) |
| **Transitive include** | 다른 헤더가 include해주는 것에 의존 — **금지** (public 기반 클래스만 예외) |
| **Component-private class** | 추가 `_`로 표시, 컴포넌트 외부 직접 사용 금지 |
| **Subordinate component** | base name에 `_`, 접두사가 되는 컴포넌트만 include 가능 |
| **Irregular package** | 설계 규칙(특히 명명)을 따르지 않는 컴포넌트로 구성된 패키지 (legacy/3rd-party) |
| **CCD** | Cumulative Component Dependency. 독립 테스트 드라이버들의 총 링크 비용 지표 |
| **Escalation / Demotion** | 기능을 물리 계층 위로 / 아래로 옮기기 |
| **Opaque pointer** | 정의 없이 이름만으로 타입을 가리키는 포인터 (Uses-In-Name-Only) |
| **Dumb data** | 상위 문맥에서만 의미를 갖는 정수 인덱스 등. 값 의미론 유지 |
| **Escalating encapsulation** | 구현 세부가 숨겨지는 지점을 상위로 올리기 (그 *사용*을 숨김) |
| **Lateral architecture** | 무거운 leaf 의존을 protocol로 대체해 수평화한 구조 |
| **Vocabulary type** | 함수 인터페이스에 널리 쓰이는 타입 (의존해도 되는 예외적 대상) |
| **Software Capital** | 전사적으로 축적된 잘 설계된 재사용 컴포넌트 저장소 = 자본 자산 |
| **Malleable / Stable** | 변경이 쉬움 / 변하지 않음. 좋은 코드는 둘 중 하나여야 함 |

## 부록 B. 이 책을 한 장으로 (핵심 명제 12개)

1. **물리 설계는 논리 설계의 전제 조건이다.** 문제를 처음 분해하는 순간부터 고려해야 한다.
2. **재사용 가능한 것은 안정적인 것뿐이다.** malleable한 코드는 최상위에 있고 공유되지 않아야 한다.
3. 계층적 재사용은 **집요한 세분화**의 결과이며, 저절로 생기지 않는다.
4. **컴포넌트가 설계의 원자 단위**다. 클래스가 아니다.
5. 컴포넌트의 크기 상한은 **단일 테스트 드라이버로 철저히 테스트 가능한가**로 정해진다.
6. **모든 레벨에서 순환 물리 의존은 금지**다. 순환은 반드시 재작업으로 제거한다.
7. **장거리 friendship 금지**가 물리 설계의 많은 결과를 파생시킨다 (다중 컴포넌트 wrapper 불가 등).
8. 사용 지점만 보고 **정의 위치를 알 수 있어야** 한다 → 명명 규칙과 짧은 패키지명.
9. **기능은 complete + minimal + primitive.** 비primitive는 상위 utility로 escalate.
10. **layered는 확장되지 않는다.** 초고층 빌딩처럼. protocol로 lateral하게 만들어라.
11. **encapsulation(코드 수정 불필요) ≠ insulation(재컴파일 불필요).** 후자가 패치 능력을 결정한다.
12. 나쁜 물리 설계의 뿌리는 **과도한 링크·컴파일 타임 의존성**이다. 이를 선제적으로 최소화하는 것이 진정한 설계 품질을 만든다.

**저자의 인과 사슬** (결론부): 물리 설계 부실 → 테스트 가능성↓ / 사용성↓ / 수정 가능성↓ → 신뢰성↓, 유지비↑, 실행 파일 크기↑, 런타임 성능↓. 간접 원인은 링크 시간↑, 이해도↓, 컴파일 시간↑. **테스트 드라이버 링크가 비싸면 테스트 예산당 테스트량이 줄고, 재사용이 링크 시간을 늘리면 재사용되지 않으며, 이해하기 어려우면 테스트·재사용·수정이 모두 어려워진다.**

## 부록 C. DB 엔진 개발자 관점 — CUBRID 같은 코드베이스에 대응시키기

이 책은 HFT 책들과 달리 **당신 업무에 직접 쓸 수 있습니다.** 대형 C++ 서버 엔진에서 흔히 겪는 문제와 이 책의 처방을 매핑하면:

| 실무 증상 | 이 책의 진단·처방 |
|---|---|
| 헤더 하나 고치면 전체 재빌드 | **insulation 부족**(7.1). `.h`의 `#include`를 `.cpp`로 밀어내고, 로컬 전방 선언 활용. 주요 인터페이스 경계에 protocol 도입 |
| 특정 모듈 하나만 떼서 단위 테스트가 불가능 | **CCD가 높고 heavy layering**(6.3). leaf가 무거운 하위시스템에 의존하는 구조를 lateral로 전환 |
| 순환 include로 컴파일이 깨짐, `#ifdef` 가드로 임시 봉합 | **레벨화 기법 9종**(Part 5)이 정확히 이 문제의 도구 상자. 우선 escalation/demotion 검토 |
| storage↔query↔optimizer가 서로를 참조 | **escalation**: 상호 의존 기능을 상위 새 컴포넌트로. 또는 **opaque pointer/dumb data**로 in-name-only화 |
| 부모-자식 구조에서 자식이 부모 포인터를 들고 있어 순환 | **demotion**(공통 정보 분리) 또는 **opaque back pointer**. Node/Edge/Graph 예시가 B-tree 페이지/노드, 트랜잭션/락 구조에 그대로 대응 |
| 통계 수집·로깅이 코어에 박혀 있어 코어가 무거움 | **Slowpath 분리 + escalation**. 코어 타입은 primitive만, 나머지는 상위 utility로 |
| 플랫폼별 코드가 도메인 코드에 섞여 있음 | **"비이식 소프트웨어는 최소화하고 격리하라"**(7.5). adapter + protocol로 lateral화 |
| storage manager 등이 전역 싱글톤 | **"singleton은 재사용을 인위적으로 제약한다"**(7.5 BAD IDEA). 상위에서 주입하는 구조로 |
| 소유 관계가 런타임 규약으로만 존재 | **Manager class**(5.7). "계층적 소유는 타입 시스템이 통제해야 한다". 재귀 소멸자는 스택 오버플로 위험 |
| 헤더가 단독 컴파일되지 않아 include 순서에 의존 | **Component Property 1**(`.cpp`가 자기 `.h`를 첫 줄에 include)이 이 문제를 영구히 제거 |
| 어느 파일에 뭐가 있는지 grep으로만 찾음 | **name cohesion**(3.4). `bdlt::Date` → `bdlt_date.h`처럼 사용 지점에서 위치가 도출되게 |
| 오픈소스 라이브러리 연동 코드가 코어에 침투 | **adapter 패키지는 고립시켜 별 라이브러리로 릴리스**(3.1 패키지 그룹 논의). 무거운 의존을 그룹에 섞지 말 것 |
| C API를 함께 제공해야 함 (CUBRID CCI 등) | **Procedural Interface**(7.4-3)의 8가지 속성이 정확한 설계 지침. C 어댑터는 PI의 정당한 3대 용례 중 하나 |

**바로 측정해볼 수 있는 것**: `#include` 지시문만 파싱해 컴포넌트 의존 그래프를 뽑고(Component Property 4의 이점), 순환을 찾고, **CCD를 계산**해보는 것. 스크립트 수십 줄로 됩니다. 리팩토링 전후 비교 지표로 쓸 수 있고, "빌드가 느리다"는 체감을 객관적 숫자로 바꿔줍니다.

**PR/커밋 메시지에 쓸 어휘**: 이 책의 용어(escalate, demote, levelize, insulate, primitive, transitive include, CCD)는 C++ 커뮤니티에서 널리 통용됩니다. "escalated non-primitive functionality to a higher-level utility to break the cyclic dependency"처럼 쓰면 리뷰어가 의도를 즉시 이해합니다.
